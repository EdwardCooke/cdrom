# F-21.2.1 · Source-fetcher service & gRPC contract

> Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **source-fetcher** service skeleton and its gRPC contract: a
dedicated, standalone gRPC process (`cmd/pipelinesource`, logic in
`internal/services/pipelinesource`) in the same shape as the other services
(`db`, `scheduler`, `artifacts`, `idp`) that exposes one RPC, `FetchSource`.
`FetchSource` takes a **reference** (a `<type>:<spec>` string naming the kind
and the file to retrieve — F-21.2.2) and an optional credential (the plaintext
secret material, when one is needed — F-21.3) and returns the file's content,
its version identifier, and its content hash. The fetcher holds no pipeline
definitions, no credentials, and no encryption key at rest; its only on-disk
state is the transient git repository cache (F-21.2.3). It performs a single
fetch per call.

**Why.** Keeping the fetch out of the API and scheduler means neither needs git
installed, outbound network egress, or the source's filesystem. The fetcher can
be run with a network policy that allows only the repos/endpoints it must reach,
and it can be scaled or replaced independently of the control plane. It also
keeps the API's process free of long-running git operations.

**Scope.**
- `cmd/pipelinesource` + `internal/services/pipelinesource` — the **source
  fetcher**: a standalone gRPC server (a new process, like `db` / `scheduler` /
  `artifacts` / `idp`) that performs the actual fetch (delegated to the clients
  in F-21.2.4) and returns the file's content, version, and hash. It holds no
  definitions, no credentials, and no key at rest (its only on-disk state is
  the transient git repository cache) and is dialed **only by the API** over
  gRPC (mutual TLS when a CA is configured).
- `proto/cdrom/pipelinesource/v1/` — the fetcher's gRPC API (`FetchSource`,
  plus the `SourceCredential` message); generated code in `internal/gen/`
  (`make proto`).
- `internal/config` — the fetcher's listen address
  (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`) and its dedicated
  metrics port (F-20).

**Acceptance criteria.**
- [x] The fetcher is a **standalone gRPC server** dialed **only by the API**;
      with a TLS CA configured the connection uses mutual TLS, and without one
      it falls back to plaintext (local dev) — the same convention as the other
      services (`internal/grpcutil`).
- [x] `FetchSource` takes a **reference** (a `<type>:<spec>` string — F-21.2.2)
      and an optional credential, and returns the file's **content**, its
      **version identifier** (the git commit hash, an HTTP
      `ETag`/`Last-Modified`, or the file's mtime), and its **content hash**
      (SHA-256 of the content).
- [x] The fetcher holds **no pipeline definitions, no credentials, and no
      encryption key at rest**; a credential is passed in for one fetch and is
      never persisted or logged. Its only on-disk state is the transient git
      repository cache (F-21.2.3), which is safe to lose (a re-clone rebuilds
      it).
- [x] The fetcher's address comes from config / env
      (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), and it serves
      its own `/metrics` + `/healthz` on a dedicated metrics port (F-20).
- [x] A fetch failure (unreachable repo/endpoint, missing file, auth failure,
      an unknown reference type, or a `file:` reference with no root
      configured) returns a clear gRPC error the API can surface on the
      source's state (F-21.5).

## The source-fetcher service

The actual fetch is done by a dedicated **source-fetcher** service — a separate
process (`cmd/pipelinesource`, logic in `internal/services/pipelinesource`), in
the same shape as the other services (`db`, `scheduler`, `artifacts`, `idp`):

- **A standalone gRPC server.** It exposes one RPC, `FetchSource`, which takes a
  **reference** (a `<type>:<spec>` string — `git` / `http` / `file`) and an
  optional credential (the plaintext secret material, when one is needed) and
  returns the file's content, its version identifier, and its content hash. The
  fetcher holds no pipeline definitions, no credentials, and no encryption key
  at rest; its only on-disk state is the transient git repository cache
  (F-21.2.3). It performs a single fetch per call.
- **Dialed only by the API, over gRPC.** The API is the only caller (the same
  topology rule as the other services: the API talks to everything else). The
  connection uses **mutual TLS** when a TLS CA is configured (`TLSConfig` in
  `internal/config`; creds built in `internal/grpcutil`) and falls back to
  plaintext without one (local dev) — exactly the convention the other services
  follow. The fetcher's address comes from config / env
  (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), and it serves its
  own `/metrics` + `/healthz` on a dedicated metrics port (F-20).
- **Why a separate process.** Keeping the fetch out of the API and scheduler
  means neither needs git installed, outbound network egress, or the source's
  filesystem. The fetcher can be run with a network policy that allows only the
  repos/endpoints it must reach, and it can be scaled or replaced independently
  of the control plane. It also keeps the API's process free of long-running
  git operations — repeated fetches of the same repository are served from the
  fetcher's local cache (fetched from upstream on every request, incrementally) instead of
  re-cloning.
- **Protos.** `proto/cdrom/pipelinesource/v1/` defines `FetchSource` (and the
  `SourceCredential` message); generated code is committed under
  `internal/gen/` (`make proto`). The service impl lives in
  `internal/services/pipelinesource/server.go` and implements the generated
  `*Server` interface (embedding `Unimplemented*Server`), per the gRPC
  conventions.

### The `FetchSource` contract

```
rpc FetchSource(FetchSourceRequest) returns (FetchSourceResponse)

message FetchSourceRequest {
  string reference;             // "<type>:<spec>" — "git" | "http" | "file"
  SourceCredential credential;  // optional; the plaintext secret material for this fetch
}

message SourceCredential {
  string kind;                  // "git-ssh" | "git-https" | "http"
  string username;              // git-https (may be empty for token-only auth)
  string token;                 // git-https / http
  string private_key;           // git-ssh (PEM)
  string host_key;              // git-ssh (expected host public key)
  string header;                // http (header the token is sent in; default Authorization: Bearer)
}

message FetchSourceResponse {
  bytes content;                // the file's content
  string version;               // git commit hash / ETag|Last-Modified / mtime
  string hash;                  // SHA-256 of content (hex)
}
```

The reference selects the kind and carries the locator (F-21.2.2); the
credential is **optional** and is needed only for a private git repository or
an authenticated HTTP endpoint. The `SourceCredential` message carries the
**plaintext** secret material for the duration of one call. The API decrypts it
(F-12) and passes it in; the fetcher uses it to authenticate the fetch and
discards it — it is never persisted or logged. The credential model itself
(kinds, regex matching, encryption at rest, API CRUD) is
[F-21.3](f-21.3-source-credentials.md).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The fetch is a separate process.** The actual fetch (a git clone/fetch from
  the fetcher's on-disk cache, an HTTP GET, or a rooted local file read) is
  performed by a dedicated **source-fetcher** service
  (`cmd/pipelinesource` / `internal/services/pipelinesource`) — a standalone
  gRPC server in the same shape as the other services. It holds no definitions,
  credentials, or key at rest (its only on-disk state is the transient git
  repository cache) and is dialed **only by the API** over gRPC: mutual TLS
  when a CA is configured, plaintext otherwise (the convention in
  `internal/grpcutil`). This keeps git, network egress, and the source's
  filesystem out of the API and scheduler, and lets the fetcher be
  network-policy'd to only the sources it must reach.
- **One RPC, a reference string.** `FetchSource` takes a single **reference**
  (`<type>:<spec>` — `git` / `http` / `file`) and an optional
  `SourceCredential` (plaintext for the one call) and returns the content,
  version identifier, and SHA-256 hash. The reference is the shared syntax for
  naming a definition file (imports in F-21.4, sources in F-21.5.1). The
  version identifier (git commit hash / `ETag` / mtime) lets a caller detect a
  no-change cheaply; the hash is the authoritative change detector used by the
  sync routine (F-21.5).
- **New fields / RPCs / endpoints (this sub-feature).** A new
  `proto/cdrom/pipelinesource/v1/` gRPC API (`FetchSource` + the
  `SourceCredential` message) with generated code in `internal/gen/` (`make
  proto`); a `cmd/pipelinesource` + `internal/services/pipelinesource` service
  (the fetcher, dialed by the API over gRPC/mTLS); and
  `CDROM_PIPELINE_SOURCE_ADDR` (default `127.0.0.1:7107`) + a dedicated metrics
  port in `internal/config`.
