# F-21.6 · Artifact packages (consumption, publishing, promotion)

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)
>
> **Absorbs [F-19 · Artifact promotion](f-19-artifact-promotion.md).** Packaging and
> promotion are two sides of the same coin — getting a build product from where
> it was made to wherever it is deployed — so F-19 is merged into this
> sub-feature and retired as a standalone row. See the consolidation note at
> the end of this file.

This sub-feature lets a pipeline declare the **packages it consumes** in
`spec.artifacts` — a list of named artifact references. Each entry gives the
artifact a `name` (how the pipeline references it, e.g. in a step's params or
env) and a `package` block describing which package to fetch and how its version
is resolved. When a run is created, the platform resolves each reference to a
concrete package version and PINS the winning registry filing's display name in
the run's snapshot, so the job consumes exactly the version the run resolved
(the job reads the pinned filing straight from the registry — the storage
redesign eliminated the original per-run copy). Beyond declaration and
resolution,
this spec defines how a job pulls the bytes onto the target: two built-in step
handlers — `download_artifact` (copy a named artifact into the job's staged
working area) and `extract` (unpack a tar, gzipped tar, or zip package) — and
completes the loop on both ends of production: a third step handler,
**`publish_artifact`**, that lets a job gather files by glob pattern and
compress them into a zip tied to the job's own namespace, plus the
**publishing endpoint** (today there is no HTTP write path to the store at
all, so this is genuinely new surface) and the **promotion operation** (moved
in from F-19) that moves packages between namespaces.

**Depends on.** [F-21.1](f-21.1-file-format-compiler.md) (the file format +
compiler that reads `spec.artifacts`). It builds on the existing artifacts
service (a namespaced file store) and the run model (F-07). The consumption
half (the step handlers) rides on the stock step machinery — typed steps and
templatable params (F-01/F-10), log streaming (F-02), timeouts and cancellation
(F-03/F-05) — and introduces **no third-party dependency** (tar, gzip, and zip
are all in the Go standard library). Publishing rides on stock authz/audit
([F-14](f-14-rbac.md) / [F-15](f-15-audit-log.md)); promotion destinations tie
in [F-17](f-17-environments.md) (environments frame the target namespace).

**Scope.**
- `internal/pipelinefile` — the `spec.artifacts` field: a list of named artifact
  references (a `name` plus a `package` block with `name`, `tag`,
  `preReleaseRegex`, `allowPreRelease`, and `useLatest`), validated at import.
- `internal/models` — a per-run snapshot of the resolved artifact versions
  (a `name` → pinned registry filing display-name map, stored on the run like
  the rest of the spec, F-01/F-11).
- The **version resolution** logic (latest by upload time, a pinned `tag`, or
  the latest pre-release per `allowPreRelease` / `preReleaseRegex` — evaluated
  in SQL over the registry's storage_object records; pre-release membership is
  an explicit flag stamped at publish time, never parsed from the tag).
- The **run-creation snapshot** step: resolve each reference and pin the
  winning filing's display name on the run (denormalized onto the job
  instances), exposing it to the job by the artifact's `name`.
- `internal/stephandlers` — three new built-in step handlers:
  **`download_artifact`** (copy a named artifact from the registry — or the
  job's own namespace — onto the target), **`extract`** (unpack a tar /
  gzipped tar / zip archive
  into a destination; format detected from magic bytes; path-slip and
  symlink-member defenses), and **`publish_artifact`** (collect files matched
  by multiline glob patterns — supporting `**` recursion and `-`-negated
  exclusions — into a zip that preserves the matched directory structure and
  uploads it to the job's own artifact namespace, so the package is intrinsically
  tied to the job that built it).
- `internal/executor` + `internal/target` — the **job's staged working area**:
  a per-job-instance scratch directory (lazily created, exported to every step
  as `CDROM_STAGE_DIR`, best-effort removed when the job finishes) that is the
  default home for downloaded and extracted packages.
- `internal/api` + `internal/authz` + `internal/audit` — the **publishing
  surface**: the reserved `packages` registry namespace, `POST /api/packages`
  (authenticated, streamed, permission-gated, audited, immutable versions),
  and the registry listing/read-back endpoints.
- `proto/cdrom/artifacts/v1` + `internal/services/artifacts` + `internal/api` —
  the **promotion operation** (former F-19): a server-side blob replication
  (COPY) from one namespace to another, exposed as `POST /api/artifacts/promote`,
  authorized (F-14) and audited (F-15).

**Acceptance criteria.**
- [x] A pipeline can declare `spec.artifacts` — a list of named package
      references (a `name` plus a `package` block with `name`, `tag`,
      `preReleaseRegex`, `allowPreRelease`, and `useLatest`); the platform
      resolves each to a concrete version at run creation and pins the
      winning registry filing's display name in the run's snapshot, exposing
      it to the job by the artifact's `name` (the job reads the pinned filing
      straight from the registry — no per-run copy).
- [x] **Version resolution** — `useLatest: true` uses the latest version of the
      package by upload time (`tag` is ignored); `useLatest` false (or unset)
      uses the exact `tag`. Whether a version is a pre-release is an EXPLICIT
      flag set at publish time (the `prerelease` field of `POST /api/packages`)
      — never inferred from the tag's shape — and flagged versions are not
      selected by default.
- [x] **Pre-releases** — `allowPreRelease: true` opts in to pre-releases: if
      `preReleaseRegex` is also set, only pre-release versions whose tag
      matches that regex are additionally eligible; if `preReleaseRegex` is
      empty, the latest pre-release by upload time is eligible. `preReleaseRegex`
      has no effect when `allowPreRelease` is false.
- [x] The resolved version is recorded on the run (a per-run snapshot, like the
      rest of the spec, F-01/F-11), so a run always uses the version that was
      resolved when it started — re-resolving on a later run can pick up a newer
      version without changing what a past run did.
- [x] A step references the artifact by its `name` (in its params or env); the
      platform makes the resolved package available to the job by copying it onto
      the target with the `download_artifact` step handler and/or unpacking it
      with the `extract` step handler (defined in the consumption section below).
- [x] The resolved package is accessible to the run's jobs through the registry
      (the artifacts service, `cmd/artifacts`) under the snapshot's pinned
      display name, and is retrievable through the API like any other artifact.
      (Superseded mechanism: the original "fetch into the run's namespace" copy
      was eliminated by the storage redesign — the snapshot pin makes it moot.)
- [x] **`download_artifact`** — copies the referenced (or literally-named)
      artifact from the registry (or the job's own namespace) into the job's
      staged working area (or an explicit `dest`), crash-safely (dot-prefixed
      temp file + rename); records the final location as a `path` step output;
      an unknown name or a store error fails the step with a diagnostic.
- [x] **`extract`** — unpacks a tar, gzipped tar, or zip archive (detected from
      magic bytes, not the file name) into `dest` (default: the staged working
      area), honoring an optional `stripComponents`; refuses path-slip and
      symlink/hard-link members; a non-archive, corrupted, or truncated input
      fails the step.
- [x] **Staged working area** — lazily created per job instance and per target
      (fan-out workers stage in isolation) under the target's **worker root**
      (config `worker_root` / `CDROM_WORKER_ROOT`; default: the OS temp dir),
      exported to every step of the job as the `CDROM_STAGE_DIR` environment
      variable, best-effort removed once the job reaches a terminal state.
      The worker root is configurable so operators can steer staged files away
      from RAM-backed mounts: when the effective root (the configured value,
      or the OS temp dir) sits on a **tmpfs/ramfs mount** (detected on Linux
      from `/proc/mounts`, deepest enclosing mount wins), the target WARNS at
      startup that staged files consume memory and can starve the host.
- [x] **`publish_artifact`** — a step collects the files matched by its
      multiline glob patterns (supporting `**` recursion and `-`-prefixed
      exclusion patterns), compresses them into a zip that preserves the
      matched directory structure with sanitized entry names (Windows-forbidden
      characters and reserved device basenames remapped so the archive opens
      on every platform; colliding sanitized names are disambiguated with a
      deterministic counter suffix before the extension, never dropped), and
      uploads
      it to the job's own artifact namespace (job-bound by construction — the
      job token's namespace scope); the zip's location and store name are
      recorded as `path` / `artifact` step outputs; a pattern that matches
      nothing fails the step.
- [x] **Publishing** — a package version can be published through the API
      (`POST /api/packages`, permission-gated, audited) into the reserved
      `packages` registry namespace under the predictable
      `<package>-<version>.<ext>` name; duplicate publication of an existing
      version is rejected (immutable); the registry is browsable
      (`GET /api/packages[...]`) and readable.
- [x] **Promotion** (former F-19) — an artifact from run A can be promoted to
      run B / another environment; the promoted artifact is byte-identical
      (the copy is a SERVER-SIDE blob replication, so identity holds by
      construction and the source's measured checksum is inherited); promotion
      is authorized (F-14) and audited (F-15).
- [x] **E2E** — `scripts/e2e/16-artifact-packages.sh` demonstrates the happy
      path in all three formats, the negative cases, the per-run version
      snapshot (an old run keeps its old version after a newer registry entry
      appears), and the publish → promote → consume cycle.

## Artifacts (package references)

A pipeline can declare the packages it consumes in `spec.artifacts` — a list of
named artifact references. Each entry gives the artifact a `name` (how the
pipeline references it, e.g. in a step's params or env) and a `package` block
describing which package to fetch and how its version is resolved:

```yaml
spec:
  artifacts:
    - name: xyz # the name of the artifact to reference in the pipeline
      package:
        name: somecoolapi # the name of the package itself; if not set, use the name of the artifact
        tag: 6.6.6 # the version part of the package; not used if useLatest is true
        preReleaseRegex: "" # the regex to apply to the pre-release tag (after the - in the version); not used if allowPreRelease is false
        allowPreRelease: false # if true, and preReleaseRegex is not set or empty, use the latest pre-release by date
        useLatest: true # if true, use the latest package version by date
```

**Version resolution.** How the platform picks the package's version:

- **`useLatest: true`** — use the latest version of the package by date; `tag`
  is ignored.
- **`useLatest` false (or unset)** — `tag` names the exact version to use.
- **Pre-releases.** A version whose tag carries a `-` suffix (e.g.
  `6.6.6-rc.1`) is a pre-release and is not selected by default. Setting
  `allowPreRelease: true` opts in to pre-releases: if `preReleaseRegex` is also
  set, only pre-release tags matching that regex are eligible; if
  `preReleaseRegex` is empty, the latest pre-release by date is eligible.
  `preReleaseRegex` has no effect when `allowPreRelease` is false.

**Tie-in with the artifacts service.** The artifacts service (`cmd/artifacts`)
is a blob store; the metadata of every file it holds (namespace, display name,
size, content hash, package coordinates, counters) lives in the Database
service's storage_object records. When a run of a pipeline that declares
`spec.artifacts` is created, the platform resolves each reference to a concrete
package version (SQL over the registry records) and pins the winning filing's
display name in the run's snapshot, so the job can consume it. The resolved
version is recorded on the run (a per-run snapshot, like the rest of the spec,
F-01/F-11), so a run always uses the version that was resolved when it started
— re-resolving on a later run can pick up a newer version without changing what
a past run did. A step references the artifact by its `name` (in its params or
env); the platform makes the resolved package available to the job through the
`download_artifact` and `extract` step handlers and the job's staged working
area (defined in the section below).

## Consumption: the `download_artifact` and `extract` step handlers

Resolving a package is half the story; the job still has to pull the bytes
onto the target and lay them out somewhere sane. That is the job of **three
built-in step handlers**, registered like any other typed step (F-01) and
running natively on the target (worker or agent, Windows and Linux, standard
library only):

| Step type | What it does |
|-----------|--------------|
| `download_artifact` | Copies a named artifact from the registry (or the job's own namespace) onto the target, into the job's staged working area (below). |
| `extract` | Unpacks an archived package — **tar, gzipped tar, or zip** — into a destination directory (default: the staged working area). |
| `publish_artifact` | Collects the files matched by multiline glob patterns (with `-`-negated exclusions), packs them into a zip preserving the matched directory structure, and uploads it to the **job's own** artifact namespace. |

They compose: `download_artifact` brings the package onto the target,
`extract` lays out its contents, and ordinary `shell` steps then run against
the result. A job that only needs the bytes on disk (to feed its own installer,
for instance) uses `download_artifact` alone. The reverse direction — turning
a job's products into a consumable package — is `publish_artifact`: the job
ships its build output into its own namespace, and the platform (promotion,
below) moves it onward.

Like every handler, both read their settings from the step's `params` map; every
string param is **templatable** against the usual interpolation contexts (run
parameters, secrets, prior steps' outputs — F-10/F-06), so an early step can
drive a later one.

### `download_artifact`

| Param | Shape | Meaning |
|-------|-------|---------|
| `artifact` | string (required) | Which file to fetch. Probes THREE locations in preference order (existence-checked, first hit wins): **(1)** if it matches a `spec.artifacts` entry of this run, that entry's PINNED registry filing (looked up via the per-run snapshot — so a re-kicked run always gets the version it originally resolved); **(2)** the literal name in the job's OWN (job-id) namespace (its own `publish_artifact` output, or a standalone job's files); **(3)** the literal name in the `packages` REGISTRY namespace (public packages — the everyday "grab the published build" path for standalone jobs). None existent → `no such artifact <ref> (probed: …)`. |
| `dest` | string | Where to put it. A relative path resolves against the job's staged working area; an absolute path is honored (the same latitude a `shell` step enjoys). Parent directories are created. Default: the staged area root, under the artifact's stored file name. |

On completion the handler records a **`path` step output** holding the absolute
location the file ended up at — the same mechanism `token_exchange` uses for its
`token` output (F-01) — so later steps' conditions and templates can address it.

### `extract`

| Param | Shape | Meaning |
|-------|-------|---------|
| `archive` | string (required) | Path to the archive file: relative → resolved against the staged working area; absolute → honored. Normally the value a preceding `download_artifact` step recorded in its `path` output. |
| `dest` | string | The directory to unpack into; created if missing. Default: the staged working area root. |
| `stripComponents` | integer | Leading path components to strip from each member name (GNU tar `--strip-components` semantics; naïve segment stripping for zip members). Default 0. Handles the ubiquitous `dist/pkg-version/` wrapper directory. |

Records a **`dest` step output** holding the absolute extraction directory.

### Format detection

`extract` does not trust the file name: it sniffs **magic bytes** — `\x1f\x8b`
means gzip (decompress, then untar); `PK\x03\x04` means zip; anything else is
treated as plain tar. A file that is none of these (corrupt, truncated, or
simply not an archive) fails the step with a diagnostic naming what was found.
Order matters because a gzipped tar begins with the gzip header.

### Security controls (portable defenses)

Archives are data someone else wrote, so `extract` treats member names hostilely:

- **Escaping paths** — member names are normalized; absolute names, drive
  letters, and `..` sequences that would land outside `dest` are refused and the
  step fails (`refusing member <name>`).
- **Symlinks / hard links** — link-typed members are refused outright. This is
  the portable stance and closes the classic “symlink escapes `dest`” hole;
  consumers that genuinely need link trees materialize them with a `shell` step.
- **Overwriting** — extraction into a populated `dest` overwrites conflicting
  files (last writer wins); documented, not an error.
- **Size blowups** — no special compression-bomb accounting in the first cut; a
  malicious archive mostly burns the step's timeout (F-03).

### The job's staged working area

The default home for both handlers:

- **Created lazily** on the first step that needs it (ordinary jobs touch no
  extra disk at all). Unique per job instance **and per target** (under the OS
  temp dir, `MkdirTemp`-style) — fan-out workers each stage their own copy; there
  is no cross-worker sharing.
- **Exported to every step of the job** as the `CDROM_STAGE_DIR` environment
  variable (identical in mechanism to how the executor already exports
  `CDROM_STEP_OUTPUT_DIR` per step). Shell commands address it natively
  (`$CDROM_STAGE_DIR/dist` in POSIX shells, `%CDROM_STAGE_DIR%\dist` in cmd.exe,
  `$env:CDROM_STAGE_DIR` in PowerShell).
- **Cleaned up** best-effort once the job reaches a terminal state (succeeded,
  failed, timed_out, cancelled); a failed removal is logged, not surfaced.
- **Orthogonal to `workdir`** — a step's declared `workdir` still governs where
  its command runs; the stage area merely provides the default payload location.
  The typical chain: `download_artifact` → `extract` (into the stage area) →
  `shell` steps running from `$CDROM_STAGE_DIR/...`.

### `publish_artifact`

The producer counterpart: turns whatever the job built into a package the rest
of the platform can consume. Because a job's token is scoped to its own
(job-id) namespace, the step uploads into **that** namespace — the package is
bound to the job that produced it by construction, no bookkeeping required.
Getting it anywhere else (another run, the `packages` registry) is promotion's
job (§ Promotion).

| Param | Shape | Meaning |
|-------|-------|---------|
| `patterns` | multiline string (required) | One glob pattern per line, processed **in order**. A line whose first character is `-` is a **negative** pattern: it excludes everything matching it from the accumulation so far (and suppresses later positive matches of the same paths). Blank lines and lines starting with `#` are ignored. Patterns are relative to `root` (below); a leading `/` roots them at `root`. |
| `root` | string | Directory scanned for matches. Relative → resolved against the job's staged working area; absolute → honored. Default: the stage area. |
| `fileName` | string | Base name of the zip to produce/upload. Templatable (F-10) — typically embeds a version: `"${packageName}-${version}.zip"`. Default: `publish.zip`. |

Semantics:

- **Matching** uses [`yargevad/filepathx`](https://github.com/yardevad/filepathx)'s
  `Glob` (MIT licensed, ~100 LOC, no transitive dependencies — vendored into
  `internal/stephandlers` with the license header preserved, patched per
  § Glob portability below): `**` spans **zero or more directory levels**
  (gitignore/zsh style), and any pattern without `**` delegates to the
  standard-library `filepath.Glob`. Matching walks the real filesystem
  (directories are traversed), so `**` costs nothing extra versus a naive walk.
- **Structure preservation.** Matched files are packed into the zip with their
  path **relative to `root`** — the directory hierarchy the globs describe is
  the hierarchy inside the archive. Separators are normalized to `/` (the
  canonical ZIP convention, so a Windows-made package extracts identically on
  Linux). Symlinks are excluded (matching the `extract` refusal stance);
  directories contribute nothing on their own.
- **Entry-name sanitization (Windows-compatibility).** Characters Windows
  forbids in file names — `*`, `?`, `"`, `<`, `>`, `|`, `:`, and the ASCII
  control characters (U+0000–U+001F) — are replaced with `_` **within each path
  segment** (segment separators are never altered). Why: `publish_artifact`
  can legitimately match files bearing such characters (that is exactly what
  the vendored globber's metacharacter shielding guards), and the zip format
  stores them without complaint — but no Windows machine can open, extract, or
  rename them, so an unsanitized package is poison to its likely consumers.
  Sanitizing makes every `publish_artifact`-produced zip openable everywhere,
  including by `extract` on Windows. A basename that is a reserved device name
  (`NUL`, `CON`, `COM1`–`COM9`, `LPT1`–`LPT9`, case-insensitive) gets a
  leading `_`. Transformations are counted and reported (the log line carries
  `sanitized=<n>` when nonzero).
- **Disambiguation on sanitize collision.** Two distinct source paths that
  sanitize to the same entry name (e.g. `a*b.txt` and `a_b.txt`) are never
  dropped and never fail the step — the losers get a **counter suffix on the
  file name, before the extension**: the first occupant keeps `a_b.txt`, the
  second becomes `a_b1.txt`, the third `a_b2.txt`, and so on. Allocation is
  deterministic and collision-aware:
  - Among contenders for the same sanitized name, the one whose **original
    leaf name equals the sanitized form** (it needed no character rewriting)
    occupies the bare name; if none qualifies, occupants are assigned in
    ascending sort order of the original source paths.
  - The counter is **per distinct sanitized entry name** — it does not climb
    across unrelated files (`x*y.dat` + `x_y.dat` yield `x_y.dat` and
    `x_y1.dat`, independent of the `a_b` family).
  - Allocated names are checked against the **full set of finalized entry
    names**, so a counter can never squat on a file that legitimately exists
    (a source tree containing `a*b.txt`, `a_b.txt`, *and* `a_b1.txt` yields
    `a_b.txt`, `a_b1.txt` (occupied — skipped), `a_b2.txt`).
  - Packing remains loss-free: every matched file lands in the archive under a
    unique name (contrast with `extract`, whose overwrite stance is
    documented and accepted — packing is the stricter moment). Counter
    assignments are counted and reported (the log line carries `renamed=<k>`
    when nonzero).
- **Zip determinism-ish.** Entries are sorted by path; timestamps are the
  files' mtimes (nothing exotic — reproducibility is not a promise, byte
  identity is enforced by the checksum, not by the encoder).
- **Empty-set failure.** If the positive patterns match nothing, or the
  negatives exclude everything, the step fails: `no files matched the given
  patterns` — a typo in a glob must not quietly publish an empty package.
- On success the handler records a **`path` step output** (the zip's absolute
  location on the target — the LOCAL copy is KEPT until the job's stage area
  is cleaned up at terminus, so a later step of the same job can consume it
  without a second download) and an **`artifact` step output** (the store
  name the zip was uploaded under), so later steps and the condition context
  can address it.

#### Glob portability (separator handling + patches to the vendored `filepathx`)

Authoring convention: `/` is the canonical separator — the same multilined
blob works on Linux and Windows. But Windows authors habitually reach for `\`,
so on Windows **both** separators are accepted as path separators; the
vendored copy adapts:

- **Separator normalization (ours).** Before matching, each pattern's
  separators are collapsed to the OS-native one: on Windows both `/` and `\`
  are treated as path separators (translated to `\`); on non-Windows `/` is
  the separator and `\` is left as a literal character (it is not a path
  separator there, and leaving it literal preserves the vendored globber's
  metacharacter-shielding guarantees for unusual file names). Mixed blobs
  (`dist\/build/**`) therefore work on Windows and degrade predictably
  elsewhere. The zip's interior paths are always `/`-joined (canonical ZIP
  convention), so a Windows-produced archive extracts identically on Linux.
- **Leading `**/` fragments (upstream PR [#6](https://github.com/yargevad/filepathx/pull/6)).**
  Splitting a pattern on `**` leaves an empty leading fragment for patterns
  like `**/*.txt`; master treats it as "match nothing," silently dropping the
  whole pattern. Patched to treat an empty fragment as `.` so leading-`**`
  patterns behave intuitively.
- **Segment joining (upstream PR [#7](https://github.com/yargevad/filepathx/pull/7)).**
  Accumulation combines the previous match with the next fragment via
  `filepath.Join` instead of raw string concatenation, giving correct
  separator placement (critical on Windows, where concatenated `a/b` + `c*d`
  mixes separators).
- **Metacharacter shielding (upstream PR [#4](https://github.com/yargevad/filepathx/pull/4)).**
  Real path names may contain glob metacharacters (`release*.zip`,
  `weird[1].dat`). When a matched path is fed forward as the *prefix* of the
  next fragment's glob, its `*`, `[`, `]` characters are neutralized (mapped
  to `?`, which matches any single character — including the literal one) so
  the literal name cannot be reinterpreted as a wildcard mid-expansion. Our
  adaptation differs from the PR in one respect: the PR mutates the recorded
  result path (making returned matches un-openable); ours shields **only the
  accumulation chain** and returns pristine paths.

These patches are carried in the vendored copy (with the upstream diffs cited
inline). Coverage: unit tests in `internal/stephandlers` (including
`//go:build windows` variants for the dual-separator handling, the
`filepath.Join` combination, and the metacharacter-shielding behaviors,
mirroring the repo's existing `*_windows_test.go` practice) plus the e2e's
glob assertions, which pin the canonical authoring form (patterns written
with `/`).

Example (multiline param, as submitted through the jobs API):

```json
{"type": "publish_artifact", "params": {
  "patterns": {"string": "dist/**\n-test_\n-dist/tmp/\n# keep only release payloads"},
  "fileName": {"string": "mypkg-{{ .params.version }}.zip"}
}}
```

### Examples

Raw spec, as submitted through the jobs API:

```json
{
  "name": "consume-coolapi",
  "target_group": "default",
  "spec": {
    "steps": [
      {"type": "download_artifact", "params": {"artifact": {"string": "xyz"}}},
      {"type": "extract", "params": {"archive": {"string": "somecoolapi-6.6.6.tar.gz"}, "dest": {"string": "dist"}}},
      {"params": {"command": {"string": "sh"}, "args": {"strings": ["-c", "test -f $CDROM_STAGE_DIR/dist/smoke/test.py && echo packaged-ok"]}}}
    ]
  }
}
```

The same thing in pipeline-file form, tying `spec.artifacts` to the handlers:

```yaml
spec:
  artifacts:
    - name: xyz
      package: {name: somecoolapi, tag: "6.6.6"}
  jobs:
    - name: prod
      steps:
        - name: fetch
          type: download_artifact
          params: {artifact: xyz}
        - name: unpack
          type: extract
          params: {archive: somecoolapi-6.6.6.tar.gz, dest: dist}
        - name: verify
          shell: test -f $CDROM_STAGE_DIR/dist/smoke/test.py && echo packaged-ok
```

Note the bridge between the two worlds: `artifact: xyz` resolves through the
run's snapshot to the actual stored file name, and the platform stores fetched
packages under a **predictable name** — `<package>-<version>.<ext>` (the
publisher's extension preserved) — so `extract.archive` can quote it statically
while the snapshot still records the authoritative mapping.

### Observability

Both handlers stream their output through the usual channels (F-02) and emit
stable, machine-greppable info lines (anchored like the rest of the system's
logs):

- `download_artifact: artifact=<ref> file=<stored> dest=<abs> size=<bytes>`
- `extract: archive=<abs> format=<tar|targz|zip> dest=<abs> members=<n>[ stripped=<k>]`
- `publish_artifact: root=<abs> matched=<n> excluded=<m> zip=<abs> size=<bytes> uploaded=<name>` (plus `sanitized=<k>` when entry names were transformed, and `renamed=<k>` when collision counters were assigned)

Failures follow the same prefixes with the reason (missing file, unsupported
format, refused member `<name>`).

### Failure modes

| Situation | Outcome |
|-----------|---------|
| `artifact` unknown neither as a reference nor as a store file | Step fails: `no such artifact <name> in run namespace` |
| Store/RPC error mid-download | Step fails; the dot-prefixed temp file is discarded (crash-safe: download to a hidden temp name, rename on success) |
| `archive` missing | Step fails: `no such file` |
| Non-archive / corrupt / truncated | Step fails: `unsupported or corrupt archive (<what was found>)` |
| Escape or link member | Step fails: `refusing member <name>` |
| Positive patterns match nothing (or negatives exclude everything) | `publish_artifact` fails: `no files matched the given patterns` |
| Invalid pattern (malformed bracket expression, etc.) | `publish_artifact` fails with the underlying glob error |
| Zip assembly or upload error | `publish_artifact` fails; the interim zip is removed (no partial archive lingers, nothing uploaded) |
| Context cancelled / timed out | The copy/extraction/zip/upload loops observe the context and bail promptly; reported cancelled / timed_out per F-05/F-03 |

## Publishing packages (the former producer gap — now in scope)

Verified against the current code: **there is no HTTP write path to the
store.** The only artifact route is `GET /api/jobs/{id}/artifacts` (a list),
and although the gRPC `UploadArtifact` proxy exists, `checkArtifactToken`
confines a job-token caller to its own (numeric job-id) namespace — a job
cannot lawfully deposit bytes anywhere else. The **job-side** publisher needs
no new authorization at all — the existing `UploadArtifact` proxy plus
`checkArtifactToken` already lets a job write into its own namespace; what is
missing is the expressing step handler (`publish_artifact`, above). The
**registry-side** surface is genuinely new, and it lands with this
sub-feature:

- **Reserved registry namespace.** Packages live in a fixed store namespace
  (`packages`), filed as `<package>-<version>.<ext>`; a version's date is the
  store's creation timestamp. Registry files are **immutable**: a publish that
  collides with an existing name is rejected (409), never overwritten.
- **Publish endpoint.** `POST /api/packages` uploads a package version:
  streamed through the API into the registry namespace (the API relays,
  consistent with the topology rule). The request identifies the package name and version
  (validated against the `<name>-<ver>.<ext>` filing convention); the API
  computes a content checksum (SHA-256) on ingest and records it on the stored
  artifact (a new optional `Artifact.content_sha256` field, tolerated by older
  readers).
- **Registry browsing.** `GET /api/packages` lists packages (distinct names
  with their versions, parsed from the registry namespace's listing); `GET
  /api/packages/{name}/{version}` returns the descriptor (file name, size,
  checksum, created-at); `GET /api/packages/{name}/{version}/contents`
  streams the bytes back. Reads are permission-gated (`packages.view`);
  writes require `packages.publish` (both denied by default per F-14).
- **Auditing.** Publish actions are recorded via `internal/audit` (F-15) with
  the actor, package, version, and checksum.
- **Resolution reads the registry.** Version-resolution candidates come from
  listing the registry namespace and parsing the file names into (tag, date)
  pairs; the resolution rules above apply.

### Promotion (former F-19)

Moving a package between places is the flip side of consuming it. The
operation is a **checksummed, streamed copy** between two store namespaces —
namespaces remain opaque to the store, so promotion is purely an orchestration
concept layered on it:

- **Operation.** A copy (source namespace + file → destination namespace +
  file) in the artifacts service: stream the copy without buffering the whole
  file, then compute the destination's checksum and compare it against the
  source's recorded `content_sha256`; a mismatch aborts and deletes the
  partial destination file.
- **Surface.** `POST /api/artifacts/promote` — the body names the source
  (namespace + file) and the target (destination namespace + optional file
  name; default: the same file name). Typical uses: a run's newly built
  package → the `packages` registry, and a registry package → another run's
  namespace so that run's jobs can consume it (the “deploy the same artifact
  to prod” case). Environment framing (F-17) is expressed by choosing the
  target namespace; the API does not interpret environments itself.
- **Guards.** Byte-identity is guaranteed by the checksum comparison above;
  promotion is permission-gated (`packages.promote`, denied by default) and
  audited (F-15) with both namespaces, the file name, and the verified
  checksum.

Two producers feed the loop. **Jobs** publish through the `publish_artifact`
step handler into their own (job-id) namespace — permitted by the job-token
scope, tied to the producing job by construction, and the everyday path for
“ship what I just built.” **Humans and CI systems** publish directly into the
`packages` registry through `POST /api/packages` — the path for curated,
versioned releases. Something moves bytes between namespaces (promote), and
the run's jobs pull them out (`download_artifact` / `extract`).

## End-to-end test plan

`scripts/e2e/16-artifact-packages.sh` (next free number after 15; wired into
`make e2e` via the `scripts/e2e.sh` header comment, standalone-runnable like its
siblings):

1. **Seed the registry.** Build fixture packages in-band (tiny trees with marker
   files and a nested subdirectory) in three forms — targz, zip, plain tar —
   plus poisoned twins (a slipping member `../../../evil.txt`, a symlink member,
   a truncated tarball). Seed primarily through the **real publish endpoint**
   (`POST /api/packages` — exercising the new surface end-to-end, including the
   immutability 409 on a re-publication of the same version); a direct store
   write is acceptable only where the endpoint would obscure the assertion
   (planting a pre-existing version before importing a pipeline). Tags planted:
   `1.0.0`, `1.0.1`, `2.0.0-rc.1`.
2. **Happy path.** Submit the raw-spec job from the example above (targz
   flavor); wait for success; grep the streamed logs for the stable handler
   lines and `packaged-ok`; verify the step outputs (`path`, `dest`) appear in
   the persisted job view.
3. **Matrix.** Repeat for the zip and plain-tar flavors (proves format
   detection).
4. **Negatives.** (a) `artifact: nosuch` → job fails with the diagnostic in the
   log; (b) `extract` on the truncated fixture → fails `unsupported or corrupt`;
   (c) the slipping fixture → fails `refusing member`, and `evil.txt` is
   provably absent from the stack's scratch dirs; (d) the symlink fixture →
   refused.
5. **Per-run snapshot (pipeline-file path).** Import a pipeline declaring
   `spec.artifacts` (reference `xyz` → package `somecoolapi`, pinned tag
   `1.0.0`); create a run and assert the run row records `1.0.0` and the job
   received the `1.0.0` payload. Then plant `1.0.1` in the registry and re-run:
   the second run resolves `1.0.1` while the first kept `1.0.0` (snapshot proof).
   A `useLatest: true` pipeline picks the newest release tag, ignoring
   `2.0.0-rc.1` unless `allowPreRelease` is set.
6. **Stage cleanup.** Poll the OS temp dir: the job's stage dir is gone after
   the job terminated.
7. **Promotion (former F-19).** Promote a fixture package from one namespace
   into another via `POST /api/artifacts/promote`; assert the destination file
   exists, its recorded checksum equals the source's `content_sha256`
   (byte-identity), and the audit log shows the promotion with both
   namespaces. Negative: promoting a nonexistent source fails cleanly.
8. **`publish_artifact` (job-bound production).** A job that (a) builds a
   small tree under the stage area via `shell` (nested dirs, a `test_` file,
   junk under `tmp/`, a file whose name contains a glob metacharacter —
   e.g. `star*.cfg` — to exercise PR #4's shielding, a file whose name
   bears Windows-forbidden characters — e.g. `bad:name?.cfg` — to exercise
   entry-name sanitization, and a collision pair — `du*p.txt` beside
   `du_p.txt` — to exercise counter disambiguation), (b) runs
   `publish_artifact` with a multiline pattern that leads with `**/` (exercising
   PR #6's empty-fragment fix) plus a `-` negation excluding the junk,
   (c) `extract`s the published zip into a sibling directory, and (d)
   verifies the rebuilt tree against the original minus the exclusions —
   asserting the metacharacter file was MATCHED (PR #4 shielding) and arrived
   underscore-sanitized (`star*.cfg` → `star_.cfg`), the
   Windows-forbidden-name file arrived sanitized (`bad:name?.cfg` →
   `bad_name_.cfg`), and the collision pair arrived as `du_p.txt` +
   `du_p1.txt` (counter disambiguation) — proving glob semantics,
   sanitization, structure preservation, and the job-namespace tie in one
   shot.
   Assert the zip is listed by `GET /api/jobs/{id}/artifacts` and the
   `path`/`artifact` step outputs are present. Negatives: a pattern matching
   nothing fails the job with `no files matched`; a malformed pattern fails
   with the glob error. (Canonical-form separation is asserted implicitly:
   the same `/`-authored pattern blob must succeed on the Windows worker
   build, where `\`-authored equivalents are additionally covered by the
   `//go:build windows` unit tests.)

## Design decisions (folded into AGENTS.md / Architecture.md)

- **`spec.artifacts` is a list of named package references.** Each entry has a
  `name` (how the pipeline references it) and a `package` block (`name`, `tag`,
  `preReleaseRegex`, `allowPreRelease`, `useLatest`). The platform resolves each
  to a concrete version (latest by upload time, a pinned `tag`, or the latest
  pre-release per `allowPreRelease` / `preReleaseRegex`) and pins the winning
  registry filing's display name in the run's snapshot, exposing it to the job
  by the artifact's `name`.
- **The resolved version is a per-run snapshot.** Like the rest of the spec
  (F-01/F-11), the resolved `name` → pinned filing display-name map is recorded
  on the run, so a run always uses the version resolved when it started; a
  later run can pick up a newer version without changing what a past run did.
- **New fields / RPCs / endpoints (this sub-feature).** A `spec.artifacts` field
  in the file format (F-21.1) and its validation in `internal/pipelinefile`; a
  per-run snapshot of resolved artifact versions on the run model; the version
  resolution logic (SQL over the registry's storage_object records); and the
  snapshot step at run creation.
- **Consumption and job-production ride on typed steps (F-01).** Three
  built-in handlers — `download_artifact` (copy a named artifact from the
  registry — or the job's own namespace — onto the target), `extract` (untar /
  ungzip-tar / unzip,
  std-lib only, magic-byte detection, path-slip + symlink refusals), and
  `publish_artifact` (multiline glob collection — `**` recursion via vendored
  MIT-licensed `filepathx` (patched per the portability section), `-`-negated
  exclusions — zipped with structure preserved, entry names sanitized for
  Windows compatibility with collision-counter disambiguation, and uploaded
  into the job's own namespace) — registered like the other built-ins. String params are fully templatable (F-10); each handler
  emits a stable log line and a step output (`path` / `dest` / `artifact`) so
  later steps can address the result.
- **The job's staged working area is the default destination.** Lazy
  `MkdirTemp` per job instance and per target (fan-out-isolated), exported to
  every step as `CDROM_STAGE_DIR` (mirroring `CDROM_STEP_OUTPUT_DIR`),
  best-effort removed at job terminus.
- **Predictable stored names.** Fetched packages are filed as
  `<package>-<version>.<ext>`; the per-run snapshot records reference name →
  (package, version, stored file name), and `download_artifact.artifact`
  accepts either world (a reference name or a literal file name).
- **Producers: two doors, one loop.** Jobs publish through the
  `publish_artifact` step handler into their own (job-id) namespace — no new
  authz needed, the job-token scope already grants exactly that door; the
  package is tied to its producing job by construction. Humans/CI publish
  curated versions into the `packages` registry through `POST /api/packages`
  (permission-gated, audited). Colliding registry publishes → 409 (immutable
  versions); a SHA-256 checksum is computed on ingest and travels with the
  artifact.
- **Globbing is vendored, patched, and platform-normalized.** `publish_artifact`'s
  pattern matching vendors the MIT-licensed `yargevad/filepathx` `Glob`
  (~100 LOC, no transitive deps; license header retained) into
  `internal/stephandlers`, carrying three upstream fixes — PR #6 (empty
  `**/` fragment ≙ `.`), PR #7 (`filepath.Join` segment combination), PR #4
  (metacharacter shielding of forwarded literals, adapted to keep returned
  paths pristine) — plus our own separator handling: `/` is the canonical
  authoring form on every platform, but on Windows `\` is equally accepted as
  a path separator (collapsed to the native one before matching; on
  non-Windows `\` stays literal, preserving the shielding guarantees). Zip
  interiors stay canonically `/`. `**` = zero-or-more directory levels;
  non-`**` patterns delegate to the standard library. Multiline patterns
  accumulate in order; `-`-prefixed lines negate.
- **Promotion absorbed from F-19.** The checksummed streamed copy
  (`POST /api/artifacts/promote`) is part of this sub-feature; F-19 is retired
  as a standalone row (consolidation note below).
- **E2E.** `scripts/e2e/16-artifact-packages.sh` covers the format matrix, the
  negatives, the per-run snapshot, stage cleanup, the job-side
  `publish_artifact` (glob + negation semantics, structure round-trip via
  extract + diff), the registry publish (incl. the immutability 409), and
  promotion (byte-identity + audit).

## Consolidation note (retiring F-19)

F-19 (artifact promotion) is **merged into F-21.6** and retired: packaging
(consuming a released build) and promotion (moving a build where it is wanted)
are two halves of one capability, and splitting them left the promotion spec
without a producer to promote from. Accompanying changes:

- `docs/Features.md` — the F-19 row is annotated as absorbed into F-21.6
  (kept for traceability, not scheduled); the F-21.6 row describes the
  consolidated scope; the suggested-phase ordering drops F-19 from its
  trailing slot.
- `AGENTS.md` — the F-19 row annotates the absorption; the F-21 row reflects
  the wider F-21.6 scope.
- F-19's acceptance criteria (byte-identical promotion, authorized + audited)
  are carried into F-21.6's criteria and e2e plan above. F-19's scope was
  exactly the promote operation, so nothing is lost in the merger.
