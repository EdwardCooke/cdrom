# F-21.5 · Externally-sourced pipelines

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature makes a pipeline's definition able to **live in an external
source** — a **git** repository, an **HTTP/HTTPS** endpoint, or a file on the
**local filesystem** (rooted in a configured directory) — instead of (or
alongside) the UI. An **externally-
sourced** pipeline is pulled from its source periodically — on a steady-state
interval (system default of 2 minutes) or a cron schedule (for precise timing,
e.g. after-hours syncs when load is minimal) — with the cadence tunable in the
pipeline's OWN file (`spec.periodicRefresh`) subject to an ADMIN GATE (a
global config knob and a per-pipeline database flag) — refreshed again when a
run is kicked off, and can be refreshed manually. The raw YAML is stored in
the database alongside a content hash so the platform can tell when the file
changed, and it is retrievable through the API; when a run is kicked off, the
source's location and revision are snapshotted onto the run row.

**The source itself is not in the file.** WHERE a pipeline is pulled from is a
database concept (a `PipelineSource` row) configured through the API, so the
same file can be checked into git, served over HTTP, or mounted on the
filesystem. HOW OFTEN it is pulled may be tuned in the file
(`spec.periodicRefresh`) — a behavioral preference of the definition, bounded
by an admin gate. The actual fetching is done by the source-fetcher service
(F-21.2); the API orchestrates the sync.

**Scope.**
- `internal/models` — a `PipelineSource` (WHERE a pipeline is pulled from: a
  `kind` of `git` / `http` / `file` and a `reference` — the `<type>:<spec>`
  locator string, F-21.2 — and a credential reference; cadence is NOT on this
  row — it lives in the pipeline's file, see below), a
  `PipelineSourceState` (last sync time, last source version, last file hash,
  last error), the `periodicRefresh` policy (`periodic_refresh_interval` /
  `periodic_refresh_schedule`) and the override gate
  (`periodic_refresh_overrides_allowed`) plus `source_file` / `source_hash`
  on the `Pipeline` row, and `source_kind` / `source_reference` /
  `source_version` / `source_file_hash` on the `PipelineRun` row (kickoff
  provenance); registered in `models.All()`.
- `internal/pipelinefile` — parse/validate `spec.periodicRefresh` (camelCase;
  `interval` a duration, `schedule` a cron expression; both optional; when
  both are set the cron drives) and emit it onto the schema; export
  reproduces it.
- `internal/services/database` — source CRUD, the stored YAML + hash, and the
  compiled pipeline; `SyncPipelineSource` / `RefreshPipelineSource` RPCs.
- `internal/api` — the **refresh orchestrator**: it dials the fetcher (F-21.2)
  to pull a source, decrypts the source's credential (F-21.3) and hands the
  plaintext to the fetcher for that one fetch, compares the returned hash to the
  stored one, and re-imports on change (F-21.1). It owns the **manual refresh**
  endpoint, the **refresh-on-run** hook (in the run-creation path, which also
  snapshots the source's location and revision onto the run row), and a
  **leader-gated periodic refresh** loop (a named lease on the Database
  service, like the scheduler's loops, F-23).
- `internal/api/server.go` — **get source** (the stored YAML + hash + last
  sync) and the **source** CRUD endpoints.

**Acceptance criteria.**
- [x] A pipeline can be sourced from a **git** repository, an **HTTP/HTTPS
      endpoint**, or a file on the **local filesystem** (a `PipelineSource`
      `kind` of `git` / `http` / `file`), and each kind is fetched by the
      source-fetcher service (F-21.2) from the source's `reference`.
- [x] An externally-sourced pipeline is refreshed periodically at its
      EFFECTIVE cadence — the pipeline file's `spec.periodicRefresh` (its
      `schedule` cron when set, else its `interval`) when the admin gate
      allows it, otherwise the system default of 2 minutes — and again when a
      run of it is kicked off; the raw YAML and its content hash are stored in
      the database and retrievable via the API.
- [x] The pipeline's FILE may declare `spec.periodicRefresh` — an `interval`
      (a duration) and/or a `schedule` (a cron expression, e.g. after-hours
      syncs when load is minimal) — overriding the system default cadence;
      when both are set the cron drives; an `interval` of `0` (without a cron)
      opts the source out of periodic polling, honored only when overrides are
      allowed.
- [x] ADMINISTRATORS control whether file overrides are honored, at two
      levels: globally (the `pipeline_source.overrides_allowed` config knob,
      default on) and per pipeline (the
      `periodic_refresh_overrides_allowed` flag on the `Pipeline` row, default
      on, editable through the pipeline API); overrides are honored only when
      BOTH allow them, and a denial falls back to the system default cadence —
      restoring the safe default, never halting polling.
- [x] A change in the source (detected by a changed content hash) re-imports the
      pipeline (bumping its version, F-11); an unchanged file is a no-op (no
      version bump, no re-dispatch) — only `last_synced_at` is updated.
- [x] A pipeline can be refreshed manually via the API (an explicit re-pull that
      applies the latest file regardless of schedule).
- [x] The actual fetch (git / HTTP / file) is performed by the separate
      source-fetcher process (F-21.2), which the API dials over gRPC; with a TLS
      CA configured the connection uses mutual TLS, and without one it falls
      back to plaintext (local dev) — the same convention as the other services.
- [x] The source-fetcher holds no definitions, credentials, or encryption key at
      rest (its only on-disk state is the transient git repository cache): the
      API decrypts the source's credential (F-21.3) and passes the plaintext to
      the fetcher for a single fetch, which is never persisted or logged.
- [x] A sync is serialized per pipeline (a source is not synced concurrently by
      two triggers), so a periodic tick and a run-kickoff refresh racing cannot
      double-apply a change.
- [x] A **refresh-on-run** that fails (e.g. the source is unreachable) does
      **not** block the run: the run proceeds on the last successfully-synced
      definition, and the failure is recorded on the source state and surfaced
      to the UI.
- [x] When a run is kicked off, the source's location and revision are
      snapshotted onto the run row (`source_kind`, `source_reference`,
      `source_version`, `source_file_hash`), so a run answers “which file, at
      which revision?” even after the source is repointed or detached; when the
      kickoff fetch fails, the provenance reflects the last successful sync.
- [x] `GET /api/pipelines/{id}/source` returns the `PipelineSource` (kind,
      reference, credential name) plus the `PipelineSourceState` (last sync
      time, last version, file hash, last error), the stored `source_file`
      (the raw YAML), and the CADENCE VIEW (the file's declared
      `periodicRefresh`, whether overrides are allowed, and the effective
      cadence).
- [x] `GET /api/pipelines/{id}` returns the pipeline's **compiled** definition
      (the same shape the UI editor shows), so the UI and the file are two views
      of the same model.
- [x] **Import** — `POST /api/pipelines` (or `PUT /api/pipelines/{id}`) accepts
      a definition in the file format (YAML or its JSON equivalent); the API
      runs it through the compiler (F-21.1) and creates/updates the pipeline. A
      pipeline becomes externally-sourced when a `PipelineSource` is attached to
      it through the source API — the source is a database concept, not part of
      the file.
- [x] **Export** — `GET /api/pipelines/{id}/export` renders the pipeline's
      current compiled definition back into the file format. For an
      externally-sourced pipeline the export reproduces a file equivalent to the
      stored `source_file`; for a UI-authored pipeline it synthesizes a file from
      the compiled model. The round-trip property (export → import → same
      compiled definition) holds.

## The source model

- **`PipelineSource`** — WHERE a pipeline is pulled from. It has a `kind`
  (`git` / `http` / `file`) and a `reference` (the `<type>:<spec>` locator
  string, F-21.2, that names the file to fetch) and a `credential` (the name
  of the `SourceCredential` used to authenticate; empty means the source is
  public / needs no credential). HOW OFTEN it is pulled is not here — that is
  the pipeline's file (below), so the source row stays a pure location fact:
  - `git` — the reference is `<repo>@<branch>[<path>]` (the git remote, the
    branch ref, and the file path in the repo, with `\@` / `\[` / `\]` / `\\`
    escaping). The fetcher serves the repository from its on-disk cache and
    reads the file at the path.
  - `http` — the reference is the endpoint that serves the definition file
    (e.g. an object-store URL or a raw-file endpoint). The fetcher does a GET
    and uses the response body as the file. Request headers come from the
    source's `http` credential (F-21.3); a credential is optional.
  - `file` — the reference is a path resolved against the fetcher's configured
    local-filesystem root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`): the file is read
    directly from `<root><path>`; no network is involved. This is the kind for
    a definition that is mounted into the fetcher's pod (e.g. a ConfigMap or a
    volume) and is "pulled" by re-reading the file. When no root is configured
    the kind is disabled.
- **`spec.periodicRefresh` (the file's cadence policy).** The pipeline's FILE
  may declare, in its `spec`:

  ```yaml
  spec:
    periodicRefresh:
      interval: 2m             # steady-state cadence (a duration)
      schedule: "0 3 * * *"    # cron expression (precise timing, e.g. after-hours)
  ```

  Either field is optional; when BOTH are set the `schedule` cron drives and
  the `interval` is ignored. The compiler validates `interval` as a duration
  and `schedule` as a cron expression (F-09's cron grammar) and stores them on
  the `Pipeline` row (`periodic_refresh_interval` /
  `periodic_refresh_schedule`); they are captured in the version snapshot
  (F-11) for history, while the refresh loop acts on the CURRENT definition.
  A pipeline with no attached source simply ignores the field.
- **Admin gate on overrides.** WHETHER the file's `periodicRefresh` is
  honored is decided by administrators, at two levels: globally, the
  `pipeline_source.overrides_allowed` config knob (default on); per pipeline,
  the `periodic_refresh_overrides_allowed` flag on the `Pipeline` row (default
  on, editable through the pipeline API by whoever may edit the pipeline).
  Overrides are honored only when BOTH allow them. Rationale: an author's file
  must not be able to silence its own monitoring (`interval: 0`) or hammer a
  busy origin — a denial falls back to the SAFE system default; it never
  halts polling outright.
- **Effective cadence rule.** Resolved at sync time (briefly cached, like the
  concurrency-limit rules): overrides allowed and `schedule` non-empty → the
  cron drives; overrides allowed and `interval` set → the source is due when
  `now >= last_attempt + interval` (an explicit `0` opts out of periodic
  polling — still refreshable on run kickoff or manually); otherwise (unset,
  or overrides denied) → the system default
  (`pipeline_source.refresh_interval` /
  `CDROM_PIPELINE_SOURCE_REFRESH_INTERVAL`, default `120s`). The loop
  due-tests each source against its next-due instant.
- **`PipelineSourceState`** — the last sync's bookkeeping: `last_synced_at`,
  `last_version` (the source's version identifier — the git commit hash, an
  HTTP `ETag`/`Last-Modified`, or the file's mtime — so a no-change can be
  detected cheaply), `file_hash` (the content hash of the file at that version),
  and `last_error` (set when a sync fails, cleared on the next success).

## The stored YAML and its hash

When an externally-sourced pipeline is synced, the API asks the source-fetcher
(F-21.2) to fetch the definition file named by the source's `reference` and
stores, on the `Pipeline` row:

- **`source_file`** — the raw YAML text, verbatim (so it is retrievable through
  the API and is the exact input the compiler ran).
- **`source_hash`** — the SHA-256 of `source_file` (hex). This is the change
  detector: two syncs that produce the same hash have not changed the
  definition.

The hash is what makes refresh cheap and idempotent. On a sync the API computes
the hash of the freshly-fetched file (the fetcher returns it) and compares it to
the stored `source_hash`:

- **Changed** (hash differs) — the file is re-compiled (F-21.1) and the
  pipeline is re-imported (create or update), which bumps the pipeline's version
  (F-11) and stores the new `source_file` / `source_hash` and the source state's
  `last_version`. A run started after the change uses the new definition.
- **Unchanged** (hash matches) — the sync is a no-op: no recompile, no version
  bump, no re-dispatch. Only `last_synced_at` is updated.

This means a periodic refresh that finds no change is free, and a run-kickoff
refresh that finds no change does not perturb an in-flight pipeline.

## Refresh triggers

An externally-sourced pipeline is refreshed in three ways:

1. **Periodically** — the API's **source-refresh loop** (leader-gated via a
   named lease on the Database service, like the scheduler's loops, F-23)
   resolves each source's EFFECTIVE cadence (the file's `spec.periodicRefresh`
   when the admin gate allows it, else the system default of 2 minutes) and
   maintains a next-due instant per source — the next cron fire when a
   `schedule` drives, otherwise `last_attempt + interval` — syncing whatever
   is due. A source opted out (a HONORED `interval` of `0`, no cron) is not
   polled.
2. **When a run is kicked off** — just before a run of an externally-sourced
   pipeline is created (manual, cron, webhook, or event trigger), the API
   performs a **refresh-on-run**: it fetches the source (via the fetcher) and,
   if the file changed, compiles it so the run executes the latest reviewed
   definition. This guarantees "what I just kicked off is what is in the source
   right now" without waiting for the next scheduled tick. A refresh-on-run that
   fails (e.g. the source is unreachable) does **not** block the run: the run
   proceeds on the last successfully-synced definition, and the failure is
   recorded on the source state and surfaced to the UI.
3. **Manually** — `POST /api/pipelines/{id}/source/refresh` forces an
   immediate sync (regardless of schedule) and applies the result. This is the
   "I just pushed, pull it now" path.

All three go through the same sync routine (fetch via the source-fetcher →
hash → compare → recompile if changed), so they are behaviorally identical; only
the trigger differs. A sync is serialized per pipeline (a source is not synced
concurrently by two triggers), so a periodic tick and a run-kickoff refresh
racing cannot double-apply a change.

## Retrieval through the API

The stored source is readable through the API:

- `GET /api/pipelines/{id}/source` — the `PipelineSource` (kind, reference,
  credential name) plus the `PipelineSourceState` (last sync time, last
  version, file hash, last error), the stored `source_file` (the raw YAML),
  and the CADENCE VIEW: the file's declared `periodicRefresh`, whether
  overrides are allowed (global ∧ pipeline), and the resulting effective
  cadence — so a user sees WHY a source polls at the rate it does. This is how
  a user sees "what definition is currently loaded and where it came from"
  without checking out the source.
- `GET /api/pipelines/{id}` — the pipeline's **compiled** definition (the same
  shape the UI editor shows), so the UI and the file are two views of the same
  model.
- The run row likewise carries the kickoff provenance (`source_kind` /
  `source_reference` / `source_version` / `source_file_hash`), stamped at run
  creation (surfaced on `GET /api/runs/{id}`), answering “which file, at which
  revision, produced this run?” even after the source is repointed or detached.

## Import and export

- **Import** — `POST /api/pipelines` (or `PUT /api/pipelines/{id}`) accepts a
  definition in the file format (YAML or its JSON equivalent). The API runs it
  through the compiler (F-21.1) and creates/updates the pipeline. A pipeline
  becomes externally-sourced when a `PipelineSource` is attached to it through
  the source API — the source is a database concept, not part of the file.
- **Export** — `GET /api/pipelines/{id}/export` renders the pipeline's current
  compiled definition back into the file format. For an externally-sourced
  pipeline the export reproduces a file equivalent to the stored `source_file`;
  for a UI-authored pipeline it synthesizes a file from the compiled model. The
  round-trip property (export → import → same compiled definition) holds because
  the compiler is a pure function of the file and the exporter is its inverse on
  the fields the file can express.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The raw YAML + hash are stored in the database.** An externally-sourced
  pipeline stores `source_file` (the verbatim YAML) and `source_hash` (its
  SHA-256) on the `Pipeline` row, plus a `PipelineSource` (where it came from:
  a `kind` of `git` / `http` / `file` and its `reference`) and a
  `PipelineSourceState` (last sync / version / error). The hash is the change
  detector: a sync that yields the same hash is a no-op (no recompile, no
  version bump); a changed hash re-imports and bumps the version (F-11). The
  stored file is retrievable through the API
  (`GET /api/pipelines/{id}/source`). The cadence policy (`periodicRefresh`)
  and its admin gate live on the SAME `Pipeline` row (file-derived + DB-flag),
  keeping the source row a pure location fact.
- **Refresh is one routine, three triggers.** A single sync routine (fetch via
  the source-fetcher → hash → compare → recompile if changed) is driven by (1)
  the API's leader-gated source-refresh loop (a named lease on the Database
  service, like the scheduler's loops, F-23) at each source's next-due instant
  (resolving the effective cadence — the file's `spec.periodicRefresh` when
  the admin gate allows it, else the system default of 2 minutes), (2) a
  refresh-on-run hook just before a run of an externally-sourced pipeline is
  created — which also snapshots the source's location and revision onto the
  run row (kickoff provenance) — and (3) a manual
  `POST /api/pipelines/{id}/source/refresh`. A sync is serialized per pipeline
  so the triggers cannot race. A refresh-on-run that fails does not block the
  run (it proceeds on the last good definition and records the error); a
  periodic or manual failure is recorded on the source state.
- **New fields / RPCs / endpoints (this sub-feature).** `PipelineSource` and
  `PipelineSourceState` models (registered in `models.All()`); `source_file` /
  `source_hash` / `source` on `Pipeline` (db); the `periodicRefresh` policy
  (`periodic_refresh_interval` / `periodic_refresh_schedule`, compiled from
  the file) and the override gate
  (`periodic_refresh_overrides_allowed`, a DB flag) on `Pipeline` (db) —
  retiring the early-slice `schedule` column on `PipelineSource` (unread);
  `source_kind` / `source_reference` / `source_version` /
  `source_file_hash` on `PipelineRun` (db); `spec.periodicRefresh` support in
  `internal/pipelinefile` (parse/validate/export);
  `GET/POST /api/pipelines[/{id}]/source[/{action}]` (api); a `source-refresh`
  background loop (a named lease on the Database service), a refresh-on-run
  hook + kickoff provenance stamp (api), and the config knobs
  `pipeline_source.refresh_interval` (system default cadence) and
  `pipeline_source.overrides_allowed` (global gate) (api).
