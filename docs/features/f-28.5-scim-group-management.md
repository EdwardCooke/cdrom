# F-28.5 · SCIM group management

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** The `/Groups` resource endpoints plus the machinery that turns
corporate group membership into Cdrom authorisation: `POST/GET
/scim/v2/Groups`, `GET/PUT/PATCH/DELETE /scim/v2/Groups/{id}`, a lightweight
group store, and the **group→role mapping applicator** that computes each
SCIM-managed user's derived role set from the configured
`idp.scim.group_role_mappings` (F-28.1). Stretches optionally to F-27
approval-group targeting. Also delivers a **read-only admin API surface**
(`GET /api/groups[…]`) that bridges the group store for the eventual UI —
landed now, before the UI exists, so the UI build consumes a settled
contract rather than retrofitting one (ruled 2026-11-06).

**Why.** Enterprises express entitlements as group membership (“admins”,
“deployers”, “approvers”). Supporting `/Groups` lets the corporate IdP sync
those memberships natively, and the mapping layer translates them into F-14
roles so authorisation tracks the directory with nobody touching Cdrom. This
pairs with F-14's JWT claim mapping: the corporate IdP both provisions (SCIM)
and authenticates (OIDC group claims), and the two stay consistent.

**Rulings (2026-11-06 — supersede the original draft where they differ).**
1. **Authorisation-cache invalidation is mandatory.** A non-empty role diff
   produced by the applicator MUST be followed by a `role_change` event on
   the shared event log (F-23) — the applicator calls the Database service's
   `PublishRoleChange` — so every API replica drops its authz cache and the
   change bites within ~50 ms without a restart (F-14). Zero-diff replays
   publish nothing (anti-noise, cf. F-28.4's lean-contact auditing).
2. **Operators keep unfettered role grants on SCIM-managed users** —
   primarily for temporary adjustments. Group recomputation is therefore
   **provenance-scoped**: it reconciles ONLY the bindings it wrote itself
   (marked `origin=scim_group` on `RoleBinding`); manual/operator grants are
   never examined, added, or removed. See *Merge policy*.
3. **Member values are opaque and taken verbatim.** Whatever the corporate
   provider puts in `members[].value` is assumed to be the same identifier it
   sends as the user's `externalId`, but that is not guaranteed. Resolution
   is best-effort (see *Member-value resolution*); values that resolve to no
   live user are **ignored, never rejected** — stored as-is, logged with the
   offending value for troubleshooting.
4. **Verbatim storage; `displayName` is NOT unique; missing roles are logged,
   not created.** Attributes are stored exactly as received (no
   normalisation). Multiple groups may legally share a `displayName`
   (departments routinely do) — the draft's 409-on-duplicate is withdrawn.
   A mapping entry whose target role does not exist in the role catalog is
   **skipped with a warning log** (role name + contributing group); roles are
   never auto-created. Skipping is safely inert: a binding to an undefined
   role would confer no permissions anyway.
5. **ALL group filtering happens inside the Database service** (clarified
   2026-11-06): `ListGroups` carries the same kind of generic equality
   predicates as `ListIDPUsers` (`display_name`, `external_id`,
   `members_value`), evaluated
   as real SQL WHERE clauses on indexed columns — callers receive only
   matching rows, so network transfer scales with the ANSWER, not the
   population. The IdP parses the SCIM filter subset into those predicates
   and keeps only page slicing (`startIndex`/`count` over the already-
   answered set). Supporting this relational form is what motivates
   normalising membership into a junction table (see *Storage*).
6. **The admin API surface exists before the UI.** The UI is not yet
   scaffolded; the read-only `/api/groups` contract lands in this feature so
   UI work later is pure consumption.

**Storage.**
- `IDPGroup` (`internal/models`, registered in `All()`): `ID` (stable numeric
  PK; the SCIM id is its decimal rendering, cf. F-28.4's user ids),
  `DisplayName` (indexed, **NOT unique**), `Description`, `ExternalID`
  (indexed; the provider's group identifier — CREATE-ONLY and IMMUTABLE,
  mirroring F-28.4's user `sticky_external_id` semantics: accepted on
  `POST`, echoed on reads, a differing `PUT` value is rejected with 400
  `unsupportedAttribute`; unlike `displayName` it IS meant to correlate
  across domains, hence filterable — see *Endpoint semantics*),
  `CreatedAt`/`UpdatedAt`.
- `IDPGroupMember` (junction table, registered in `All()`): `GroupID` +
  `Value` (composite unique). `Value` holds the member's VERBATIM string —
  deliberately unvalidated against the user directory at write time (the
  `ApprovalGroup.Members` spirit, F-27), so unknown or departed members
  degrade gracefully instead of poisoning the write. Normalisation (instead
  of a JSON blob column) is what makes ruling 5 possible: `members[value]
  eq` becomes an indexed EXISTS-join, add/remove become row operations,
  and reverse membership becomes an index lookup.
- `RoleBinding` gains `Origin` (string, default `"manual"`): provenance of
  the write — `"manual"` (operator/local/JIT paths, i.e. everything predating
  this column) or `"scim_group"` (written solely by the F-28.5 applicator).
  This is what makes ruling 2 mechanically sound: recomputation diffs only
  `scim_group`-origin bindings.
- Groups are **hard-deletable** (contrast with users): audit trails attach to
  users (actors), not groups, and a deleted group can be recreated — no
  tombstone machinery.

**Member-value resolution.** A stored member value is tried against the user
directory in order: (1) `ExternalID` (the assumed provider identifier), then
(2) `Username` (providers that stuff the login name in). Matches consider
LIVE users only — a tombstoned user counts as unresolvable. Outcomes:
- **Resolved** — the value participates in mapping application for that user
  and expands to `{$ref, value, displayName}` on `GET {id}`.
- **Unresolved** — the value is KEPT in the group (verbatim), expands to
  `{value}` alone (no `$ref`/`displayName`), contributes to no role
  computation, and emits a **warning log naming the value** (troubleshooting
  aid). Writes are never refused on its account.

Reverse membership (needed by the applicator) is an indexed query on the
junction: which groups carry a given user's `ExternalID`/`Username` value.

**Endpoint semantics.**
- `POST` — create a group; embedded members processed (unresolvable values
  stored + logged, per above). May carry `externalId` (stored trimmed;
  OMITTED ⇒ NULL-ish empty). 201. Duplicate `displayName` is legal — no 409.
- `GET` (collection) — paginated `ListResponse`; filter subset: `displayName
  eq X`, `externalId eq X` (exact — provider identifiers are
  case-MEANINGFUL, so the translated predicate is ALWAYS case-sensitive),
  `members[value] eq X` (matches stored values literally), AND-chains,
  quoted values; anything else ⇒ 400 `invalidFilter`. The IdP translates the
  subset into `ListGroups` predicates — evaluation happens wholly in the
  Database service (ruling 5); the IdP only slices the page.
- `GET {id}` — members expanded to `{$ref, value, displayName}`: `value` is
  the stored verbatim string; `$ref` is the resolved user's SCIM `Location`
  (honoring F-28.1's `public_base` pin/per-request derivation via
  `scimLocation`); unresolvable values degrade to `{value}`. Emits
  `externalId` when set.
- `PUT` — definite replace of `displayName`/`description` and the FULL member
  value set (presence-flagged, cf. F-28.4's definite profile replace).
  `externalId` is IMMUTABLE: echoing the stored value is a no-op; posting a
  DIFFERING value ⇒ 400 `unsupportedAttribute` (mirrors the /Users
  classifier's immutability treatment).
- `PATCH` — ops on `members` (`add`/`remove`, values applied verbatim) and
  `displayName`/`description` (`replace`); membership changes are
  transactional junction-row mutations inside the Database service (not an
  IdP-side RMW — the `ApprovalGroup` member-RPC precedent).
- `DELETE` — hard-delete the group; recompute every resolved member (their
  derived set may shrink; orphaned `scim_group` bindings removed).
- Unknown id ⇒ 404; conflicts/errors are RFC 7644-shaped via the F-28.1
  shared encoder. Reads unaudited; mutations audited (below).

**Mapping application.** Deterministic, idempotent, replay-safe.
- Derived roles wanted for a user = the **union** of the mapped roles over
  all groups the user belongs to (per `idp.scim.group_role_mappings`, keyed
  by `displayName` exact match; duplicate-displayName groups share the
  mapping harmlessly).
- **Merge policy (ruling 2).** The user's effective role set =
  manual/operator bindings (ANY origin other than `scim_group`) ∪
  reconciled `scim_group` bindings ∪ token-claim/claim-mapping contributions
  (F-14, orthogonal). The applicator's diff touches ONLY `scim_group`
  bindings: add wanted-but-absent, remove present-but-unwanted. Operator
  grants — made for temporary adjustments — survive every recomputation.
  Known corollaries: (a) leaving one of several groups deriving the same
  role keeps the role (union semantics); (b) if an operator manually grants
  a role that is ALSO group-derived, departing the group removes only the
  `scim_group` copy — the manual grant persists (attributability is
  unknowable; conservatively keep); (c) unmapped groups are stored inertly
  (membership recorded, no authorisation effect).
- **Algorithm** (per affected user U):
  ```
  D    = ⋃ mapped(g.display_name) for groups g containing U   (indexed junction query)
         − names missing from the role catalog   (each: WARNING log, skipped)
  have = { b.roleName | b ← ListRoleBindings(U), b.origin == "scim_group" }
  add(D − have)  /  remove(have − D)
  if diff ≠ ∅ → PublishRoleChange()                    (ruling 1)
  ```
- **Trigger points:** group `PATCH`/`PUT` (each distinct resolved member),
  group `DELETE` (remaining resolved members), user `POST`/`PUT`/`PATCH`
  carrying embedded `groups` (after ensuring memberships, below), and
  implicitly any replay (connector resync) — convergence is by construction.
- **Placeholders & embedded groups (switchover, planned per F-28.4 S2).**
  The stock `user` placeholder binding a SCIM-provisioned user receives is
  MANUAL-origin and **augmented, never displaced**, by derived roles. The
  current `HadGroups` acknowledge-and-discard path in `scim_users.go` flips
  to a trigger point: each embedded value is matched against EXISTING groups
  by exact `displayName`, then by numeric Location; a match ensures the
  value is present in that group's `MemberValues` (gap-fill); a miss is
  ignored + logged (no phantom groups are created from opaque values).
  **Precedence:** group-resource writes are authoritative (PUT replaces the
  full set); user-document embeddings are best-effort supplementation — a
  periodic full-directory resync (authoritative group PUTs) heals any
  ordering skew.
- **Deprovisioning neutrality.** A user's tombstone (F-28.3/4 `DELETE`)
  prunes nothing: memberships are opaque values (harmless while the user is
  gone), expansion already excludes tombstoned users, and no role
  recomputation occurs (authentication is blocked regardless). Rehire needs
  no repair — the values are still there and the next group write/resync
  re-applies.
- **Missing mapped roles (ruling 4):** skipped at application time with a
  warning log (role name + group `displayName`); no creation, no failure.
- **Static mappings.** `group_role_mappings` is process-static config
  (loaded at boot, F-28.1); adopting a changed mapping set requires an IdP
  restart, after which the next sync/replay reconverges.
- **Safety refinement (landed S3):** the reverse-membership enumeration
  treats a TRANSIENT failure (user lookup or listing) as an ERROR, not "no
  groups" — collapsing it to empty would make the caller WIPE the user's
  entire `scim_group` lane on a blip. Only a definitive NotFound (the user
  is truly gone) yields the empty set.
- **Stretch (LANDED):** a mapping entry may target an F-27 approval group
  instead of an F-14 role by prefixing the value `ag:`
  (`group_role_mappings: { "security-owners": "ag:sec-owners" }`) — the
  single-knob discriminant keeps the F-28.1 config surface unchanged. While
  a user's derivation walks their groups, each `ag:` target ADDS the user's
  username to the named approval group via the idempotent
  `AddApprovalGroupMember` RPC (additive + replay-safe; membership REMOVAL
  is not mirrored — departure governance stays with the group resource).
  A missing approval-group name is skipped with a warning (ruling 4's
  twin); the name set is cached briefly (instance-scoped, 30 s TTL) so the
  mirror costs one listing per burst. Orthogonal channel: no role binding,
  no `role_change` publication involved.

**Auditing & metrics.** Mutation events follow F-28.4's lean-contact
habit: `scim.group.create` / `scim.group.replace` / `scim.group.members` /
`scim.group.delete` (actor = the presenting connector; movements attach
before/after, no-move contacts record a `changed:false` marker); resulting
NON-EMPTY role diffs append a companion event naming the user, the gained
and lost roles, and the triggering group. Metrics ride
`cdrom_scim_operations_total{op,result}` with the new `group_*` op values.

**Slices & acceptance criteria.** Four-plus-one sequential increments
(S1 → S5 strictly), each ending compiled, tested, and demonstrable
(checkpoint commit per slice); acceptance boxes sit under their delivering
slice and fill in as slices land (house style, cf. F-28.3/F-28.4).
