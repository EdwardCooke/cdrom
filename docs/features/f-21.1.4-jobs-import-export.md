# F-21.1.4 · Jobs, deployment options & import/export API

> Part of [F-21.1 · File format & compiler](f-21.1-file-format-compiler.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The `spec.jobs` map (a name → job-spec map: `steps`, `needs`,
`variables`, `variableSets`, `environment`, `workerGroup`, and the standard
deployment options) mapped onto the database schema, and the API surface that
makes a YAML definition runnable: **import** (`POST /api/pipelines` /
`PUT /api/pipelines/{id}` accepts the file format and runs it through the
compiler) and **export** (`GET /api/pipelines/{id}/export` renders the compiled
definition back to the file format, with the round-trip property). This is the
integration point: a pipeline defined in YAML can be imported and becomes
runnable.

**Depends on.** [F-21.1.1](f-21.1.1-manifest-envelope.md),
[F-21.1.2](f-21.1.2-step-spec.md) (steps), and
[F-21.1.3](f-21.1.3-variables-secrets.md) (variables) — a job composes steps
and variables, and the import/export API runs the whole compiler.

**Why.** The jobs map is where the file's deployment intent (which environment,
which worker group, how to retry, what it depends on) meets the database schema,
and the import/export API is what makes "the UI editor and the file format are
two views of the same model" true: the same compiled definition can be authored
in the UI or imported from a file, and exported back to a file that re-imports
equivalently.

**Scope.**
- `internal/pipelinefile` — the `spec.jobs` map: each job's name is its stable
  `key` (F-08); `needs` (optional) lists the names of the jobs it depends on →
  `DependsOn` (F-08) — empty means no dependencies — and the job DAG is
  validated at import (unique keys, known `needs`, no cycle; shared with F-08);
  `environment` (F-17); `workerGroup` (the worker group the job runs on,
  defaulting to `spec.workerGroup`); and the standard deployment options
  (`timeout` F-03, `retry` F-04, `failureMode` F-01, `concurrencyKeys` F-16,
  `automation` / `approval` F-17, `ignoreFailed` F-06, `stepBarrier` F-01,
  `triggers` F-09, `params` F-10, `labels` F-29). A field the file does not set
  is left at the database default (the same defaults the UI path uses), so a
  minimal file is valid.
- `internal/api/server.go` — **import**: `POST /api/pipelines` (or
  `PUT /api/pipelines/{id}`) accepts a definition in the file format (YAML or
  its JSON equivalent); the API runs it through the compiler (validate + map to
  the schema) and creates/updates the pipeline.
- `internal/api/server.go` — **export**: `GET /api/pipelines/{id}/export`
  renders the pipeline's current compiled definition back into the file format;
  the round-trip property (export → import → same compiled definition) holds
  because the compiler is a pure function of the file and the exporter is its
  inverse on the fields the file can express.

**Acceptance criteria.**
- [x] A pipeline defined in YAML can be imported (via the API) and becomes
      runnable.
- [x] `spec.jobs.<name>` maps to `Job.Key` (the name is the key, F-08);
      `needs` (optional) maps to `DependsOn` (F-08) — empty means no
      dependencies — and the job DAG is validated at import (unique keys, known
      `needs`, no cycle; shared with F-08).
- [x] A job names the environment it targets (`environment`, F-17) and the
      worker group it runs on (`workerGroup`, defaulting to `spec.workerGroup`).
- [x] Standard deployment options in the file (timeout, retry, failure mode,
      concurrency keys, environment, automation, approval, needs, triggers,
      params, labels) map onto the database schema; a field the file does not
      set is left at the database default (the same defaults the UI path uses),
      so a minimal file is valid.
- [x] **Import** — `POST /api/pipelines` (or `PUT /api/pipelines/{id}`) accepts
      a definition in the file format (YAML or its JSON equivalent); the API
      runs it through the compiler (validate + map to the schema) and
      creates/updates the pipeline.
- [x] **Export** — `GET /api/pipelines/{id}/export` renders the pipeline's
      current compiled definition back into the file format; exporting a
      pipeline reproduces a file that re-imports equivalently (round-trip): the
      exported file, re-imported, yields the same compiled definition.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Standard deployment options map onto the schema.** The file's deployment
  fields (timeout, retry, failure mode, concurrency keys, environment,
  automation, approval, needs, triggers, params, labels) map one-to-one onto the
  existing database fields (F-01…F-17, F-29); an unset field falls back to the
  database default, so a minimal file is valid.
- **Import and export are two views of one model.** Import runs the file
  through the compiler (a pure function of the file) to create/update the
  pipeline; export is the compiler's inverse on the fields the file can express,
  so the round-trip property (export → import → same compiled definition)
  holds. For a UI-authored pipeline the export synthesizes a file from the
  compiled model.
- **New fields / RPCs / endpoints (this sub-feature).** The `spec.jobs` mapping
  in `internal/pipelinefile` (name → `Job.Key`, `needs` → `DependsOn` with the
  shared F-08 DAG validation, `environment`, `workerGroup` defaulting to
  `spec.workerGroup`, and the standard deployment options); `POST /api/pipelines`
  / `PUT /api/pipelines/{id}` accepting the file format (YAML or its JSON
  equivalent); and `GET /api/pipelines/{id}/export`.
