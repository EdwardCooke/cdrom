# F-21.1.3 · Variables, masked variables & secret sources

> Part of [F-21.1 · File format & compiler](f-21.1-file-format-compiler.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The file's variable model: there is **no separate concept of a
secret** — every value is a variable, and a variable is **masked** when its
value is not a plain string. A variable is `name: value` (a plain value),
`name: {encrypted: <ciphertext>}` (a builtin F-12 ciphertext), or
`name: {secretSource: <name>, key: <key>}` (a value from a named
`secretSources` entry). All variables — masked or not — are referenced the same
way, as `{{ .params.<name> }}`. Variable sets are inline `variables` maps
declared under `spec.variableSets` and referenced by a job in its
`variableSets` list; `secretSources` is the named-resource section that backs
the sourced kind.

**Depends on.** [F-21.1.1](f-21.1.1-manifest-envelope.md) (the manifest
envelope + compiler skeleton). It builds on F-10 (parameters & variables) and
F-12 (secrets management).

**Why.** One uniform `variables` shape for plain and masked values alike keeps
the file simple: a step does not care where a value came from or whether it is
masked, and the platform tracks which variables are masked (redacting their
values in logs and hiding them in the UI) without a separate secret concept.

**Scope.**
- `internal/pipelinefile` — variable value shapes: a plain value,
  `{encrypted: <ciphertext>}` (a builtin F-12 ciphertext — the ciphertext is
  what `POST /api/secrets/encrypt` returns; the API decrypts it at dispatch and
  hands the plaintext to the target), or `{secretSource: <name>, key: <key>}`
  (a value from the named `secretSources` entry, resolved by the API at
  dispatch). The compiler records which variables are **masked** (value not a
  plain string); a masked variable's value is redacted in logs and hidden in
  the UI, and its plaintext is never persisted or returned to the UI.
- `spec.variableSets` — named variable sets, each an inline `variables` map
  (external-file / vault imports are F-21.4); a job references sets by name in
  its `variableSets` list.
- Merging: at compile time the compiler resolves each named set and merges the
  sets' variables with the job's inline `variables` into the run's parameters
  for that job's spec interpolation (F-10), with the job's inline variables
  winning over a set's on a key collision.
- `spec.secretSources` — named secret sources (F-12): each entry has a `kind`
  (a secret-store kind — `Vault` / `OpenBao` are reserved kinds; the built-in
  AES store is the default when no source is named), a `path` (the source
  path), and an `audience` (the token audience used to fetch from the source).
  The source's settings are stored opaquely on the pipeline (like a secret
  declaration, F-12); the API resolves the named source to a concrete value at
  dispatch and hands it to the target.

**Acceptance criteria.**
- [x] There is no separate concept of a secret: a variable is `name: value`
      (a plain value), `name: {encrypted: <ciphertext>}` (a builtin F-12
      ciphertext), or `name: {secretSource: <name>, key: <key>}` (a value from a
      named `secretSources` entry); a variable is **masked** when its value is
      not a plain string, the platform tracks which variables are masked (their
      values are redacted in logs and hidden in the UI), and all variables —
      masked or not — are referenced the same way, as `{{ .params.<name> }}`.
- [x] The plaintext of a masked variable is never persisted or returned to the
      UI.
- [x] Variable sets are inline `variables` maps declared under
      `spec.variableSets`; a job references sets by name in its `variableSets`
      list.
- [x] At compile time the sets' variables are merged with the job's inline
      `variables` into the run's parameters for that job's spec interpolation
      (F-10), with the job's inline variables winning over a set's on a key
      collision.
- [ ] `secretSources` is a section of named, referencable secret sources: each
      entry has a `kind` (a secret-store kind, F-12 — `Vault` / `OpenBao` are
      reserved kinds; the built-in AES store is the default when no source is
      named), a `path`, and an `audience`; a variable references a source **by
      name** with a `key` selecting the value within the source; the source's
      settings are stored opaquely on the pipeline (like a secret declaration,
      F-12) and the API resolves the named source to a concrete value at
      dispatch.
- [x] Named, referencable resources are declared in a consistent `spec` section
      and referenced by name — `secretSources` (F-12), and the same pattern for
      variable sets, steps, and jobs.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Masked variables, not a separate concept of a secret.** Every value is a
  variable: a plain variable is `name: value`, and a variable is **masked**
  when its value is a map — `{encrypted: <ciphertext>}` for a builtin F-12
  ciphertext or `{secretSource: <name>, key: <key>}` for a value from a named
  `secretSources` entry. This keeps one uniform `variables` shape (F-10) for
  plain and masked values alike, and masked variables are referenced the same
  way as any other variable (`{{ .params.<name> }}`); the platform tracks which
  variables are masked (redacting their values in logs and hiding them in the
  UI), and the `secretSources` section (renamed from `secretVaults`) is the
  named-resource section that backs the sourced kind.
- **The named-resource pattern.** `secretSources` is the template for how the
  file declares any named, referencable resource: a `spec` section that is a
  map of `name → settings`, referenced by name elsewhere in the file.
  `variableSets`, `steps`, and `jobs` all follow the same shape, so a reader
  who knows one section knows them all. New kinds of named resource slot into
  the same pattern without changing the referencing rules.
- **New fields / RPCs / endpoints (this sub-feature).** Variable value-shape
  parsing + masked-variable tracking in `internal/pipelinefile`; the
  `spec.variableSets` section (inline `variables` maps) and a job's
  `variableSets` list (merge into the run's parameters, F-10, job-inline wins);
  and the `spec.secretSources` section (stored opaquely on the pipeline, F-12,
  resolved at dispatch).
