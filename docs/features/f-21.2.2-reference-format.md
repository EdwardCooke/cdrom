# F-21.2.2 · Reference format & parsing

> Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **reference** — the single `<type>:<spec>` string that names a
definition file to fetch — and the rules for parsing it. A reference has a
`<type>` of `git` / `http` / `file` followed by a `:` and the kind-specific
locator. The reference is the shared syntax for naming a definition file: the
source-fetcher (F-21.2.1) parses it to perform the fetch, and the same syntax
is what a file's imports (F-21.4) and a `PipelineSource` (F-21.5.1) use to
point at a file.

**Why.** A single string that names both the kind and the locator keeps the
"where is this file" question in one place and portable across the fetcher,
imports, and the source model — and it lets a file reference another file (or a
repository) without any structured locator object.

**Scope.**
- The reference grammar for the three kinds (`git` / `http` / `file`), the
  backslash-escaping rules, and the left-to-right parsing algorithm.
- The fetcher's reference parser (in `internal/services/pipelinesource`), which
  selects the kind and the locator and returns a clear error for an unknown
  type or a malformed reference.

**Acceptance criteria.**
- [x] A fetch is named by a **reference** — a `<type>:<spec>` string with
      `<type>` of `git` / `http` / `file` — and the fetcher parses it to select
      the kind and the locator; an unknown type is a clear error.
- [x] A **`git`** reference is `<repo>@<branch>[<path>]`: the branch ref may
      contain `/` (and any other character git allows in a ref), and the file
      path is wrapped in `[]`. The first **unescaped** `@` is the branch
      separator, so a `@` that is part of the repository (the `git@host` in an
      SSH remote, or a literal `@` in an HTTPS path) or part of the branch is
      escaped as `\@`; a literal `[` / `]` / `\` is escaped as `\[` / `\]` /
      `\\`. The reference must end immediately after the closing `]`.
- [x] An **`http`** reference is the full URL of the endpoint that serves the
      file; request headers are not part of the reference (they come from the
      source's `http` credential, F-21.3).
- [x] A **`file`** reference is a path resolved against the fetcher's
      configured local-filesystem root (F-21.2.4); the reference itself carries
      only the path.
- [x] A malformed reference (an unknown type, a `git` reference with no
      unescaped `@` or no `[`/`]`, or a reference with trailing content after
      the closing `]`) is a clear error.

## The reference format

A fetch is named by a single **reference** string — `<type>:<spec>`, where
`<type>` is the kind of source and `<spec>` is the kind-specific locator. The
reference is the shared syntax for naming a definition file: the source-fetcher
parses it to perform the fetch, and the same syntax is what a file's imports
(F-21.4) and a `PipelineSource` (F-21.5.1) use to point at a file.

| Type   | Spec | Example |
|--------|------|---------|
| `git`  | `<repo>@<branch>[<path>]` — the git remote, the branch ref, and the file path wrapped in `[]` (a `@` in the repo or branch is escaped as `\@`) | `git:https://github.com/edwardcooke/cdrom.git@main[/some/path/file.yaml]` |
| `http` | the URL of the endpoint that serves the file | `http:https://www.example.com/some/file.yaml` |
| `file` | the path of the file, resolved against the fetcher's configured local-filesystem root | `file:/shared-variables.yaml` |

**`git`** — `<repo>@<branch>[<path>]`:

- `<repo>` — the git remote, in the SSH form
  (`ssh://github.com:EdwardCooke/cdrom.git`) or the HTTPS form
  (`https://github.com/EdwardCooke/cdrom.git`).
- `<branch>` — the branch ref to track (e.g. `main`); it may contain `/` and
  any other character git allows in a ref. The `@<branch>` segment is written
  explicitly even for the default branch.
- `[<path>]` — the path of the file within the repository, wrapped in square
  brackets (e.g. `[/some/path/file.yaml]`).

**Escaping.** A backslash `\` escapes the next character. The structurally
significant characters — `@` (the branch separator), `[` and `]` (the path
brackets), and `\` itself — must be escaped to appear literally:

| Literal | Written as |
|---------|-----------|
| `@`     | `\@`      |
| `[`     | `\[`      |
| `]`     | `\]`      |
| `\`     | `\\`      |

The only **unescaped** `@` in the reference is the branch separator. Any `@`
that is part of the repository — the `git@host` in an SSH remote, or a literal
`@` in an HTTPS path — or part of the branch must be written as `\@`.

**Parsing.** The reference is parsed left to right, honoring escapes:

1. The first **unescaped** `@` is the branch separator; the text before it
   (escapes resolved) is the repository.
2. The first **unescaped** `[` after the separator opens the path; the text
   between the separator and the `[` (escapes resolved) is the branch.
3. The first **unescaped** `]` after the opener closes the path; the text
   between the brackets (escapes resolved) is the path.
4. The reference must end immediately after the closing `]`.

**Examples.**

- `git:https://github.com/edwardcooke/cdrom.git@main[/some/path/file.yaml]`
  → repo `https://github.com/edwardcooke/cdrom.git`, branch `main`, path
  `/some/path/file.yaml`.
- `git:ssh://github.com:EdwardCooke/cdrom.git@main[/path/to/file.yaml]`
  → an SSH remote, branch `main`, path `/path/to/file.yaml`.
- `git:https://somegit.com/edward\@test/cdrom.git@branch\@name[/test/aweird\]path/file.yaml]`
  → repo `https://somegit.com/edward@test/cdrom.git` (a literal `@` in the
  path, escaped), branch `branch@name` (a literal `@`, escaped), path
  `/test/aweird]path/file.yaml` (a literal `]`, escaped).

**`http`** — the full URL of the endpoint that serves the file (e.g. an
object-store URL or a raw-file endpoint). Request headers (e.g. an
`Authorization` header) are not part of the reference — they come from the
source's `http` credential (F-21.3), which makes a credential **optional**: an
endpoint that needs no authentication is fetched with a plain GET.

**`file`** — a path resolved against the fetcher's configured local-filesystem
root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`, F-21.2.4): the file is read from
`<root><path>`. For example, a reference of `file:/shared-variables.yaml` with
a root of `/shared` reads `/shared/shared-variables.yaml`. The root keeps the
fetcher from reading arbitrary files on its host; when no root is configured the
`file` kind is disabled.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **A reference is a single `<type>:<spec>` string.** A fetch is named by one
  string — `<type>` of `git` / `http` / `file`, a `:`, then the kind-specific
  locator. The reference is the shared syntax for naming a definition file: the
  source-fetcher parses it, and the same syntax is what a file's imports
  (F-21.4) and a `PipelineSource` (F-21.5.1) use to point at a file.
- **`git` references are `<repo>@<branch>[<path>]` with backslash escaping.**
  The file path is wrapped in `[]`, which frees the branch ref to contain `/`
  (and any other character git allows in a ref). The first **unescaped** `@` is
  the branch separator, so a `@` that is part of the repository (the `git@host`
  in an SSH remote, or a literal `@` in an HTTPS path) or part of the branch is
  escaped as `\@`; a literal `[` / `]` / `\` is escaped as `\[` / `\]` / `\\`.
  The reference is parsed left to right honoring escapes and must end
  immediately after the closing `]`.
- **`http` headers are not in the reference.** An `http` reference is just the
  URL; request headers come from the source's `http` credential (F-21.3), which
  makes a credential optional (a public endpoint is fetched with a plain GET).
- **`file` references carry only the path.** A `file` reference is a path
  resolved against the fetcher's configured local-filesystem root (F-21.2.4);
  the root is a deployment concern, not part of the reference.
- **New fields / RPCs / endpoints (this sub-feature).** The reference grammar
  and parser in `internal/services/pipelinesource` (the fetcher selects the
  kind and locator from the reference and returns a clear error for an unknown
  type or a malformed reference).
