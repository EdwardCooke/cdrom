# F-21.3 · Source credentials

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature adds **source credentials** — named, database-stored
credentials that authenticate a fetch of a private source (a private git
repository, or an HTTP/HTTPS endpoint that requires a token). Credentials are
**matched to a source by a prefix**, **updatable through the API**, and their
secret material is **encrypted at rest** (F-12). The source-fetcher (F-21.2)
never stores a credential: the API decrypts it and passes the plaintext to the
fetcher for a single fetch.

**What.** A `SourceCredential` model (a named credential with a `kind` of
`git-ssh` / `git-https` / `http`, a `prefix` matched against a source's
URL, and encrypted secret material), stored in the database and managed through
the API (CRUD). When a source is synced, the API selects the credential to use
(an explicit `credential` name on the source, else the longest matching
`prefix`), decrypts its secret material, and hands the plaintext to the
source-fetcher (F-21.2) for that one fetch.

**Why.** Private sources need authentication, but the fetcher holds no
credentials at rest (its only on-disk state is the transient git repository
cache, F-21.2) and the API should not hold long-lived secrets in configuration.
Storing credentials in the database (encrypted), matching them to sources by
prefix, and managing them through the API keeps secret material out of config
files and the fetcher, and makes a stale credential diagnosable without a repo
checkout.

**Depends on.** F-12 (the secret store the API encrypts/decrypts with) and F-14
(the RBAC permissions).

**Scope.**
- `internal/models` — a `SourceCredential` (a `name`, a `kind` of `git-ssh` /
  `git-https` / `http`, a `prefix` over the source URL, a `description`,
  and the kind's secret material — stored as F-12 ciphertext when marked
  sensitive, in plaintext otherwise); registered in `models.All()`.
- `internal/services/database` — credential CRUD (create / read / update /
  delete), storing the secret material opaquely (ciphertext).
- `internal/api` — the **source-credential** CRUD endpoints (the API encrypts
  the plaintext on create/update via the F-12 store and redacts it on read), and
  the credential **matching** used by the sync routine (F-21.5): an explicit
  `credential` name on the source, else the longest matching `prefix`.
- `internal/api/server.go` — `GET/POST /api/source-credentials`,
  `GET/PUT/DELETE /api/source-credentials/{name}`.

**Acceptance criteria.**
- [x] A `SourceCredential` has a `name` (unique; the value a
      `PipelineSource.credential` references), a `kind` (`git-ssh` /
      `git-https` / `http`), a `prefix` (matched against a source's
      `reference` — the repository URL for a `git` source, the endpoint URL for
      an `http` source), a `description` (optional), and the kind's secret
      material.
- [x] The secret material is, by kind: `git-https` — `username` (may be empty
      for token-only auth) and `token`; `git-ssh` — `privateKey` (PEM) and
      `hostKey` (the expected host public key, for host-key verification);
      `http` — a **list of headers**, each a header name and value with its own
      `sensitive` flag (default `false`) that marks that header's value as
      secret material.
- [x] For an `http` credential, each header is a name and value (the value
      carries the secret, e.g. `Authorization: Bearer <token>`). When a
      header's `sensitive` flag is `true`, the **entire header value** is
      secret material — encrypted at rest and redacted on read (shown as
      `<redacted>`); when it is `false` (the default), that header's value is
      stored in plaintext and returned as-is, so a non-sensitive header is
      easily viewed and modified. A credential may carry any number of
      headers, each with its own sensitivity.
- [x] The secret material is **encrypted with the API's secret store** (F-12)
      before it is stored: the API encrypts on create/update and the database
      service stores the ciphertext opaquely (it never sees the key).
- [x] The plaintext is **never returned to the UI** — a credential read back
      through the API shows its `name`, `kind`, `prefix`, `description`, and
      (for `git-https`) `username`, but the token / private key are redacted
      (and, for `http`, each header value is masked when its `sensitive` flag
      is `true`, returned in plaintext when it is `false`).
- [x] When a source is synced: if the source names a `credential`, that
      credential is used; otherwise the source's `reference` is matched against
      every credential's `prefix` and the **most specific (longest) matching
      prefix** wins; a source matching no credential uses no credential (a
      public source).
- [x] The chosen credential's secret material is decrypted by the API for that
      single fetch and handed to the source-fetcher (F-21.2); it is not
      persisted anywhere else and is not logged.
- [x] A credential that fails to authenticate (a rotated token, a revoked key)
      surfaces as a sync failure on the source state (F-21.5) and is visible in
      the UI, so a stale credential is diagnosable without a repo checkout.
      (Implemented with the minimal F-21.5.1/F-21.5.2 slice: a source refresh
      records the fetch error on the source state's `last_error`, surfaced via
      `GET /api/pipelines/{id}/source`.)
- [x] `GET /api/source-credentials` lists credentials (secret material
      redacted); `POST` creates one (the body carries the plaintext secret
      material, which the API encrypts before storing); `GET/{name}` fetches one
      (redacted); `PUT/{name}` updates (re-encrypts the secret material);
      `DELETE/{name}` deletes (rejected with 409 if a source still references it
      by name).
- [x] Listing requires `source-credentials.can-view`; create/update/delete
      require `source-credentials.can-manage` (admins have both). A change
      publishes a `source_credential` WS event so the UI stays current.

## The credential model

- **`SourceCredential`** — a named credential:
  - `name` (unique; the value a `PipelineSource.credential` references).
  - `kind` — `git-ssh`, `git-https`, or `http`.
  - `prefix` — a string prefix matched against a source's `reference` (the
    repository URL for a `git` source, the endpoint URL for an `http` source).
    When a fetch needs a credential, the API matches the source's `reference`
    against every credential's `prefix`; the **most specific (longest) matching
    prefix** wins. A source whose `reference` matches no credential uses no
    credential (a public source). A source that names a `credential` by name
    uses that specific credential (the name is an explicit override of the
    prefix match).
  - The **secret material**, by kind:
    - `git-https` — `username` (may be empty for token-only auth) and `token`
      (a personal access token or bot password). The fetcher authenticates the
      git clone/fetch as `https://<username>:<token>@host/...` (the token is
      never logged).
    - `git-ssh` — `privateKey` (the PEM-encoded private key) and `hostKey` (the
      expected host public key, for host-key verification so a fetch is not
      vulnerable to a MITM). The fetcher uses the key for the SSH handshake and
      verifies the server's host key against `hostKey`.
    - `http` — a **list of headers** (each a header name and value; the value
      carries the secret, e.g. `Authorization: Bearer <token>`), each with its
      own `sensitive` flag (default `false`). When a header's `sensitive` flag
      is `true`, the **entire header value** is secret material — the fetcher
      sends it on its GET of the endpoint, but it is encrypted at rest,
      redacted in logs, and never returned to the UI (a credential read back
      shows the header name with its value masked, e.g.
      `Authorization: <redacted>`). When it is `false` (the default), that
      header's value is stored in plaintext and returned as-is, so a
      non-sensitive header is easily viewed and modified. A credential may
      carry any number of headers, each with its own sensitivity.
  - `description` (optional, human-readable).

The secret material (`token` for `git-https`, `privateKey` and `hostKey` for
`git-ssh`, and — for `http` — each header value whose `sensitive` flag is
`true`) is **encrypted with the API's secret store** (F-12)
before it is stored, exactly like a masked variable's value: the API encrypts
on create/update and the database service stores the ciphertext opaquely (it
never sees the key). The plaintext is never returned to the UI — a credential
read back through the API shows its `name`, `kind`, `prefix`, `description`,
and (for `git-https`) `username`, but the token / private key are redacted
(and, for `http`, each header value is masked when its `sensitive` flag is
`true` and returned in plaintext when it is `false`).
Updating a credential re-encrypts the new secret material; the existing one is
replaced.

How a source is matched to a credential (an explicit `credential` name, else
the longest matching `prefix`) and how the chosen credential is decrypted and
handed to the fetcher for a single fetch is in
[F-21.3.2](f-21.3.2-credential-matching.md). The CRUD endpoints, the
encrypt-on-write / redact-on-read behavior, the RBAC gates, and the
`source_credential` WS event are in
[F-21.3.3](f-21.3.3-source-credential-api.md).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Source credentials are DB-stored, prefix-matched, and API-managed.** A
  `SourceCredential` (kind `git-ssh` / `git-https` / `http`, a `prefix`
  over the source's `reference`, and encrypted secret material) is stored in the
  database
  (secret material encrypted with the F-12 store, opaque to the database
  service) and managed through the API (CRUD, gated on
  `source-credentials.can-view` / `can-manage`). A source is matched to a
  credential by the longest matching `prefix` (or an explicit `credential` name
  override); the credential's secret is decrypted by the API for a single fetch
  and handed to the source-fetcher (which stores nothing) — it is never logged
  or returned to the UI. `git-ssh` credentials carry a private key + host key
  (host-key verified); `git-https` credentials carry a token (and an optional
  username); an `http` credential carries a **list of headers** (each name +
  value, the value carrying the secret), each of which can be marked sensitive
  via its own `sensitive` flag (default `false`) — when sensitive its entire
  value is encrypted at rest and masked on read, when not it is stored in
  plaintext and returned as-is.
- **New fields / RPCs / endpoints (this sub-feature).** A `SourceCredential`
  model (registered in `models.All()`); credential CRUD in the database service
  (secret material stored as F-12 ciphertext when marked sensitive, in
  plaintext otherwise); `GET/POST /api/source-credentials`
  and `GET/PUT/DELETE /api/source-credentials/{name}` (api); a
  `source-credentials.can-view` / `source-credentials.can-manage` permission
  pair (F-14); and a `source_credential` WS event.
