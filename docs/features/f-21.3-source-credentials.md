# F-21.3 · Source credentials

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature adds **source credentials** — named, database-stored
credentials that authenticate a fetch of a private source (a private git
repository, or an HTTP/HTTPS endpoint that requires a token). Credentials are
**matched to a source by a regex**, **updatable through the API**, and their
secret material is **encrypted at rest** (F-12). The source-fetcher (F-21.2)
never stores a credential: the API decrypts it and passes the plaintext to the
fetcher for a single fetch.

**What.** A `SourceCredential` model (a named credential with a `kind` of
`git-ssh` / `git-https` / `http`, a `pattern` regex matched against a source's
URL, and encrypted secret material), stored in the database and managed through
the API (CRUD). When a source is synced, the API selects the credential to use
(an explicit `credential` name on the source, else the longest matching
`pattern`), decrypts its secret material, and hands the plaintext to the
source-fetcher (F-21.2) for that one fetch.

**Why.** Private sources need authentication, but the fetcher is stateless and
the API should not hold long-lived secrets in configuration. Storing credentials
in the database (encrypted), matching them to sources by regex, and managing
them through the API keeps secret material out of config files and the fetcher,
and makes a stale credential diagnosable without a repo checkout.

**Scope.**
- `internal/models` — a `SourceCredential` (a `name`, a `kind` of `git-ssh` /
  `git-https` / `http`, a `pattern` regex over the source URL, a `description`,
  and the kind's secret material, stored as F-12 ciphertext); registered in
  `models.All()`.
- `internal/services/database` — credential CRUD (create / read / update /
  delete), storing the secret material opaquely (ciphertext).
- `internal/api` — the **source-credential** CRUD endpoints (the API encrypts
  the plaintext on create/update via the F-12 store and redacts it on read), and
  the credential **matching** used by the sync routine (F-21.5): an explicit
  `credential` name on the source, else the longest matching `pattern`.
- `internal/api/server.go` — `GET/POST /api/source-credentials`,
  `GET/PUT/DELETE /api/source-credentials/{name}`.

**Acceptance criteria.**
- [ ] A `SourceCredential` has a `name` (unique; the value a
      `PipelineSource.credential` references), a `kind` (`git-ssh` /
      `git-https` / `http`), a `pattern` (a regex matched against a source's
      `url`), a `description` (optional), and the kind's secret material.
- [ ] The secret material is, by kind: `git-https` — `username` (may be empty
      for token-only auth) and `token`; `git-ssh` — `privateKey` (PEM) and
      `hostKey` (the expected host public key, for host-key verification);
      `http` — `token` and an optional `header` (default
      `Authorization: Bearer <token>`).
- [ ] The secret material is **encrypted with the API's secret store** (F-12)
      before it is stored: the API encrypts on create/update and the database
      service stores the ciphertext opaquely (it never sees the key).
- [ ] The plaintext is **never returned to the UI** — a credential read back
      through the API shows its `name`, `kind`, `pattern`, `description`, and
      (for `git-https`) `username`, but the token / private key are redacted.
- [ ] When a source is synced: if the source names a `credential`, that
      credential is used; otherwise the source's `url` is matched against every
      credential's `pattern` and the **most specific (longest) matching
      pattern** wins (the same resolution rule as F-16's concurrency-limit
      rules); a source matching no credential uses no credential (a public
      source).
- [ ] The chosen credential's secret material is decrypted by the API for that
      single fetch and handed to the source-fetcher (F-21.2); it is not
      persisted anywhere else and is not logged.
- [ ] A credential that fails to authenticate (a rotated token, a revoked key)
      surfaces as a sync failure on the source state (F-21.5) and is visible in
      the UI, so a stale credential is diagnosable without a repo checkout.
- [ ] `GET /api/source-credentials` lists credentials (secret material
      redacted); `POST` creates one (the body carries the plaintext secret
      material, which the API encrypts before storing); `GET/{name}` fetches one
      (redacted); `PUT/{name}` updates (re-encrypts the secret material);
      `DELETE/{name}` deletes (rejected if a source still references it by name).
- [ ] Listing requires `source-credentials.can-view`; create/update/delete
      require `source-credentials.can-manage` (admins have both). A change
      publishes a `source_credential` WS event so the UI stays current.

## The credential model

- **`SourceCredential`** — a named credential:
  - `name` (unique; the value a `PipelineSource.credential` references).
  - `kind` — `git-ssh`, `git-https`, or `http`.
  - `pattern` — a regular expression matched against a source's `url`. When a
    fetch needs a credential, the API matches the source's `url` against every
    credential's `pattern`; the **most specific (longest) matching pattern**
    wins (the same resolution rule as F-16's concurrency-limit rules). A source
    whose `url` matches no credential uses no credential (a public source). A
    source that names a `credential` by name uses that specific credential (the
    name is an explicit override of the regex match).
  - The **secret material**, by kind:
    - `git-https` — `username` (may be empty for token-only auth) and `token`
      (a personal access token or bot password). The fetcher authenticates the
      git clone/fetch as `https://<username>:<token>@host/...` (the token is
      never logged).
    - `git-ssh` — `privateKey` (the PEM-encoded private key) and `hostKey` (the
      expected host public key, for host-key verification so a fetch is not
      vulnerable to a MITM). The fetcher uses the key for the SSH handshake and
      verifies the server's host key against `hostKey`.
    - `http` — `token` (a bearer token or API key) and optional `header` (the
      header the token is sent in; default `Authorization: Bearer <token>`). The
      fetcher sends the header on its GET of the endpoint.
  - `description` (optional, human-readable).

The secret material (`token` for `git-https` / `http`, `privateKey` and
`hostKey` for `git-ssh`) is **encrypted with the API's secret store** (F-12)
before it is stored, exactly like a masked variable's value: the API encrypts
on create/update and the database service stores the ciphertext opaquely (it
never sees the key). The plaintext is never returned to the UI — a credential
read back through the API shows its `name`, `kind`, `pattern`, `description`,
and (for `git-https`) `username`, but the token / private key are redacted.
Updating a credential re-encrypts the new secret material; the existing one is
replaced.

### Matching and use

When a source is synced (F-21.5):

1. If the source names a `credential`, that credential is used.
2. Otherwise the source's `url` is matched against every credential's
   `pattern`; the longest matching pattern's credential is used.
3. If neither applies, the fetch runs unauthenticated (a public source).

The chosen credential's secret material is decrypted by the API for that single
fetch and handed to the source-fetcher (F-21.2, over the gRPC call); it is not
persisted anywhere else (the fetcher is stateless) and is not logged. A
credential that fails to authenticate (a rotated token, a revoked key) surfaces
as a sync failure on the source state (`last_error`) and is visible in the UI,
so a stale credential is diagnosable without a repo checkout.

### API surface

- `GET /api/source-credentials` — list credentials (secret material redacted).
- `POST /api/source-credentials` — create a credential (the body carries the
  plaintext secret material, which the API encrypts before storing).
- `GET /api/source-credentials/{name}` — fetch one (redacted).
- `PUT /api/source-credentials/{name}` — update (re-encrypts the secret
  material).
- `DELETE /api/source-credentials/{name}` — delete (rejected if a source still
  references it by name).

Listing requires `source-credentials.can-view`; create/update/delete require
`source-credentials.can-manage` (admins have both). A change publishes a
`source_credential` WS event so the UI stays current. Because the secret
material is encrypted at rest and redacted on read, a holder of `can-view` can
see which sources a credential covers (its `pattern`) but not the token or key
itself.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Source credentials are DB-stored, regex-matched, and API-managed.** A
  `SourceCredential` (kind `git-ssh` / `git-https` / `http`, a `pattern` regex
  over the source URL, and encrypted secret material) is stored in the database
  (secret material encrypted with the F-12 store, opaque to the database
  service) and managed through the API (CRUD, gated on
  `source-credentials.can-view` / `can-manage`). A source is matched to a
  credential by the longest matching `pattern` (or an explicit `credential` name
  override); the credential's secret is decrypted by the API for a single fetch
  and handed to the source-fetcher (which stores nothing) — it is never logged
  or returned to the UI. `git-ssh` credentials carry a private key + host key
  (host-key verified); `git-https` and `http` credentials carry a token (and,
  for `git-https`, an optional username).
- **New fields / RPCs / endpoints (this sub-feature).** A `SourceCredential`
  model (registered in `models.All()`); credential CRUD in the database service
  (secret material stored as F-12 ciphertext); `GET/POST /api/source-credentials`
  and `GET/PUT/DELETE /api/source-credentials/{name}` (api); a
  `source-credentials.can-view` / `source-credentials.can-manage` permission
  pair (F-14); and a `source_credential` WS event.
