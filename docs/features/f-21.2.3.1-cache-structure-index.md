# F-21.2.3.1 · Cache structure & index

> Part of [F-21.2.3 · Git repository cache](f-21.2.3-git-repository-cache.md) · Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The on-disk **structure** of the fetcher's git repository cache: a
configurable cache root, the portable per-repository directory naming, and the
**text index file** that maps each cached repository to its directory and its
last-accessed / last-fetched timestamps. The index is the cache's authoritative
map and is updated **atomically** (temp file + rename). This is the foundation
the fetch lifecycle (F-21.2.3.2), the cross-replica locking (F-21.2.3.3), and
the cleanup thread (F-21.2.3.4) build on.

**Why.** A cache needs a stable, portable layout and a single authoritative map
of what is cached. Naming directories by creation time keeps them sortable and
uniquely identifiable across replicas, and an atomically-updated text index is
the coordination point that lets multiple fetcher replicas sharing the cache
(e.g. two pods on a PVC) agree on which directory holds which repository and
when it was last used — without a database.

**Scope.**
- The on-disk cache under a process-level cache root
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, default the `repositories` directory
  under the OS temp directory).
- The per-repository directory naming (`<unix-epoch-seconds>-<counter>`).
- The **text index file** at the cache root (one line per cached repository:
  the directory, the URL, the last-accessed and last-fetched Unix epoch
  timestamps), updated **atomically** (temp file + rename).
- `internal/config` — `CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`.

**Acceptance criteria.**
- [ ] The **cache root** is configurable at the process level
      (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`) and defaults to a `repositories`
      directory under the OS temp directory (e.g. `/tmp/repositories` on Linux,
      `%TEMP%\repositories` on Windows); each cached repository lives in its own
      subdirectory of the root.
- [ ] A cached repository's **directory name** is a Unix epoch timestamp and an
      incrementing counter (e.g. `1761024000-3`) — characters that are safe on
      both Windows and Linux filesystems, and that sort by creation time.
- [ ] A **text index file** at the cache root records, per cached repository,
      the repository directory, the repository URL, the last-accessed Unix
      epoch timestamp, and the last-fetched Unix epoch timestamp.
- [ ] The index is updated **atomically** (the new content is written to a temp
      file in the same directory and renamed over the index) on every change, so
      a reader never sees a partially written index.

## The cache structure

The cache is a directory tree under a single root, with one text file at the
root that maps its contents.

- **Cache root.** The root of the cache is configurable at the process level
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`) and defaults to a `repositories`
  directory under the OS temp directory — `/tmp/repositories` on Linux,
  `%TEMP%\repositories` on Windows (`os.TempDir()`). Each cached repository
  lives in its own subdirectory of the root.
- **Repository directory names.** A repository's directory is named
  `<unix-epoch-seconds>-<counter>` (e.g. `1761024000-0`, `1761024000-1`) —
  the Unix epoch timestamp of when it was created, plus a process-local
  incrementing counter that disambiguates repositories created within the same
  second. Digits and a hyphen are safe on both Windows and Linux filesystems,
  and the name sorts by creation time.
- **The index file.** A simple text file at the cache root records the cache's
  contents: one line per cached repository — the repository directory, the
  repository URL, the last-accessed Unix epoch timestamp, and the last-fetched
  Unix epoch timestamp (tab-separated:
  `<dir>\t<url>\t<last-accessed-epoch>\t<last-fetched-epoch>`). The index is the
  authoritative map of which directory holds which repository, and it is updated
  **atomically**: every change rewrites the whole file to a temp file in the
  same directory and renames it over the index (a rename within one volume is
  atomic on both Windows and Linux). A process-wide lock serializes index
  mutations within a process; across replicas the atomic rewrite plus the
  per-repository lock (F-21.2.3.3) keep the shared index consistent.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The cache is a directory tree with a single authoritative text index.**
  The fetcher keeps checked-out repositories under a process-level cache root
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, default the `repositories` directory
  under the OS temp directory). Each repository's directory is named
  `<unix-epoch>-<counter>` (portable across Windows and Linux, sortable by
  creation time); a text index file at the root maps each repository URL to its
  directory and its last-accessed and last-fetched Unix epoch timestamps and is
  rewritten atomically (temp file + rename) on every change. The index is the
  cache's authoritative map and the shared coordination point across replicas.
- **New fields / RPCs / endpoints (this sub-feature).** The cache structure in
  `internal/services/pipelinesource` (cache root + per-repository directory
  naming + the atomic text index); and `CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`
  (default `<os.TempDir()>/repositories`) in `internal/config`.
