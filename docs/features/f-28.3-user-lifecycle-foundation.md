# F-28.3 · User lifecycle foundations (soft delete)

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** Give the IdP's user directory (F-24) a full lifecycle: an explicit
`active` flag, a soft-delete tombstone, a corporate external ID, and a
provenance marker — and convert every “delete user” path (the Database
service's `DeleteIDPUser`, the admin `DELETE /api/users`) into a tombstone
rather than a physical row removal. Establishes the four-state model the SCIM
operations manipulate: **active**, **deactivated** (`active=false`, “on
leave”), **deprovisioned** (tombstoned, “gone”), and **re-provisioned**
(tombstone cleared, same stable ID, “re-hire”). Deliberately
transport-independent: none of this requires SCIM to be enabled.

**Why.** Soft delete is the core requirement of F-28. Historical actions —
audit events (F-15), approval decisions (F-13), run triggers (F-07/F-09) —
name their actor by the user's stable ID. Hard-deleting a departed employee
leaves those references dangling forever (“who deployed prod #412?” →
unknown). Tombstoning keeps every actor permanently resolvable, keeps identity
stable across depart/re-hire cycles, and makes re-hire a clean reactivation of
the same row instead of a confusing duplicate.

**States.**

| State | Row | Authenticates | Restored by |
|-------|-----|---------------|-------------|
| Active | present, `active=true`, no tombstone | yes | — |
| Deactivated | present, `active=false`, no tombstone | no | activation (SCIM `PATCH active:true` / admin) |
| Deprovisioned | present, tombstoned (`deleted_at` set), `active=false` | no | re-provisioning (SCIM `POST` with matching identity) |
| Re-provisioned | tombstone cleared, repopulated, same ID | yes (once populated) | — |

Deactivated and deprovisioned both block authentication; only deprovisioned
is hidden from ordinary listings.

**Scope.**
- `internal/models` — `IDPUser` gains: `Active` (bool, default `true`),
  `DeletedAt` (`*time.Time` tombstone marker; the entity deliberately does
  not embed `gorm.Model`, so the marker is explicit and indexed), `ExternalID`
  (string; the corporate directory's stable identifier, e.g. the Azure object
  ID; indexed), and `Provisioned` (bool; externally-sourced record — SCIM or
  JIT — vs. locally registered). Picked up by `All()` / `AutoMigrate`;
  existing rows migrate as `active=true`, no tombstone, locally-sourced.
- `proto/cdrom/db/v1/db.proto` + `internal/services/database` — the `IDPUser`
  message carries `active`, `deleted_at`, `external_id`, `provisioned`;
  `DeleteIDPUser` becomes a **soft delete** (sets the tombstone, flips
  `active=false`, zeroes the password hash so leftover credentials cannot
  revive the record); a new `ReactivateIDPUser` (clears the tombstone, sets
  `active=true`, zeroes the password hash, preserves the ID and all history);
  `ListIDPUsers` gains an `include_deleted` flag (regular listings exclude
  tombstoned rows; audit/tooling opts in).
- `internal/idp` — the `UserStore` interface gains `Activate` / `Deactivate` /
  `SoftDelete` / `Reactivate`, and `List` takes an `includeDeleted` option;
  the `User` struct mirrors the new fields; the DB-backed and in-memory
  implementations honour them. The IdP's gRPC user-management RPCs (the F-24
  surface) propagate the new fields and the soft-delete semantics.
- **Sign-in enforcement** — the F-24 login path rejects deactivated and
  deprovisioned users (distinct error messages). Already-issued tokens stay
  valid until their own expiry (mid-life revocation follows the existing
  token-validation path; noted as a limitation, unchanged here).
- `internal/api` — `DELETE /api/users` becomes a soft delete (identical
  tombstone semantics to SCIM `DELETE`); `GET /api/users` omits tombstoned
  users by default and offers an admin-only `include_deleted` view showing
  all four states.
- **Registration reservation** — `POST /api/register` with a tombstoned email
  is refused (conflict): the identity is reserved for restoration via
  reactivation, preventing accidental shadow duplicates.
- F-15 audit — actor-resolution joins tolerate tombstoned users (lookup
  includes deleted rows), so “who did this” stays answerable indefinitely.

**Design decisions.**
- **Soft delete is the only delete** in the normal lifecycle. Erasure-grade
  hard delete, if ever mandated (privacy regulation), is a separate,
  explicit, admin-only operation outside this feature (zeroing credentials
  the way F-26 does for service accounts).
- **Credentials are zeroed on tombstone**: the password hash is destroyed at
  deprovision, so a revived record is only usable once its rightful source
  (SCIM re-population or an admin password reset) reinstates one.
- **The stable ID is sacrosanct**: reactivation reuses the row and its
  numeric ID (the token subject), never allocates a new one.
- **Provenance drives downstream restrictions**: F-28.4 uses `Provisioned` to
  refuse manual identity edits on SCIM-managed users.

**Acceptance criteria.**
- [ ] `IDPUser` migrates cleanly: existing rows gain `active=true`, no
      tombstone, empty external ID, `provisioned=false`.
- [ ] `DeleteIDPUser` tombstones (row retained, `deleted_at` set,
      `active=false`, password hash zeroed); the user can no longer
      authenticate.
- [ ] `ReactivateIDPUser` clears the tombstone and restores eligibility; the
      user's ID is unchanged; prior audit/approval/trigger references still
      resolve.
- [ ] A deactivated user (`active=false`, no tombstone) cannot authenticate;
      activating restores authentication.
- [ ] Regular `ListIDPUsers` excludes tombstoned rows; `include_deleted`
      returns them flagged.
- [ ] Admin `DELETE /api/users` has identical tombstone semantics;
      `GET /api/users` (admin, `include_deleted`) shows the
      active/deactivated/deprovisioned states.
- [ ] Registering with a tombstoned email is refused rather than duplicated.
- [ ] Past actions by a deprovisioned user remain attributable (name/email
      resolvable) in the audit trail (F-15).
- [ ] Integration tests walk the full state-transition graph (SQLite via
      `database.Open`).
