# F-28.3 · User lifecycle foundations (soft delete)

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** Give the IdP's user directory (F-24) a full lifecycle: an explicit
`active` flag, a soft-delete tombstone, a corporate external ID, and a
provenance marker — and convert every “delete user” path (the Database
service's `DeleteIDPUser`, the admin `DELETE /api/users`) into a tombstone
rather than a physical row removal. Establishes the four-state model the SCIM
operations manipulate: **active**, **deactivated** (`active=false`, “on
leave”), **deprovisioned** (tombstoned, “gone”), and **re-provisioned**
(tombstone cleared, same stable ID, “re-hire”). Deliberately
transport-independent: none of this requires SCIM to be enabled. Two
authentication-authority rules are pinned here as well, because the SCIM
steady state depends on them: **provenance-driven channel lockdown** (a
provisioned user signs in via SSO only) and **break-glass administration**
(an ephemeral, random-identity local-admin escape hatch when SSO/SCIM is
lost).

**Why.** Soft delete is the core requirement of F-28. Historical actions —
audit events (F-15), approval decisions (F-13), run triggers (F-07/F-09) —
name their actor by the user's stable ID. Hard-deleting a departed employee
leaves those references dangling forever (“who deployed prod #412?” →
unknown). Tombstoning keeps every actor permanently resolvable, keeps identity
stable across depart/re-hire cycles, and makes re-hire a clean reactivation of
the same row instead of a confusing duplicate.

**States.**

| State | Row | Authenticates | Restored by |
|-------|-----|---------------|-------------|
| Active | present, `active=true`, no tombstone | yes | — |
| Deactivated | present, `active=false`, no tombstone | no | activation (SCIM `PATCH active:true` / admin) |
| Deprovisioned | present, tombstoned (`deleted_at` set), `active=false` | no | re-provisioning (SCIM `POST` with matching identity) |
| Re-provisioned | tombstone cleared, repopulated, same ID | yes (once populated) | — |

Deactivated and deprovisioned both block authentication; only deprovisioned
is hidden from ordinary listings.

**Slices.** Built as three sequential increments, each ending compiled,
tested, and demonstrable (checkpoint commit per slice):

- **Slice 1 — Lifecycle foundation (model + store semantics).** The passive
  model deltas: `IDPUser` gains `Active`, `DeletedAt`, `ExternalID`,
  `Provisioned`, and the temporal-credential pair
  (`TemporaryPasswordHash` / `TemporaryPasswordValidUntil`), picked up by
  `All()` / `AutoMigrate` (existing rows migrate as active, locally-sourced,
  no tombstone, no temporal credential). Proto/message propagation;
  `DeleteIDPUser` becomes a tombstone (retains the row, flips
  `active=false`, zeroes the hash); the new `ReactivateIDPUser`;
  `ListIDPUsers.include_deleted`; `UserStore.Activate / Deactivate /
  SoftDelete / Reactivate` + `List(includeDeleted)` honoured by the
  DB-backed and in-memory implementations. No behavioural change yet —
  nothing consumes the new state. Demonstrable: integration tests walk the
  full state-transition graph against SQLite.
- **Slice 2 — Enforcement (sign-in + admin surface).** The behavioural
  changes: the login path rejects deactivated, deprovisioned, and
  `provisioned=true` users with distinct errors (teeth 2–3 of the channel
  lockdown); the admin write side refuses to attach a password to a
  provisioned user (Conflict); registration reservation (tombstoned email →
  409); `DELETE /api/users` adopts tombstone semantics; `GET /api/users`
  gains the admin `include_deleted` view of all four states; audit
  actor-resolution tolerates tombstoned rows. Demonstrable: a curl
  walkthrough — register → deactivate → login refused → delete →
  tombstone-refused + `include_deleted` listing → register-reservation
  conflict.
- **Slice 3 — Break-glass (endpoint + temporal credential + hygiene).** The
  IdP HTTP listener upgrades to `OptionalClientCert` with per-route
  peer-chain verification; `POST /emergency/break-glass` coins a
  random-identity admin with a request-TTL-bound temporal password
  (response `{email, password, expires_at}`, plaintext exactly once);
  the login path honours the temporal window; the Database-service
  candidate-query backing the live-pool cap (429 beyond it); the hygiene
  sweep deactivates expired users and zeroes their temporal hash; the
  toggle, uniform denials, and certificate-attributed audit. Demonstrable:
  mTLS curl → sign in via `/api/login` → expiry refusal → sweep effect →
  cap 429 → audit line carrying the peer CN.

Dependency: S1 → S2 → S3 strictly; S1's fields sit dormant until S2/S3
consume them (mirror of F-28.2's S1).

**Scope.**
- `internal/models` — `IDPUser` gains: `Active` (bool, default `true`),
  `DeletedAt` (`*time.Time` tombstone marker; the entity deliberately does
  not embed `gorm.Model`, so the marker is explicit and indexed), `ExternalID`
  (string; the corporate directory's stable identifier, e.g. the Azure object
  ID; indexed), `Provisioned` (bool; externally-sourced record — SCIM or
  JIT — vs. locally registered), and the break-glass temporal-credential
  pair `TemporaryPasswordHash` (text; Argon2ID encoding of a short-lived
  password) + `TemporaryPasswordValidUntil` (*time.Time; nil = none) — the
  login path accepts the temporal password only inside its window. Picked up
  by `All()` / `AutoMigrate`; existing rows migrate as `active=true`, no
  tombstone, locally-sourced, no temporal credential.
- `proto/cdrom/db/v1/db.proto` + `internal/services/database` — the `IDPUser`
  message carries `active`, `deleted_at`, `external_id`, `provisioned`;
  `DeleteIDPUser` becomes a **soft delete** (sets the tombstone, flips
  `active=false`, zeroes the password hash so leftover credentials cannot
  revive the record); a new `ReactivateIDPUser` (clears the tombstone, sets
  `active=true`, zeroes the password hash, preserves the ID and all history);
  `ListIDPUsers` gains an `include_deleted` flag (regular listings exclude
  tombstoned rows; audit/tooling opts in).
- `internal/idp` — the `UserStore` interface gains `Activate` / `Deactivate` /
  `SoftDelete` / `Reactivate`, and `List` takes an `includeDeleted` option;
  the `User` struct mirrors the new fields; the DB-backed and in-memory
  implementations honour them. The IdP's gRPC user-management RPCs (the F-24
  surface) propagate the new fields and the soft-delete semantics.
- **Sign-in enforcement** — the F-24 login path rejects deactivated and
  deprovisioned users (distinct error messages), and rejects
  `provisioned=true` users on the password channel outright (checked before
  any hash compare; distinct “managed by the identity provider — sign in
  via SSO” error; see Auth channels). Already-issued tokens stay
  valid until their own expiry (mid-life revocation follows the existing
  token-validation path; noted as a limitation, unchanged here).
- **Channel lockdown (write side)** — no write path may attach a password to
  a `provisioned=true` user: the admin `UpdateUser` password field is
  refused (Conflict); SCIM `PUT`/`PATCH` cannot express it (RFC 7643 carries
  no password attribute). Combined with the login refusal, the password
  channel is closed at both doors.
- **Break-glass administration** — `POST /emergency/break-glass` on the
  IdP's HTTP listener, guarded by a CA-signed client certificate (per-route
  mTLS check, curl-native): each call COINS a new ephemeral local admin —
  randomized `breakglass-…@invalid` login, `provisioned=false`, `admin`
  role, request-TTL-bound Argon2ID password (default 24 h) returned exactly
  once. Strictly additive: it never modifies any existing user. Gated by
  `idp.break_glass_enabled` (default true), capped on live accounts, and
  audited with the caller's certificate attributed on every call. See
  Break-glass administration.
- `internal/api` — `DELETE /api/users` becomes a soft delete (identical
  tombstone semantics to SCIM `DELETE`); `GET /api/users` omits tombstoned
  users by default and offers an admin-only `include_deleted` view showing
  all four states.
- **Registration reservation** — `POST /api/register` with a tombstoned email
  is refused (conflict): the identity is reserved for restoration via
  reactivation, preventing accidental shadow duplicates.
- F-15 audit — actor-resolution joins tolerate tombstoned users (lookup
  includes deleted rows), so “who did this” stays answerable indefinitely.

**Design decisions.**
- **Soft delete is the only delete** in the normal lifecycle. Erasure-grade
  hard delete, if ever mandated (privacy regulation), is a separate,
  explicit, admin-only operation outside this feature (zeroing credentials
  the way F-26 does for service accounts).
- **Credentials are zeroed on tombstone**: the password hash is destroyed at
  deprovision, so a revived record is only usable once its rightful source
  (SCIM re-population or an admin password reset) reinstates one.
- **The stable ID is sacrosanct**: reactivation reuses the row and its
  numeric ID (the token subject), never allocates a new one.
- **Provenance drives downstream restrictions**: F-28.4 uses `Provisioned` to
  refuse manual identity edits on SCIM-managed users.
- **Auth channels are locked by provenance** (normative rule in Auth
  channels): `provisioned=true` ⇒ SSO/OIDC only; the password channel is
  closed at login *and* at every password write. Granting a local password
  to a directory-established user would fork identity authority and quietly
  undo the sole-source invariant.
- **The escape hatch is itself ephemeral and additive** (Break-glass
  administration): when SSO/SCIM is lost, an operator presents the API's
  mTLS client certificate to the IdP's HTTP endpoint (stock tools such as
  curl) and receives a throwaway random-identity admin whose password
  self-expires (request TTL, default 24 h). It never touches any existing
  user — nothing to corrupt, only something temporary to hold until the
  repair lands.

**Auth channels (provenance lockdown).** A user’s interactive channels are
a function of their provenance:

- `provisioned=false` (locally registered, F-24) — the password channel is
  theirs; nothing here changes F-24 behaviour.
- `provisioned=true` (arrived by SCIM push or JIT on first OIDC login) —
  **SSO/OIDC only**, enforced with three teeth:
  1. **Arrival without a password.** The SCIM mapping has no password
     attribute, and tombstone reactivation zeroes the hash (above): a
     provisioned user structurally holds no credential for the password
     channel.
  2. **Write side closed.** Administrative attachment of a password is
     refused (admin `UpdateUser` → Conflict; SCIM has no password attribute
     to express one).
  3. **Login side closed.** The F-24 `Login` path rejects
     `provisioned=true` before comparing any hash, with a distinct error
     directing the user to SSO — so a hash smuggled in by legacy state or
     defect can never reopen the door despite teeth 1–2.

Rationale: a user established by the corporate directory owes their
legitimacy to it; a working local password would fork identity authority
(two masters of one identity) and quietly void the sole-source invariant.
Delegated machine credentials are out of scope for the rule: F-25 user API
keys (voluntary, audited admin grants) and F-26 service accounts (separate
principals entirely) remain issuable for provisioned users. Migration
implication: a pre-existing local (password) user that SCIM later encounters
is *not* absorbed (F-28.4’s conflict matrix returns the record unchanged);
moving such a user to SSO-only is an explicit, audited admin act, never
implicit.

**Break-glass administration.** The F-28 steady state puts user authority in
the corporate IdP. A prolonged SSO outage, SCIM damage that deprovisions
every admin, or a claim-mapping regression that strips the admin role can
leave the deployment with zero authenticated humans — and F-14 denies
non-admins the ability to grant admin. The existing relief, `POST
/api/register` (unauthenticated; first user → admin), evaporates once the
directory is non-empty. Hence a dedicated escape hatch that is itself
ephemeral and strictly additive:

- **Transport: HTTP + mTLS on the IdP, not gRPC.** `POST
  /emergency/break-glass` on the IdP's existing HTTP listener (beside the
  OIDC surface, default :7104). Chosen over the gRPC-via-API variant for
  two reasons: (1) stock tools drive the drill — `curl --cacert ca.crt
  --cert client.crt --key client.key https://idp:7104/emergency/
  break-glass` — no grpcurl, gateway, or generated stubs required; (2) it
  avoids extending the API's bearer-exempt list and keeps working if the
  API itself is impaired. Implementation note: the listener moves from
  server-cert-only to `OptionalClientCert` (handshake-transparent to
  browsers — certificate requested, not demanded) with a per-route
  peer-chain verification on this route alone. Only the API holds a
  CA-signed client certificate today, so the operator fishes it from the
  API workload (pod exec / mounted secret). Calls without a valid peer
  certificate receive a uniform 403.
- **Fresh identity every time — never modifies existing users.** Each call
  inserts a brand-new user; the algorithm has no lookup-or-update and no
  converge/reactivate branch, so no existing row is ever touched. The login
  name is randomized: `breakglass-<16 chars from [0-9a-z]>@invalid`
  (reserved TLD, unroutable; ~75 bits of entropy). Draw, insert; on the
  practically impossible unique violation, redraw (bounded retries) —
  failing closed rather than touching somebody else's row.
- **Temporal credential.** The new user (`provisioned=false`,
  `active=true`, roles `[admin]`) receives a cryptographic-random
  Argon2ID password stored as a **temporal** password — new `IDPUser`
  columns `temporary_password_hash` / `temporary_password_valid_until`; the
  permanent hash stays empty. The TTL rides the request body
  (`ttl_seconds`, optional): unset means `break_glass_default_ttl` (default
  **24 h**), clamped to `break_glass_max_ttl` (default **7 days**) (config
  `idp.break_glass_default_ttl` / `idp.break_glass_max_ttl`, env
  `CDROM_IDP_BREAK_GLASS_*`); the response echoes `email`, `password`,
  `expires_at`. The login path accepts the temporal password only inside
  its window; past expiry it is unusable (evaluated constant-time
  regardless).
- **Sweep + anti-spam cap.** The IdP's periodic hygiene sweep deactivates
  expired break-glass users and zeroes their temporal hash — symmetric with
  “soft delete is the only delete” (row kept, credential voided; accrual is
  incident-frequency and benign). A bounded pool of live (unexpired)
  break-glass admins (default **3**, borrowing the F-28.2 key-pool shape)
  refuses further coinage with 429 until some expire — throttling
  admin-row spray.
- **Hygiene + attribution.** The plaintext password is returned **exactly
  once** (`Cache-Control: no-store`); never logged, never audited (house
  rule shared with F-25/F-26/F-28.2: record the event, not the secret).
  mTLS earns what the bearer-exempt variant could not: the caller's
  certificate is attributed — F-15 event actor `break-glass(<peer-cn>)`
  plus a conspicuous WARN log on every invocation.
- **Toggle + honest trust posture.** `idp.break_glass_enabled` (default
  **true**; `CDROM_IDP_BREAK_GLASS_ENABLED`); when off the route answers
  with the same uniform 403 (no state advertised). The risk is stated
  plainly: whoever holds the API's client certificate can coin ephemeral
  platform admins — equivalent to possessing the API's TLS secret /
  node-access tier. Compensation: short TTL, small live-pool cap, full
  audit with certificate attribution, and the private-network assumption.
  Further tightening (second static phrase, source allowlists) is
  deliberately out of scope.
- **Drill.** Fetch the API's client certificate (from the API workload) →
  `curl POST /emergency/break-glass` (optionally with `ttl_seconds`) → copy
  the once-shown `email` + `password` → sign in via `POST /api/login` →
  repair SSO / claim mapping / SCIM. No rotation step: the credential
  self-destructs at expiry; extended access means a fresh invocation that
  supersedes the older one.

**Acceptance criteria.** Tagged by delivering slice (S1 = lifecycle
foundation, S2 = enforcement, S3 = break-glass).

*S1 — lifecycle foundation* (passive deltas; no behavioural change yet).
- [ ] `IDPUser` migrates cleanly: existing rows gain `active=true`, no
      tombstone, empty external ID, `provisioned=false`, no temporal
      credential.
- [ ] `DeleteIDPUser` tombstones (row retained, `deleted_at` set,
      `active=false`, password hash zeroed).
- [ ] `ReactivateIDPUser` clears the tombstone and restores eligibility; the
      user's ID is unchanged; prior audit/approval/trigger references still
      resolve.
- [ ] Regular `ListIDPUsers` excludes tombstoned rows; `include_deleted`
      returns them flagged.
- [ ] Integration tests walk the full state-transition graph (SQLite via
      `database.Open`).

*S2 — enforcement* (behavioural changes to sign-in and the admin surface).
- [ ] A deactivated user (`active=false`, no tombstone) cannot authenticate;
      activating restores authentication.
- [ ] A deprovisioned user cannot authenticate (distinct error from the
      deactivated refusal).
- [ ] A `provisioned=true` user cannot authenticate via the password
      channel: `Login` rejects them distinctly before hash comparison, and
      no admin write path can set their password (both directions tested).
- [ ] Admin `DELETE /api/users` has identical tombstone semantics;
      `GET /api/users` (admin, `include_deleted`) shows the
      active/deactivated/deprovisioned states.
- [ ] Registering with a tombstoned email is refused rather than duplicated.
- [ ] Past actions by a deprovisioned user remain attributable (name/email
      resolvable) in the audit trail (F-15).

*S3 — break-glass* (endpoint, temporal credential, hygiene).
- [ ] `POST /emergency/break-glass` with a CA-signed client certificate
      succeeds with zero authenticated humans: coins a new random-identity
      admin, modifies no other row (directory diff asserted), returns the
      once-only password plus `expires_at`; the credentials sign in via
      `POST /api/login`.
- [ ] Invocations are strictly additive and ephemeral: a second call coins
      a different user (no merge, no revival); the password is dead at
      `expires_at`; the sweep deactivates expired users; the live-pool cap
      refuses spray (429).
- [ ] Every invocation writes an F-15 audit event attributing the caller's
      certificate leaf (plus a WARN log); the password appears in neither.
- [ ] Calls without a valid client certificate, and calls while disabled,
      receive the same uniform denial (no state disclosed).
- [ ] Break-glass users are `provisioned=false` (ordinary admin API can
      clean them up) and structurally outside SCIM governance (random
      reserved-TLD email).
