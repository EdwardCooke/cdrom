# F-21.5.2 · The sync routine

> Part of [F-21.5 · Externally-sourced pipelines](f-21.5-externally-sourced-pipelines.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The single **sync routine** that every refresh trigger (F-21.5.3)
goes through: the API dials the source-fetcher (F-21.2) to pull the source's
definition file — selecting and decrypting the source's credential (F-21.3) and
handing the plaintext to the fetcher for that one fetch — compares the returned
content hash to the stored `source_hash`, and **re-imports on change**
(recompile via F-21.1, version bump F-11) or **no-ops when unchanged**. A sync
is serialized per pipeline so concurrent triggers cannot double-apply a change.

**Depends on.** [F-21.1](f-21.1-file-format-compiler.md) (the compiler that
re-imports a changed file), [F-21.2](f-21.2-source-fetcher.md) (the fetcher),
[F-21.3](f-21.3-source-credentials.md) (the credential the API decrypts and
hands to the fetcher), and
[F-21.5.1](f-21.5.1-source-model-storage.md) (the source model + stored hash).

**Why.** One routine (fetch → hash → compare → recompile if changed) means the
three triggers are behaviorally identical — only the trigger differs — and the
hash comparison makes refresh cheap and idempotent: a sync that finds no change
is free, and a run-kickoff refresh that finds no change does not perturb an
in-flight pipeline.

**Scope.**
- `internal/api` — the **sync routine**: select the credential (an explicit
  `credential` name on the source, else the longest matching `pattern`,
  F-21.3) → decrypt it (F-12) → dial the source-fetcher (F-21.2; mutual TLS
  when a TLS CA is configured, plaintext without one) → compare the returned
  hash to the stored `source_hash` → on **change**: recompile (F-21.1) +
  re-import (create or update, bumping the pipeline's version, F-11) + store
  the new `source_file` / `source_hash` and the source state's
  `last_version`; on **no change**: update only `last_synced_at`.
- Per-pipeline serialization (a source is not synced concurrently by two
  triggers).
- Failure handling: a sync failure (an unreachable source, a missing file, a
  credential that fails to authenticate) is recorded on the source state's
  `last_error` (cleared on the next success) and surfaced to the UI; the
  plaintext credential is never persisted or logged.

**Acceptance criteria.**
- [ ] A change in the source (detected by a changed content hash) re-imports the
      pipeline (bumping its version, F-11) and stores the new `source_file` /
      `source_hash` and the source state's `last_version`; a run started after
      the change uses the new definition.
- [ ] An unchanged file (hash matches) is a no-op: no recompile, no version
      bump, no re-dispatch — only `last_synced_at` is updated.
- [ ] The actual fetch (git / HTTP / filesystem) is performed by the separate
      source-fetcher process (F-21.2), which the API dials over gRPC; with a TLS
      CA configured the connection uses mutual TLS, and without one it falls
      back to plaintext (local dev) — the same convention as the other services.
- [ ] The source-fetcher holds no definitions, credentials, or encryption key at
      rest: the API selects the source's credential (an explicit `credential`
      name, else the longest matching `pattern`, F-21.3), decrypts it (F-12),
      and passes the plaintext to the fetcher for a single fetch, which is never
      persisted or logged.
- [ ] A sync is serialized per pipeline (a source is not synced concurrently by
      two triggers), so a scheduled tick and a run-kickoff refresh racing cannot
      double-apply a change.
- [ ] A sync failure (an unreachable source, a missing file, a credential that
      fails to authenticate — a rotated token, a revoked key) is recorded on the
      source state's `last_error` (cleared on the next success) and surfaced to
      the UI, so a stale credential or a dead source is diagnosable without a
      repo checkout.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Refresh is one routine.** A single sync routine (fetch via the
  source-fetcher → hash → compare → recompile if changed) is shared by all three
  triggers (F-21.5.3), so they are behaviorally identical; only the trigger
  differs. The hash is the change detector: a sync that yields the same hash is
  a no-op (no recompile, no version bump); a changed hash re-imports and bumps
  the version (F-11).
- **The fetch is delegated, the credential is transient.** The API dials the
  source-fetcher (F-21.2) over gRPC (mutual TLS when a CA is configured,
  plaintext otherwise) and hands it the source's credential — decrypted for that
  single fetch — which the stateless fetcher uses to authenticate and then
  discards; it is never persisted or logged. A sync is serialized per pipeline
  so the triggers cannot race.
- **New fields / RPCs / endpoints (this sub-feature).** The sync routine in
  `internal/api` (credential selection + decryption, the fetcher dial, the hash
  compare, the recompile + re-import on change, the per-pipeline serialization,
  and the `last_error` recording); `SyncPipelineSource` /
  `RefreshPipelineSource` RPCs (db).
