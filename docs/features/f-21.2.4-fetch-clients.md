# F-21.2.4 · Fetch clients (git / http / file)

> Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature is the fetcher's three **fetch clients** — one per reference
kind (F-21.2.2) — that retrieve a single file and produce the `FetchSource`
response (content, version identifier, content hash). The **`git`** client
reads a file from a repository served by the on-disk cache (F-21.2.3); the
**`http`** client does a GET of an endpoint; the **`file`** client reads a file
from the fetcher's host, resolved against a configured local-filesystem root.
Each client applies the call's optional `SourceCredential` (F-21.3) when one is
needed.

**Why.** The clients are the only place the fetcher touches git, the network,
or the local filesystem, so the rest of the service (the gRPC contract,
F-21.2.1) stays thin and the fetch behavior is isolated per kind. Keeping the
`file` kind rooted in a configured directory stops the fetcher from reading
arbitrary files on its host.

## Sub-features

F-21.2.4 is decomposed into one sub-feature per fetcher, each with its own spec
file. This file is the **overview**; the sub-features below hold the detailed
scope, acceptance criteria, and design decisions for each client.

| Sub-feature | Spec | Scope | Depends on |
|-------------|------|-------|------------|
| **F-21.2.4.1** Git fetch client | [f-21.2.4.1](f-21.2.4.1-git-fetch-client.md) | The `git` client — read a file at a branch ref from a repository served by the cache (F-21.2.3), apply a `git-ssh`/`git-https` credential, return the commit hash | F-21.2.2, F-21.2.3 |
| **F-21.2.4.2** HTTP fetch client | [f-21.2.4.2](f-21.2.4.2-http-fetch-client.md) | The `http` client — a GET of the endpoint, request headers from the `http` credential (optional), return the `ETag`/`Last-Modified` | F-21.2.2 |

**Suggested build order:** the three clients are independent of each other and
can be built in parallel once the reference parser (F-21.2.2) exists; the
`git` client additionally needs the cache (F-21.2.3).

**Depends on.** [F-21.2.2](f-21.2.2-reference-format.md) (the reference each
client parses), [F-21.2.3](f-21.2.3-git-repository-cache.md) (the cache the
`git` client serves from), and [F-21.3](f-21.3-source-credentials.md) (the
credential the API decrypts and hands to the client for a fetch of a private
source).

**Scope.**
- The **`git`** client — read a single file at a branch ref from a repository
  served by the cache (F-21.2.3); authenticate a private repository with a
  `git-ssh` or `git-https` credential; return the branch's commit hash as the
  version identifier.
- The **`http`** client — a GET of the endpoint; request headers come from the
  source's `http` credential (a `token` sent in a configurable `header`,
  default `Authorization: Bearer <token>`); return the `ETag`/`Last-Modified`
  as the version identifier.
- The **`file`** client — read a file from `<root><path>` where `<root>` is the
  configured local-filesystem root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`); the
  resolved path must stay within the root; return the file's mtime as the
  version identifier. The kind is **disabled** when no root is configured.
- `internal/config` — `CDROM_PIPELINE_SOURCE_FILE_ROOT` (unset = the `file`
  kind disabled).

**Acceptance criteria.**
- [ ] A file can be fetched from a **git** repository (F-21.2.4.1), an
      **HTTP/HTTPS** endpoint (F-21.2.4.2), or a file on the **local
      filesystem** (F-21.2.4.3), each named by a reference (F-21.2.2).
- [ ] The **`git`** client reads the file from the repository served by the
      cache (F-21.2.3) and returns the branch's commit hash as the version
      identifier; a private repository is authenticated by a `git-ssh` or
      `git-https` credential (F-21.3).
- [ ] The **`http`** client does a GET and uses the response body as the file;
      request headers are supplied by the source's `http` credential (F-21.3) —
      a credential is **optional**. It returns the `ETag`/`Last-Modified` as
      the version identifier.
- [ ] The **`file`** client reads the file directly from `<root><path>` (no
      network, no cache) and returns the file's mtime as the version
      identifier; a `file:` reference is resolved against
      `CDROM_PIPELINE_SOURCE_FILE_ROOT` and the kind is **disabled** when no
      root is configured.
- [ ] Each client returns the file's **content** and its **content hash**
      (SHA-256 of the content) alongside the kind's version identifier.

## The three source kinds

`FetchSource` (F-21.2.1) parses the reference (F-21.2.2) and performs one of
three fetches, each by a dedicated client:

- **`git`** (F-21.2.4.1) — the reference names the repository, the branch ref,
  and the path of the definition file within the repo. The fetcher serves the
  repository from its **on-disk cache** (F-21.2.3): a cached checkout is
  refetched from upstream (subject to the debounce), or a repository with no
  cache entry is cloned into a new cache directory. It reads the file at `path`
  and returns the branch's commit hash as the version identifier. A private
  repository is authenticated by a `git-ssh` or `git-https` credential (F-21.3)
  passed in for the call; a public repository needs no credential.
- **`http`** (F-21.2.4.2) — the reference is the endpoint that serves the
  definition file (e.g. an object-store URL or a raw-file endpoint). The
  fetcher does a GET and uses the response body as the file. Request headers
  are supplied by the source's `http` credential (F-21.3 — a `token` sent in a
  configurable `header`, default `Authorization: Bearer <token>`); there are no
  in-band headers on the reference, and a credential is **optional** — an
  endpoint that needs no authentication is fetched with a plain GET. It returns
  the `ETag`/`Last-Modified` as the version identifier.
- **`file`** (F-21.2.4.3) — the reference is a path resolved against the
  fetcher's configured local-filesystem root
  (`CDROM_PIPELINE_SOURCE_FILE_ROOT`): the file is read directly from
  `<root><path>`; no network is involved and the file is not cached. This is
  the kind for a definition that is mounted into the fetcher's pod (e.g. a
  ConfigMap or a volume) and is "pulled" by re-reading the file. It returns the
  file's mtime as the version identifier. When no root is configured the kind
  is disabled and a `file:` fetch fails with a clear error.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **One client per kind.** The fetcher's git / HTTP / filesystem clients each
  retrieve a single file named by a reference (F-21.2.2) and produce the
  `FetchSource` response (content, version identifier, content hash). The
  `git` client reads from the cache (F-21.2.3); the `http` client does a GET;
  the `file` client reads a rooted local path.
- **`file:` references are rooted.** A `file:` reference is resolved against a
  configured local-filesystem root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`), so the
  fetcher can read only files under that root — never an arbitrary path on its
  host. With no root configured the `file` kind is disabled.
- **HTTP headers come from the credential store.** An `http` fetch's request
  headers are supplied by the source's `http` credential (F-21.3), not in-band
  on the reference — so a credential is optional (a public endpoint is fetched
  with a plain GET).
- **New fields / RPCs / endpoints (this sub-feature).** The fetcher's git /
  HTTP / filesystem clients in `internal/services/pipelinesource` (a single
  file at a ref / URL / rooted path, authenticated by a `SourceCredential`
  passed in for that one call when one is needed); and
  `CDROM_PIPELINE_SOURCE_FILE_ROOT` (unset = the `file` kind disabled) in
  `internal/config`.
