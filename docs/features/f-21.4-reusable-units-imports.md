# F-21.4 · Reusable units & cross-file imports

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature adds **cross-file imports** and **step reuse across
environments** on top of the single-file format and compiler from F-21.1.
Reusable units — sets of variables, steps, or entire jobs — are pulled in from
other files with **explicit fields** (`importFrom` on a step or job, `import` on
a variable set), and steps are **reused** across environments: shared steps live
under `spec.steps` and each environment's job references them by name (`ref`),
so environments differ only in their variables and a few local steps.

**What.** The compiler (F-21.1) is extended to resolve **imports**: a step, a
job's steps, a whole job, or a variable set can be pulled in from another file
(via the source-fetcher, F-21.2). A referenced file is itself a Kubernetes-style
manifest whose `kind` (`Step` / `VariableSet` / `Job`) tells the compiler how to
read it — each file holds exactly one unit, and its `spec` is that unit's
definition. The compiler fetches each referenced file, splices the unit in
place (or merges a variable set's variables), and validates it as if it were
inline.

**Why.** Teams keep a `shared/` directory of step, variable set, and job
definitions that many pipelines pull in, and keep each environment's pipeline
file small. Because steps are named and shared, "deploy to dev/staging/prod" is
shared steps plus per-environment jobs (differing only by variable sets and a
few local steps) and a `needs` chain — not copied jobs.

**Depends on.** [F-21.1](f-21.1-file-format-compiler.md) (the file format +
compiler) and [F-21.2](f-21.2-source-fetcher.md) (the fetcher that retrieves
referenced files).

**Scope.**
- `internal/pipelinefile` — import resolution: `importFrom` (on a step, a job's
  `steps`, or a job) and `import` (on a variable set, from external files or
  vaults), splicing the fetched unit in place and validating it as if inline;
  the `Step` / `VariableSet` / `Job` file kinds (a file's `kind` tells the
  compiler how to read it).
- The compiler's import rules: a unit name is unique across the merged
  namespace (the file's own units plus all imported units); imports may be
  transitive; a cycle of imports is a validation error; a `ref` / `variableSets`
  entry must name a unit that is defined (inline, shared, or imported).
- Step reuse across environments: shared steps under `spec.steps` referenced by
  a job with `ref` (an empty entry is shorthand for `ref: <same name>`); each
  environment is a distinct job (unique name) that reuses the shared steps and
  differs only by its variable sets and a few job-local steps.

**Acceptance criteria.**
- [ ] A pipeline can pull in sets of variables, steps, or entire jobs from other
      files with explicit fields (`importFrom` on a step or job, `import` on a
      variable set); an imported unit is spliced in place and validated as if it
      were inline.
- [ ] A referenced file is a Kubernetes-style manifest whose `kind`
      (`Step` / `VariableSet` / `Job`) tells the compiler how to read it; each
      file holds exactly one unit, and its `spec` is that unit's definition
      (shaped exactly like one entry in the pipeline's corresponding section);
      the file's `metadata` is ignored (a file contributes a reusable unit, not
      a competing pipeline).
- [ ] Steps can be reused across environments: shared steps under `spec.steps`
      are referenced by a job with `ref`, and each environment is a distinct job
      (unique name) that reuses the shared steps and differs only by its
      variable sets and a few job-local steps.
- [ ] A job's `steps` is a name → spec map that can be pulled in from another
      file with `importFrom`; any steps the job defines locally override the
      imported steps by name (the imported steps are the base, local steps win).
- [ ] An empty step entry in a job's `steps` map (no fields) is shorthand for
      `ref: <same name>` — it implicitly references the shared step of the same
      name; a name with no matching shared step is a validation error.
- [ ] A job can be pulled in from another file with `importFrom: <uri>`; any
      fields set on the local job override the imported job's (like a step's
      `importFrom`).
- [ ] A variable set can import a vault's values with `import: [{vault: <name>}]`
      (every key in the vault, as masked variables) or
      `import: [{vault: <name>, keys: [a, b, c]}]` (a subset of keys); a set's
      variables are the union of its inline `variables` and the imported ones
      (the inline ones win on a key collision).
- [ ] A variable set file's `spec` can carry its own `secretSources` section
      (shaped exactly like the pipeline's `spec.secretSources`, F-21.1.3); the
      set owns the secret sources its masked variables and `import` vault
      entries reference, so the set is self-contained. When the set is imported
      into a pipeline, its `secretSources` are merged into the pipeline's
      `secretSources` namespace (the pipeline's own win on a name collision).
- [ ] A unit name is unique across the merged namespace (the file's own units
      plus all imported units); a collision is a validation error.
- [ ] Imports may be transitive (an imported file may itself use `importFrom` /
      `import` to pull in others); a cycle of imports is a validation error.
- [ ] A `ref` must name a step that is defined (inline, shared, or imported) and
      a `variableSets` entry must name a variable set declared under
      `spec.variableSets`; otherwise the import fails with an actionable error
      naming the missing name.
- [ ] A locator is resolved against the pipeline's source: for a `git` source,
      relative to the file's path in the repo (the fetcher fetches the
      referenced file from the same repo/branch); for an `http` source, relative
      to the file's URL (the fetcher resolves it against the source's base URL);
      for a `filesystem` source, relative to the file's directory on the
      fetcher's host.

## The referenced files (variable set, step, job)

The files a pipeline pulls in are themselves Kubernetes-style manifests, with a
`kind` that tells the compiler how to read them. Each file holds **exactly one
unit**, and its `spec` is that unit's definition — the same shape as one entry
in the pipeline's corresponding section — so a file contributes a reusable unit
that matches what the pipeline expects:

**A variable set file** (`kind: VariableSet`) — one variable set per file; its
`spec` is the set itself, shaped exactly like an entry under the pipeline's
`spec.variableSets` (an inline `variables` map and/or `import` from files or
vaults), plus its own `secretSources` section (shaped exactly like the
pipeline's `spec.secretSources`, F-21.1.3) — the set **owns** the secret
sources its masked variables and `import` vault entries reference, so the set
is self-contained and needs no `secretSources` re-declared in every pipeline
that imports it. Importing it merges its variables into the named set in the
pipeline and its `secretSources` into the pipeline's `secretSources` namespace
(the pipeline's own win on a name collision):

```yaml
# variablesets/dev.yaml
apiVersion: cdrom/alphav1
kind: VariableSet
metadata:
  name: dev
spec:
  variables:
    region: eu-west
    replicas: "2"
  secretSources:
    prod-secrets:
      kind: Vault
      path: cdrom/dev
      audience: cdrom
  import:
    - vault: prod-secrets
      keys:
        - deploy_token
```

**A step file** (`kind: Step`) — one step per file; its `spec` is the step
definition itself, shaped exactly like an entry under the pipeline's
`spec.steps` (or a job's `steps`). The step takes its name from where the
pipeline references it (the map key), so the file does not name it:

```yaml
# steps/unit-test.yaml
apiVersion: cdrom/alphav1
kind: Step
metadata:
  name: unit-test
spec:
  shell:
    command: make
    args: ["test"]
  workdir: /src
  timeout: 5m
```

**A job file** (`kind: Job`) — one job per file; its `spec` is the job spec
itself, shaped exactly like an entry under the pipeline's `spec.jobs` (its
`steps`, `needs`, `variables`, `variableSets`, `environment`, `workerGroup`,
and deployment options):

```yaml
# jobs/deploy-dev.yaml
apiVersion: cdrom/alphav1
kind: Job
metadata:
  name: deploy-dev
spec:
  steps:
    # Empty entry: shorthand for `ref: step1` (the shared step of the same name).
    step1:
    step2:
      shell:
        command: |
          echo "deploy to dev"
  variables:
    canary: "true"
  variableSets:
    - dev
```

When a pipeline pulls one of these in (a variable set via `import`, a step via
`importFrom`, or a job via `importFrom`), the compiler splices the file's `spec`
into the pipeline's matching unit and validates it as if it were inline: a
`VariableSet` file's variables are merged into the named set that imports them,
and a `Step` / `Job` file's spec becomes the step or job the pipeline names it.
The file's `metadata` is ignored (a file contributes a reusable unit, not a
competing pipeline), and any fields the importing pipeline sets locally override
the imported file's.

## Imports and references

Reusable units are pulled in from other files with **explicit fields** (rather
than YAML tags). A field carries either a locator (a source URI or a path
relative to the current file) or a name (a reference to a unit already declared
in the file):

- **`importFrom: <uri>`** (on a step, a job's `steps`, or a job) — pull a step
  definition, a job's steps, or a whole job from another file. On a step, the
  referenced file is a `Step` manifest holding a single step spec; any settings
  present on the local step override the imported step's. On a
  job's `steps`, it pulls the steps from the referenced file as the base; any
  steps the job defines locally override the imported steps by name (the job's
  other fields — `needs`, `variables`, `variableSets`, `environment`,
  `workerGroup`, … — stay local). On a job, it pulls the whole job spec; any
  fields set on the local job override the imported job's, including its
  `steps` (a local `steps` map overrides the imported job's steps by name).
  Example:
  `unit-test: {importFrom: git://github.com/blah/blah/steps/unit-test.yaml}`.
- **`ref: <name>`** (on a step) — reference a step already defined in
  `spec.steps` (or pulled in by another step's `importFrom`) by name. When the
  step's own name matches the referenced step's, the `ref` can be omitted: an
  empty entry (`step1:`) is shorthand for `ref: step1`.
- **`import: [{from: <uri>}, {vault: <name>}, {vault: <name>, keys: […]}, …]`**
  (on a variable set) — pull one or more external files **or vaults** into a
  variable set under `spec.variableSets`. A `{from}` entry fetches a
  `VariableSet` file and merges its variables into the set; a `{vault}` entry
  imports every value in the named `secretSources` entry (as masked variables),
  and a `{vault, keys}` entry imports a subset of its keys. The set's
  variables are the union of its inline `variables` and the imported variables.
  A `{vault}` entry names a `secretSources` entry that is either the set's own
  (declared in the set file's `spec.secretSources`, which the set owns) or one
  the importing pipeline declares; when the set is imported, its
  `secretSources` are merged into the pipeline's `secretSources` namespace (the
  pipeline's own win on a name collision), so a set that declares its own
  sources is self-contained. Example:
  `dev: {import: [{from: git://…/dev.yaml}, {vault: prod-secrets}]}`.
- **`variableSets: [<name>, …]`** (on a job) — reference named variable sets
  (declared under `spec.variableSets`) to merge into the job's variables.
  Example: `variableSets: [global, dev]`.
- The same pattern extends to the other named resources: a secret source can be
  pulled in from another file with `importFrom`.

A locator is resolved against the pipeline's source, exactly like the main file:
for a `git` source, relative to the file's path in the repo (the fetcher fetches
the referenced file from the same repo/branch); for an `http` source, relative
to the file's URL (the fetcher resolves it against the source's base URL); for a
`filesystem` source, relative to the file's directory on the fetcher's host. The
source-fetcher (F-21.2) fetches each referenced file and the compiler splices
the fetched unit in place (or merges a variable set's variables into the job's
`variables`). The rules:

- A unit name is unique across the merged namespace (the file's own units plus
  all imported units); a collision is a validation error.
- Imports may be transitive (an imported file may itself use `importFrom` /
  `import` to pull in others); a cycle of imports is a validation error.
- A `ref` must name a step that is defined (inline, shared, or imported) and a
  `variableSets` entry must name a variable set declared under
  `spec.variableSets`; otherwise the import fails with an actionable error
  naming the missing name.
- Only the referenced unit is spliced in; an imported file's `kind` tells the
  compiler how to read it (a `Step` / `VariableSet` / `Job` file contributes a
  reusable unit, not a competing pipeline), and its `metadata` is ignored.

This is what lets a team keep a `shared/` directory of step, variable set, and
job definitions that many pipelines pull in by `importFrom` (steps and jobs) or
`import` (variable sets), and keep each environment's pipeline file small.

## Reusable units and job reuse

Three kinds of unit are reusable and importable: **variable sets**, **steps**,
and **jobs**.

- **Variable sets** (`variableSets`) are named groups of variables. Each has an
  inline `variables` map and/or an `import` list of external files or vaults —
  a set may have both, and its variables are the union of the inline `variables`
  and the imported ones (the inline ones win on a key collision) — and its own
  `secretSources` section (shaped like the pipeline's `spec.secretSources`,
  F-21.1.3), which the set owns and which back its masked variables and `import`
  vault entries. The compiler fetches each file via the source-fetcher and
  merges them. A job references sets by name in its `variableSets` list, and
  carries its own inline variables in a `variables` map. At compile time the
  compiler resolves each named set (fetching its files) and merges the sets'
  variables with the job's inline `variables` into the run's parameters for
  that job's spec interpolation (F-10), with the job's inline variables winning
  over a set's on a key collision; a set's `secretSources` are merged into the
  pipeline's `secretSources` namespace (the pipeline's own win on a name
  collision), so a set that declares its own sources is self-contained.
- **Steps** are named step specs, and they live in two places: **shared** steps
  under `spec.steps` (a name → step-spec map), and **job-local** steps under a
  job's `steps` map. Each entry is inline, a `ref` to a shared step, or an
  `importFrom` pull from another file. A `ref` / `importFrom` is expanded in
  place (its full step spec) at compile time, so a job can mix shared and local
  steps freely. A job's `steps` can also be pulled in from another file with
  `importFrom`; any steps the job defines locally override the imported steps by
  name (the imported steps are the base).
- **Jobs** are named job specs under `spec.jobs` (a `steps` map, an optional
  `needs` list, a `variables` map, a `variableSets` list, an `environment`, a
  `workerGroup`, and the standard deployment options). A job can be pulled in
  from another file with `importFrom` (any fields set on the local job override
  the imported job's, including its `steps` — a local `steps` map overrides the
  imported job's steps by name).

**Job reuse across environments.** Because steps are named and shared, each
environment is its own job that reuses the same shared steps (via `ref`) and
differs only by the variable sets it references (via `variableSets`) and a few
job-local steps. This is the "each environment is very similar and only varies
by variables" case: `deploy-dev` and `deploy-prod` both `ref` `step1` (the
shared step) and differ only by the variable sets in their `variableSets` list
and their local steps. The DAG (`needs`) is expressed over the jobs' names (a
job with no `needs` has no dependencies), so a promotion chain (`deploy-dev →
deploy-prod`) is a normal F-08 dependency.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Reusable units and job reuse.** Variable sets, steps, and jobs are named,
  reusable units. Steps live in two places — shared steps under `spec.steps`
  and job-local steps under a job's `steps` map — and each entry is inline, a
  `ref` to a shared step, an `importFrom` pull from another file, or empty — an
  empty entry is shorthand for a `ref` to the shared step of the same name (all
  explicit fields, not YAML tags). Variable sets are inline `variables` maps
  and/or `import` from external files or vaults, plus their own `secretSources`
  section (shaped like the pipeline's `spec.secretSources`, F-21.1.3) that the
  set owns and that back its masked variables (merged into the pipeline's
  `secretSources` namespace on import, the pipeline's own winning on a name
  collision); a job references sets by name in its `variableSets` list and
  carries its own inline variables in a `variables` map. A job can itself be
  pulled in with `importFrom` (local fields override the imported job's). A referenced file holds exactly one unit — a
  `VariableSet`, `Step`, or `Job` manifest whose `spec` is that unit's
  definition — so the compiler splices the referenced units in place, fetches
  each referenced file via the source-fetcher, and merges everything into one
  namespace (unique names; transitive imports; no import cycles). Because steps
  are named and shared, each environment is its own job that reuses the same
  shared steps (via `ref`) and differs only by the variable sets it references
  (via `variableSets`) and a few local steps, so "deploy to dev/staging/prod"
  is shared steps plus per-environment jobs and a `needs` chain (a job with no
  `needs` has no dependencies), not copied jobs.
- **New fields / RPCs / endpoints (this sub-feature).** Import resolution in
  `internal/pipelinefile` (`importFrom` on a step, a job's `steps`, or a whole
  job; `import` on a variable set from external files or vaults); the
  `Step` / `VariableSet` / `Job` file kinds (a file's `kind` tells the compiler
  how to read it); and the compiler's import rules (unique names across the
  merged namespace, transitive imports, no import cycles, resolvable `ref` /
  `variableSets`). No new endpoints — imports are resolved during the import /
  sync path established by F-21.1 / F-21.5.
