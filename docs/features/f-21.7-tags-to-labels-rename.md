# F-21.7 · `tags` → `labels` rename (+ `metadata.annotations`)

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature renames the platform's **`tags`** to **`labels`** (the F-29
concept) across the codebase, and adds **`metadata.annotations`** to the file
format. The F-29 feature (labeling) is already implemented but its code still
uses the `tags` name; F-21's file format calls them `labels` (the
Kubernetes-style `metadata.labels`), so the rename reconciles the code with the
file format and the rest of the platform's documentation.

**What.** A mechanical, behavior-preserving rename of the labeling concept from
`tags` to `labels` across models, the database service, the API, the protos,
config, and the worker — plus adding `metadata.annotations` (free-form key/value
pairs used only for UI searchability; they never affect behavior) to the file
format and the pipeline model.

**Why.** The file format (F-21.1) uses `metadata.labels`, and AGENTS.md / F-29
already describe the concept as `labels`. The code still says `tags`. Renaming
keeps one term across the file, the API, the database, and the docs, so a reader
who knows the file format knows the API.

**Depends on.** [F-21.1](f-21.1-file-format-compiler.md) (the file format that
uses `metadata.labels` / `metadata.annotations`). It is otherwise independent of
the other F-21.x sub-features and can be done in parallel.

**Scope.**
- `internal/models` — rename the `Tag` struct to `Label`, the `Tags`
  in-memory fields on `Pipeline` / `PipelineVersion` / `Job` / `JobExecution` /
  `Worker` / `Environment` / `WorkerGroup` to `Labels` (JSON `labels`), and the
  `TagOwner*` constants to `LabelOwner*`; add an `Annotations` field (free-form
  key/value, UI-search-only) to `Pipeline` (and the file format's
  `metadata.annotations`).
- `internal/services/database` — rename `replaceTags` → `replaceLabels`,
  `loadTags` → `loadLabels`, `loadTagsByOwner` → `loadLabelsByOwner`,
  `ownerIDsMatchingTags` → `ownerIDsMatchingLabels`, `runIDsMatchingTags` →
  `runIDsMatchingLabels`, and the `tags.go` file to `labels.go`; the `Label`
  table (renamed from `Tag`).
- `internal/api` — rename `tagFilterFromQuery` → `labelFilterFromQuery` and the
  `tag=key=value` query param to `label=key=value`; the `tags` request/response
  fields to `labels`.
- `proto/` — rename the `tags` fields to `labels` (api / db / scheduler protos);
  regenerate with `make proto`.
- `internal/config` — rename `CDROM_WORKER_TAGS` → `CDROM_WORKER_LABELS` and the
  config key `worker_tags` → `worker_labels`.
- `internal/worker` — the worker's `tags` → `labels` (sent on `RegisterWorker`).
- The file format's `metadata.annotations` (F-21.1) is stored on the pipeline
  and surfaced to the UI for searchability (it never affects behavior).

## The rename

The F-29 labeling feature is implemented but named `tags` in the code. F-21's
file format (F-21.1) calls the same concept `labels` (the Kubernetes-style
`metadata.labels`), and AGENTS.md / F-29 already describe it as `labels`. This
sub-feature renames the code to match, so there is one term across the file,
the API, the database, and the docs.

The rename is **mechanical and behavior-preserving** — it changes names, not
semantics. The mapping is:

| From (`tags`) | To (`labels`) |
|---------------|---------------|
| `models.Tag` struct / `Tag` table | `models.Label` struct / `Label` table |
| `models.TagOwner*` constants | `models.LabelOwner*` constants |
| `*.Tags` in-memory fields (`gorm:"-"`) | `*.Labels` (JSON `labels`) |
| `replaceTags` / `loadTags` / `loadTagsByOwner` | `replaceLabels` / `loadLabels` / `loadLabelsByOwner` |
| `ownerIDsMatchingTags` / `runIDsMatchingTags` | `ownerIDsMatchingLabels` / `runIDsMatchingLabels` |
| `internal/services/database/tags.go` | `internal/services/database/labels.go` |
| `tagFilterFromQuery` + `tag=key=value` query param | `labelFilterFromQuery` + `label=key=value` |
| proto `tags` fields (api / db / scheduler) | proto `labels` fields (`make proto`) |
| `CDROM_WORKER_TAGS` / `worker_tags` | `CDROM_WORKER_LABELS` / `worker_labels` |
| worker `tags` (sent on `RegisterWorker`) | worker `labels` |

The `Label` table keeps the same shape as the `Tag` table: one row per
key/value pair, keyed by `owner_type` + `owner_id` + `key` (a unique index),
with a `(key, value)` index for search-by-label. The owner-type constants
(`pipeline`, `pipeline_version`, `job`, `job_execution`, `environment`,
`worker`, `worker_group`) are unchanged in value — only the Go constant names
change.

**`metadata.annotations`.** Alongside the rename, the file format's
`metadata.annotations` (F-21.1) — free-form key/value pairs used only for UI
searchability — is stored on the pipeline (an `Annotations` field) and surfaced
to the UI. Annotations never affect behavior; they are a search/discovery
mechanism distinct from `labels` (which are combined onto a job run, F-29).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The `tags` term is renamed to `labels`** (the F-29 concept) across the
  platform — pipelines, jobs, environments, worker groups, and workers — so the
  file format's `metadata.labels` (F-21.1) is the same `Label` set the rest of
  the platform uses. The rename is mechanical and behavior-preserving: the
  `Tag` model becomes `Label`, the `Tags` fields become `Labels`, the
  `TagOwner*` constants become `LabelOwner*`, the `tag=` query param becomes
  `label=`, the protos' `tags` fields become `labels`, and
  `CDROM_WORKER_TAGS` becomes `CDROM_WORKER_LABELS`.
- **`metadata.annotations` is UI-search-only.** Free-form key/value pairs on the
  file format's `metadata` block, stored on the pipeline and surfaced to the UI
  for searchability; they never affect behavior (unlike `labels`, which are
  combined onto a job run, F-29).
- **New fields / RPCs / endpoints (this sub-feature).** A `Label` model
  (renamed from `Tag`, registered in `models.All()`); `Labels` fields on
  `Pipeline` / `PipelineVersion` / `Job` / `JobExecution` / `Worker` /
  `Environment` / `WorkerGroup` (renamed from `Tags`); an `Annotations` field on
  `Pipeline`; the `label=key=value` query param (renamed from `tag=`); the
  protos' `labels` fields (renamed from `tags`, `make proto`); and
  `CDROM_WORKER_LABELS` / `worker_labels` (renamed from `CDROM_WORKER_TAGS` /
  `worker_tags`).
