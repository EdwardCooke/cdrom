# F-21.2.3 · Git repository cache

> Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature is the fetcher's **git repository cache** — a (shared) on-disk
cache of checked-out git repositories that backs the `git` kind (F-21.2.4). A
repository is kept for a **rolling 24 hours** (pruned only after 24 hours
without use), is **refetched from upstream** on every file request (subject to
a configurable **debounce**), is **resynced** (re-cloned) when a fetch fails,
and is **locked** while it is cloned/fetched/resynced so multiple fetcher
replicas sharing the cache never race. The cache is the fetcher's only on-disk
state and is transient — safe to lose (a re-clone rebuilds it).

**Why.** Cloning a repository on every fetch is slow, so the fetcher keeps
checked-out repositories on disk. But a cached checkout can go stale (upstream
moves, a force push), so every request refetches from upstream on a debounce;
a fetch that fails is resynced by re-cloning so the cache self-heals. In a
multi-replica (HA) deployment several fetcher replicas (e.g. two pods in
Kubernetes) can run against the same cache on a shared volume (a PVC), so a
repository is locked while it is being fetched or resynced, and the index file
is the shared coordination point that keeps the replicas from double-fetching
or reading a half-written checkout.

  configurable duration) that skips a refetch of a recently fetched repository.

  inactive for more than 24 hours and removes orphaned directories.

  `CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`.

**Acceptance criteria.**
- [ ] **Git repositories are cached on disk for a rolling 24 hours**
      (F-21.2.3.2): a checked-out repository is pruned only after 24 hours
      without use, and every fetch of the repository updates its last-accessed
      timestamp, so an actively used repository is never pruned.
- [ ] The **cache root** is configurable at the process level
      (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, F-21.2.3.1) and defaults to a
      `repositories` directory under the OS temp directory.
- [ ] A **text index file** at the cache root (F-21.2.3.1) records, per cached
      repository, the repository directory, the repository URL, the
      last-accessed Unix epoch timestamp, and the last-fetched Unix epoch
      timestamp; it is updated **atomically** on every change.
- [ ] Every time a file is requested from a repository, the repository is
      **refetched from upstream** (F-21.2.3.2), so upstream changes — including
      a **force push** — are brought down fresh; a fetch that fails **resyncs**
      the repository by re-cloning from upstream.
- [ ] A repository is **locked** while it is being cloned, fetched, or resynced
      (F-21.2.3.3), so multiple fetcher replicas sharing the cache (e.g. two
      pods on a PVC) never read a half-written checkout or double-fetch.
- [ ] A recently fetched repository is not refetched again within the
      **debounce window** (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`,
      F-21.2.3.2); the last-fetched timestamp is shared in the index file so the
      debounce is effective across replicas.
- [ ] A **cleanup thread** (F-21.2.3.4) periodically walks the cache and deletes
      repositories that have been inactive for more than 24 hours; before a
      directory is pruned, its entry is removed from the index file.

## The git repository cache

Cloning a repository on every fetch is slow, so the fetcher keeps checked-out
git repositories on disk for a **rolling 24 hours**: a repository used again
within 24 hours of its last use is reused instead of re-cloned, and one that
goes 24 hours unused is pruned. Every time a file is requested from a
repository the repository is **refetched from upstream** (subject to a
configurable **debounce**) so upstream changes — including a force push — are
brought down fresh; a fetch that fails is **resynced** by discarding the
checkout and re-cloning from upstream. The cache is transient working state —
the fetcher's only on-disk state — and is safe to lose: losing it only costs a
re-clone.

The cache root is a **shared** directory: in a multi-replica (HA) deployment
several fetcher replicas (e.g. two pods in Kubernetes) can run against the same
cache on a shared volume (a PVC). Because the replicas share the cache, a
repository is **locked** while it is being fetched or resynced, and the index
file is the shared coordination point that keeps the replicas from
double-fetching or reading a half-written checkout.

The pieces (detail in the sub-features):

- **Cache structure & index** (F-21.2.3.1) — the cache root, the portable
  per-repository directory naming (`<unix-epoch>-<counter>`), and the
  atomically-updated text index file that maps each repository URL to its
  directory and its last-accessed / last-fetched timestamps.
- **Fetch lifecycle** (F-21.2.3.2) — the rolling 24-hour window, the
  refetch-on-request behavior (a `git fetch` + hard reset that absorbs a force
  push), the configurable fetch debounce, and the resync-on-failure behavior.
- **Cross-replica locking** (F-21.2.3.3) — the per-repository OS file lock (with
  a stale-lock timeout) that serializes access while a repository is
  cloned/fetched/resynced.
- **Cleanup thread** (F-21.2.3.4) — the background goroutine that prunes
  repositories inactive for more than 24 hours and sweeps orphaned directories.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Git repositories are cached on disk for a rolling 24 hours, refetched on a
  debounce, and locked across replicas.** The fetcher keeps checked-out
  repositories under a process-level cache root
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, default the `repositories` directory
  under the OS temp directory). Each repository's directory is named
  `<unix-epoch>-<counter>` (portable across Windows and Linux); a text index
  file at the root maps each repository URL to its directory and its
  last-accessed and last-fetched Unix epoch timestamps and is rewritten
  atomically (temp file + rename) on every change. Every file request
  **refetches** the repository from upstream (a `git fetch` + hard reset, which
  absorbs a force push) unless it was fetched within the configurable
  **debounce** window (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`); a fetch
  that fails **resyncs** by discarding the checkout and re-cloning from
  upstream. The cache root is **shared** across fetcher replicas (e.g. two pods
  on a PVC), so a repository is **locked** (a per-repository OS file lock with a
  stale-lock timeout) while it is cloned/fetched/resynced, and a background
  cleanup thread prunes repositories inactive for more than 24 hours, removing
  the index entry before the directory. The cache is transient and is the
  fetcher's only on-disk state.
- **New fields / RPCs / endpoints (this sub-feature).** The git repository cache
  in `internal/services/pipelinesource` (cache root + text index +
  per-repository lock + fetch debounce + cleanup thread); and
  `CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR` (default `<os.TempDir()>/repositories`)
  and `CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE` (the fetch debounce window) in
  `internal/config`.
