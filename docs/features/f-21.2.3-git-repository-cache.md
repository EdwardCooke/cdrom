# F-21.2.3 · Git repository cache

> Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature is the fetcher's **git repository cache** — a (shared) on-disk
cache of bare git object stores that backs the `git` kind (F-21.2.4). A
repository is kept for a **rolling 24 hours** (pruned only after 24 hours
without use), is **fetched from upstream** on every file request (incremental —
a no-op when the branch is unchanged), is **resynced** (re-cloned) when a fetch
fails, and is **locked** while it is cloned/fetched/resynced so multiple fetcher
replicas sharing the cache never race. The cache is the fetcher's only on-disk
state and is transient — safe to lose (a re-clone rebuilds it).

**Why.** Cloning a repository on every fetch is slow, so the fetcher keeps bare
object stores on disk. But a cached store can go stale (upstream moves, a force
push), so every request fetches from upstream; a fetch is incremental (a no-op
when the branch is unchanged, only the new commits when it moved), so no
debounce is needed to coalesce bursts. A fetch that fails is resynced by
re-cloning so the cache self-heals. In a multi-replica (HA) deployment several
fetcher replicas (e.g. two pods in Kubernetes) can run against the same cache on
a shared volume (a PVC), so a repository is locked while it is being fetched or
resynced, and the index file is the shared coordination point that keeps the
replicas from double-fetching or reading a half-written store.

## The git repository cache

Cloning a repository on every fetch is slow, so the fetcher keeps bare git
object stores on disk for a **rolling 24 hours**: a repository used again within
24 hours of its last use is reused instead of re-cloned, and one that goes 24
hours unused is pruned. Every time a file is requested from a repository the
repository is **fetched from upstream** (incrementally — a no-op when the branch
is unchanged, only the new commits when it moved) so upstream changes —
including a force push — are brought down fresh; a fetch that fails is
**resynced** by discarding the store and re-cloning from upstream. The cache is
transient working state — the fetcher's only on-disk state — and is safe to
lose: losing it only costs a re-clone.

The cache root is a **shared** directory: in a multi-replica (HA) deployment
several fetcher replicas (e.g. two pods in Kubernetes) can run against the same
cache on a shared volume (a PVC). Because the replicas share the cache, a
repository is **locked** while it is being fetched or resynced, and the index
file is the shared coordination point that keeps the replicas from
double-fetching or reading a half-written checkout.

The pieces (detail in the sub-features):

- **Cache structure & index** (F-21.2.3.1) — the cache root, the portable
  per-repository directory naming (a random UUID), and the
  atomically-updated text index file that maps each repository URL to its
  directory and its last-accessed / last-fetched timestamps.
- **Fetch lifecycle** (F-21.2.3.2) — the rolling 24-hour window, the
  fetch-on-request behavior (a shallow bare clone on first use, then an
  incremental `git fetch` of the requested branch on every request, performed
  by go-git so there is no external `git` binary dependency), and the
  resync-on-failure behavior.
- **Cross-replica locking** (F-21.2.3.3) — the per-repository lock file (created
  atomically, with a heartbeat and a stale-lock timeout) that serializes access
  while a repository is cloned/fetched/resynced.
- **Cleanup thread** (F-21.2.3.4) — the background goroutine that prunes
  repositories inactive for more than 24 hours and sweeps orphaned directories.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Git repositories are cached on disk for a rolling 24 hours, fetched on
  every request, and locked across replicas.** The fetcher keeps bare object
  stores under a process-level cache root
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, default the `repositories` directory
  under the OS temp directory). Each repository's directory is named with a
  random UUID (portable across Windows and Linux); a text index
  file at the root maps each repository URL to its directory and its
  last-accessed and last-fetched Unix epoch timestamps and is rewritten
  atomically (temp file + rename) on every change. Every file request
  **fetches** the requested branch from upstream into the shared store
  (incremental — a no-op when unchanged, the delta when it moved, forced so a
  force push is absorbed); a fetch that fails **resyncs** by discarding the
  store and re-cloning from upstream. There is **no debounce**: a fetch is
  cheap when idle, so coalescing bursts is unnecessary. The cache root is
  **shared** across fetcher replicas (e.g. two pods on a PVC), so a repository
  is **locked** (a per-repository lock file created atomically, with a heartbeat
  and a stale-lock timeout) while it is cloned/fetched/resynced, and a
  background cleanup thread prunes repositories inactive for more than 24
  hours, removing the index entry before the directory. The cache is transient
  and is the fetcher's only on-disk state.
- **New fields / RPCs / endpoints (this sub-feature).** The git repository cache
  in `internal/services/pipelinesource` (cache root + text index +
  per-repository lock + cleanup thread); and
  `CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR` (default `<os.TempDir()>/repositories`)
  in `internal/config`.
