# F-21.1.1 · Manifest envelope & compiler skeleton

> Part of [F-21.1 · File format & compiler](f-21.1-file-format-compiler.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The compiler's foundation: parsing a pipeline definition as a
**Kubernetes-style manifest** — `apiVersion` (currently `cdrom/alphav1`), a
`kind` (`Pipeline` / `VariableSet` / `Step` / `Job`), a `metadata` block
(`name`, `description`, `labels`, `annotations`), and a `spec` holding
everything else — and routing a document on `kind`. The compiler
(`internal/pipelinefile`) parses the YAML preserving key order, validates the
envelope, and produces a typed in-memory definition that the other F-21.1.x
sub-features fill in (steps in F-21.1.2, variables in F-21.1.3, jobs and
deployment options in F-21.1.4).

**Why.** A consistent manifest envelope is what lets the compiler route a
document (and, later, an imported file — F-21.4) on `kind`, and what makes the
file recognizable as a Cdrom definition. Parsing that preserves key order is
what makes a YAML map yield a deterministic ordered step/job list.

**Scope.**
- `internal/pipelinefile` — manifest parsing: `apiVersion` (currently only
  `cdrom/alphav1` is accepted; an unknown version is a validation error),
  `kind` dispatch (`Pipeline` / `VariableSet` / `Step` / `Job`), `metadata`
  (`name` required, `description`, `labels`, `annotations`), and `spec`
  (everything else).
- YAML parsing that preserves key order (so a map still yields a deterministic
  ordered list).
- Actionable validation errors: a clear message naming the offending file, key,
  and reason.
- camelCase mapping keys throughout the file format.

**Acceptance criteria.**
- [ ] A pipeline definition is a Kubernetes-style manifest with an `apiVersion`
      (currently `cdrom/alphav1`), a `kind` (`Pipeline` / `VariableSet` /
      `Step` / `Job`), a `metadata` block, and a `spec`; the compiler dispatches
      on `kind` to know how to interpret a document.
- [ ] `apiVersion` is the schema version of the file format; an unknown
      `apiVersion` is a validation error (the format evolves by bumping it
      through the project's lifecycle).
- [ ] `metadata` carries `name` (required), `description`, `labels` (the F-29
      key/value pairs), and `annotations` (free-form key/value pairs used only
      for UI searchability — they never affect behavior); everything else is
      under `spec`.
- [ ] The YAML is parsed preserving key order, so a map (steps, jobs) still
      yields a deterministic ordered list.
- [ ] Invalid definitions are rejected with actionable errors (a clear message
      naming the offending file, key, and reason).
- [ ] Mapping keys in the file are camelCase (`concurrencyKeys`,
      `variableSets`, `importFrom`, `secretSources`, …).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The file is a Kubernetes-style manifest.** Every definition has an
  `apiVersion` (currently `cdrom/alphav1`), a `kind` (`Pipeline` /
  `VariableSet` / `Step` / `Job`), a `metadata` block (`name`, `description`,
  `labels`, `annotations`), and a `spec` holding the rest. `apiVersion` and
  `kind` are the only keys the compiler uses to route a document; `metadata` is
  the identity block; and everything else lives under `spec`. `apiVersion` is
  bumped as the format evolves through the project's lifecycle, and
  `metadata.annotations` is free-form key/value data used only for UI
  searchability (it never affects behavior).
- **New fields / RPCs / endpoints (this sub-feature).** The
  `internal/pipelinefile` compiler package: manifest parsing (`apiVersion` /
  `kind` / `metadata` / `spec`), `kind` dispatch, key-order-preserving YAML
  parsing, and the actionable validation-error format (offending file, key, and
  reason) that the other F-21.1.x sub-features build on.
