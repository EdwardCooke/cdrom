# F-21.2.3.2 · Fetch lifecycle (fetch-on-request, resync)

> Part of [F-21.2.3 · Git repository cache](f-21.2.3-git-repository-cache.md) · Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **fetch lifecycle** for a `git` reference against the cache
(F-21.2.3.1): the rolling 24-hour retention window, the **fetch-on-request**
behavior (a shallow bare clone on first use, then an incremental `git fetch` of
the requested branch on every request — no debounce, no worktree, no reset),
and **resync-on-failure** (a failed fetch discards the object store and
re-clones from upstream). This is the behavior the `git` fetch client
(F-21.2.4.1) drives. The git operations (clone / fetch / object reads) are
performed by **go-git** (a pure-Go git implementation), so the fetcher has no
external dependency on the `git` binary.

**Why.** A cached repository can go stale (upstream moves, a force push), so a
repository that is reused must be brought up to date on every request. Because
a git fetch is **incremental** — a no-op (ref advertisement only) when the
branch is unchanged, and only the new commits when it moved — fetching on every
request is cheap and needs no debounce to coalesce bursts. And a cache entry can
become corrupt or diverged, so a failed fetch must self-heal by re-cloning
rather than returning a bad file. Together these keep the cache both fresh and
self-maintaining, with minimal network traffic.

**Scope.**
- The **rolling 24-hour** retention window (a repository is pruned only after
  24 hours without use; every use updates its last-accessed timestamp).
- The **fetch-on-request** behavior: a shallow (depth 1) **bare** clone of the
  requested branch on first use, then a plain incremental `git fetch` of the
  requested branch on every subsequent request (works for a different branch
  than the one the store was cloned with).
- The **resync-on-failure** behavior: discard the object store and re-clone from
  upstream when a fetch fails.
- The file is read **from the object store** at the requested branch's tip
  (no worktree checkout, no reset).

**Acceptance criteria.**
- [x] **Git repositories are cached on disk for a rolling 24 hours**: a cached
      object store is pruned only after 24 hours without use, and every fetch of
      the repository updates its last-accessed timestamp, so an actively used
      repository is never pruned.
- [x] On a fetch, the repository's last-accessed timestamp in the index file
      (F-21.2.3.1) is updated; if the repository has no entry, a new cache
      directory is created, the repository is shallow-cloned into it (bare,
      depth 1, the requested branch), and a new index entry is added.
- [x] Every time a file is requested from a repository, the repository is
      **fetched from upstream** (a `git fetch` of the requested branch), so
      upstream changes — including a **force push** — are brought down fresh.
      The fetch is incremental: it transfers no objects when the branch is
      unchanged and only the new commits when it moved.
- [x] A request for a **different branch** than the one the store was cloned
      with fetches that branch into the shared object store and returns that
      branch's file and tip commit (no stale-branch content).
- [x] A fetch that fails (a diverged / non-fast-forward state, local corruption,
      a transient error) **resyncs** the repository: the object store is
      discarded and the repository is re-cloned from upstream; if the re-clone
      also fails, the fetch fails with a clear error.

## The fetch lifecycle

A fetch of a `git` reference (F-21.2.2) against the cache (F-21.2.3.1) follows
this lifecycle. The repository's lock (F-21.2.3.3) is held for the duration of
steps 4–6.

1. The reference is parsed into the repository URL, the branch, and the path
   (F-21.2.2).
2. The index is consulted for the repository URL.
3. The repository's **lock** is acquired (F-21.2.3.3); a concurrent fetch of the
   same repository — on this replica or another — waits for it.
4. **Cache miss** (no index entry) — a new directory (named with a random
   UUID) is created under the cache root, the repository is **shallow-cloned
   (depth 1) as a bare object store** for the requested branch, and a new index
   entry (the repository directory, the URL, and the current timestamp for both
   last-accessed and last-fetched) is added by an atomic index rewrite
   (F-21.2.3.1).
5. **Cache hit** (an index entry exists) — the entry's last-accessed timestamp
   is updated to now (updating it on every use is what makes the 24-hour window
   *rolling*: an actively used repository is never pruned). The requested
   branch is then **fetched from upstream** into the shared object store: a
   plain `git fetch` of the branch ref (the explicit refspec works for a
   different branch than the one the store was cloned with). The fetch is
   incremental — a no-op when the branch is unchanged, only the new commits when
   it moved — and absorbs a **force push** (the refspec is forced). The
   entry's last-fetched timestamp is updated to now (an atomic index rewrite).
6. **Resync on fetch failure** — if the fetch fails for any reason (a diverged
   / non-fast-forward state, local corruption, a transient error), the object
   store is discarded and the repository is **re-cloned from upstream** (a full
   resync, shallow, the requested branch). If the re-clone also fails, the lock
   is released and the fetch fails with a clear error.
7. The file is read **from the object store** at the requested branch's tip
   commit (F-21.2.4.1) — no worktree is checked out and no reset is performed.
   The response's version identifier is the requested branch's commit hash; the
   content hash is the SHA-256 of the file's content.
8. The lock is released.

### Fetch on request

Every time a file is requested from a repository, the requested branch is
**fetched from upstream** into the shared bare object store. A fetch is
incremental: when the branch is unchanged the server sends only the ref
advertisement (no objects), and when it moved it sends only the new commits.
The forced refspec (`+refs/heads/<branch>:refs/remotes/origin/<branch>`) is what
makes the cache absorb a **force push**: the upstream branch may have been
rewritten, so the remote-tracking ref is moved to exactly what upstream now has.
Because the file is read from the objects at the requested branch's tip (not
from a checked-out worktree), there is no reset step and no way for a different
branch's content to leak into the response.

### Resync on failure

If a fetch fails for any reason — a diverged / non-fast-forward state, local
corruption, a transient error — the object store is discarded and the
repository is **re-cloned from upstream** (a full resync, shallow, the requested
branch). This is the self-heal path: a corrupt or diverged entry is replaced
with a fresh clone rather than returned to the caller. If the re-clone also
fails, the lock is released and the fetch fails with a clear error (F-21.2.1).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **A cached repository is fetched on every request and resynced on failure.**
  Every file request **fetches** the requested branch from upstream into the
  shared bare object store (incremental — a no-op when unchanged, the delta when
  it moved, forced so a force push is absorbed); a fetch that fails **resyncs**
  by discarding the store and re-cloning from upstream. There is **no debounce**:
  a fetch is cheap when idle, so coalescing bursts is unnecessary, and removing
  it eliminates the stale-branch window a debounce created. The rolling 24-hour
  window is kept alive by updating the last-accessed timestamp on every use.
- **The cache holds a bare object store per repository URL, shared across
  branches.** The file is read from the objects at the requested branch's tip —
  no worktree, no reset. This keeps the disk cost at ~1x the working tree
  (deduplicated across branches) and makes a branch switch a cheap incremental
  fetch.
- **New fields / RPCs / endpoints (this sub-feature).** The fetch lifecycle in
  `internal/services/pipelinesource` (fetch-on-request, resync-on-failure, the
  bare object store, and the read-from-objects file read).
