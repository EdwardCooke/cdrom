# F-21.2.3.2 · Fetch lifecycle (refetch, debounce, resync)

> Part of [F-21.2.3 · Git repository cache](f-21.2.3-git-repository-cache.md) · Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **fetch lifecycle** for a `git` reference against the cache
(F-21.2.3.1): the rolling 24-hour retention window, the **refetch-on-request**
behavior (a `git fetch` + hard reset that absorbs upstream changes including a
force push), the configurable **fetch debounce** (a recently fetched repository
is not refetched again within the window), and **resync-on-failure** (a failed
fetch discards the checkout and re-clones from upstream). This is the behavior
the `git` fetch client (F-21.2.4) drives.

**Why.** A cached checkout can go stale (upstream moves, a force push), so a
repository that is reused must be brought up to date — but refetching on every
single request would hammer the upstream, so a debounce coalesces bursts. And a
cache entry can become corrupt or diverged, so a failed fetch must self-heal by
re-cloning rather than returning a bad file. Together these keep the cache both
fresh and self-maintaining.

**Scope.**
- The **rolling 24-hour** retention window (a repository is pruned only after
  24 hours without use; every use updates its last-accessed timestamp).
- The **refetch-on-request** behavior: a `git fetch` of the branch ref followed
  by a hard reset of the checkout to the fetched ref.
- The **fetch debounce** (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`, a
  configurable duration) that skips a refetch of a recently fetched repository.
- The **resync-on-failure** behavior: discard the checkout and re-clone from
  upstream when a fetch/reset fails.
- `internal/config` — `CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`.

**Acceptance criteria.**
- [ ] **Git repositories are cached on disk for a rolling 24 hours**: a
      checked-out repository is pruned only after 24 hours without use, and
      every fetch of the repository updates its last-accessed timestamp, so an
      actively used repository is never pruned.
- [ ] On a fetch, the repository's last-accessed timestamp in the index file
      (F-21.2.3.1) is updated; if the repository has no entry, a new cache
      directory is created, the repository is cloned into it, and a new index
      entry is added.
- [ ] Every time a file is requested from a repository, the repository is
      **refetched from upstream** (a `git fetch` of the branch + a hard reset to
      the fetched ref), so upstream changes — including a **force push** — are
      brought down fresh.
- [ ] A recently fetched repository is not refetched again within the
      **debounce window** (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`, a
      configurable duration); the last-fetched timestamp is shared in the index
      file so the debounce is effective across replicas.
- [ ] A fetch that fails (a diverged / non-fast-forward state, local corruption,
      a transient error) **resyncs** the repository: the checkout is discarded
      and the repository is re-cloned from upstream; if the re-clone also fails,
      the fetch fails with a clear error.

## The fetch lifecycle

A fetch of a `git` reference (F-21.2.2) against the cache (F-21.2.3.1) follows
this lifecycle. The repository's lock (F-21.2.3.3) is held for the duration of
steps 4–6.

1. The reference is parsed into the repository URL, the branch, and the path
   (F-21.2.2).
2. The index is consulted for the repository URL.
3. The repository's **lock** is acquired (F-21.2.3.3); a concurrent fetch of the
   same repository — on this replica or another — waits for it.
4. **Cache miss** (no index entry) — a new directory `<epoch>-<counter>` is
   created under the cache root, the repository is cloned into it (checking out
   the branch), and a new index entry (the repository directory, the URL, and
   the current timestamp for both last-accessed and last-fetched) is added by an
   atomic index rewrite (F-21.2.3.1).
5. **Cache hit** (an index entry exists) — the entry's last-accessed timestamp
   is updated to now (updating it on every use is what makes the 24-hour window
   *rolling*: an actively used repository is never pruned). The repository is
   then **refetched from upstream** unless it was fetched within the debounce
   window (below): a `git fetch` of the branch ref followed by a hard reset of
   the checkout to the fetched ref, which absorbs upstream changes including a
   force push. When a fetch does run, the entry's last-fetched timestamp is
   updated to now (an atomic index rewrite).
6. **Resync on fetch failure** — if the fetch (or the reset) fails for any
   reason (a diverged / non-fast-forward state, local corruption, a transient
   error), the checkout is discarded and the repository is **re-cloned from
   upstream** (a full resync, checking out the branch). If the re-clone also
   fails, the lock is released and the fetch fails with a clear error.
7. The file is read from the checkout at the branch ref (F-21.2.4). The
   response's version identifier is the branch's commit hash after the
   fetch/clone; the content hash is the SHA-256 of the file's content.
8. The lock is released.

### Refetch on request

Every time a file is requested from a repository, the repository is **refetched
from upstream** — a `git fetch` of the branch ref followed by a hard reset of
the checkout to the fetched ref. A hard reset (not a merge) is what makes the
cache absorb a **force push**: the upstream branch may have been rewritten, so
the checkout is reset to exactly what upstream now has, discarding any local
divergence. This is what keeps a reused checkout fresh.

### The debounce

A repository that was fetched very recently is not refetched again on the next
request: if the entry's last-fetched timestamp is within the **debounce window**
(`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`, a configurable duration, default
e.g. 30s), the refetch is skipped and the file is read from the current
checkout. The debounce keeps a burst of requests for the same repository (many
pipelines from one repo syncing at once, or several replicas fetching
concurrently) from hammering the upstream. The last-fetched timestamp lives in
the shared index file (F-21.2.3.1), so the debounce is effective across
replicas, not just within one process.

### Resync on failure

If a fetch (or the hard reset) fails for any reason — a diverged /
non-fast-forward state, local corruption, a transient error — the checkout is
discarded and the repository is **re-cloned from upstream** (a full resync,
checking out the branch). This is the self-heal path: a corrupt or diverged
entry is replaced with a fresh clone rather than returned to the caller. If the
re-clone also fails, the lock is released and the fetch fails with a clear error
(F-21.2.1).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **A cached repository is refetched on every request, on a debounce, and
  resynced on failure.** Every file request **refetches** the repository from
  upstream (a `git fetch` + hard reset, which absorbs a force push) unless it
  was fetched within the configurable **debounce** window
  (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`); a fetch that fails **resyncs**
  by discarding the checkout and re-cloning from upstream. The rolling 24-hour
  window is kept alive by updating the last-accessed timestamp on every use.
- **New fields / RPCs / endpoints (this sub-feature).** The fetch lifecycle in
  `internal/services/pipelinesource` (refetch-on-request, the fetch debounce,
  and resync-on-failure); and `CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE` (the
  fetch debounce window) in `internal/config`.
