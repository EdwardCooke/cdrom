# F-21.5.1 · Source model & storage

> Part of [F-21.5 · Externally-sourced pipelines](f-21.5-externally-sourced-pipelines.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The database model for externally-sourced pipelines: a
`PipelineSource` (WHERE a pipeline is pulled from: a `kind` of `git` / `http` /
`file`, a `reference` — the `<type>:<spec>` locator string, F-21.2 — and a
credential reference), a `PipelineSourceState` (the last sync's bookkeeping),
the raw YAML + content hash stored on the `Pipeline` row
(`source_file` / `source_hash`), the `periodicRefresh` POLICY stored on the
`Pipeline` row (compiled from the file's `spec.periodicRefresh`: an
`interval` duration and/or a `schedule` cron, overriding the system default of
2 minutes when the admin gate allows it), the override GATE
(`periodic_refresh_overrides_allowed`, a DB flag on the `Pipeline` row), and
the kickoff-provenance fields on the `PipelineRun` row (`source_kind` /
`source_reference` / `source_version` / `source_file_hash`). The SOURCE
(location) is a **database concept** configured through the API — it is not in
the file — so the same file is portable across source kinds; the CADENCE is a
property of the definition and MAY be in the file.

> **Status (IMPLEMENTED).** The `PipelineSource` + `PipelineSourceState`
> models, the source attach/get/detach/list RPCs, the `CountSourcesByCredential`
> RPC (F-21.3.3's delete guard), and the `Set/GetPipelineSourceState` RPCs are
> implemented, along with the `POST/GET/DELETE /api/pipelines/{id}/source`
> endpoints. The stored `source_file` / `source_hash` on the `Pipeline` row,
> the `periodicRefresh` policy + admin gate (file field, DB flag, system
> default knob), the retirement of the early-slice `schedule` column on
> `PipelineSource`, the run-row provenance fields, and the kickoff provenance
> stamping are implemented (all acceptance criteria met).

**Why.** Keeping the source out of the file means the definition is purely the
definition: the same file can be checked into git, served over HTTP, or mounted
on the filesystem, and where it is pulled from is a deployment concern managed
through the API. Storing the raw YAML + hash makes the loaded definition
retrievable through the API and gives the sync routine (F-21.5.2) a cheap,
authoritative change detector.

**Scope.**
- `internal/models` — a `PipelineSource` (PURE LOCATION: a `kind` of
  `git` / `http` / `file` and a `reference` — the `<type>:<spec>` locator
  string, F-21.2, that names the file to fetch — and a `credential` (the name
  of the `SourceCredential` used to authenticate; empty means the source is
  public / needs no credential); the early-slice `schedule` column is RETIRED
  — cadence moved to the file), a `PipelineSourceState` (`last_synced_at`,
  `last_version`, `file_hash`, `last_error`), `source_file` /
  `source_hash`, the `periodicRefresh` policy (`periodic_refresh_interval` —
  a duration, e.g. `2m`; `periodic_refresh_schedule` — a cron expression), and
  the override gate (`periodic_refresh_overrides_allowed`, default true) on
  the `Pipeline` row, and `source_kind` / `source_reference` /
  `source_version` / `source_file_hash` on the `PipelineRun` row (kickoff
  provenance); registered in `models.All()`.
- `internal/pipelinefile` — parse/validate `spec.periodicRefresh` (camelCase;
  `interval` a duration, `schedule` a cron expression per F-09's grammar;
  both optional; when both are set the cron drives) and emit it onto the
  schema; export reproduces it.
- `internal/services/database` — source CRUD (attach / update / detach a
  source to / from a pipeline) and the stored YAML + hash.
- `internal/api/server.go` — the **source** CRUD endpoints and
  `GET /api/pipelines/{id}/source` (the `PipelineSource` plus the
  `PipelineSourceState` and the stored `source_file`).

**Acceptance criteria.**
- [x] A `PipelineSource` has PURE LOCATION: a `kind` (`git` / `http` /
      `file`) and a `reference` — the `<type>:<spec>` locator string (F-21.2)
      that names the file to fetch: `git` — `<repo>@<branch>[<path>]` (the git
      remote, the branch ref, and the file path in the repo, with `\@` / `\[` /
      `\]` / `\\` escaping); `http` — the endpoint URL that serves the file;
      `file` — a path resolved against the fetcher's configured
      local-filesystem root — and a `credential` (the name of the
      `SourceCredential` used to authenticate; empty means the source is
      public / needs no credential). The `reference` is the single source of
      truth for the locator and is what the API passes to `FetchSource`.
- [x] The pipeline's FILE may declare `spec.periodicRefresh` — an `interval`
      (a duration, e.g. `2m`) and/or a `schedule` (a CRON expression, e.g.
      `"0 3 * * *"` for after-hours syncs when load is minimal) — that
      overrides the system default cadence (2 minutes) for that pipeline's
      source; when both are set the cron drives and the interval is ignored;
      an `interval` of `0` (with no cron) opts the source out of periodic
      polling. Invalid durations or malformed crons are compile-time errors
      (actionable, F-21.1.1).
- [x] ADMINISTRATORS control whether file overrides are honored: globally via
      the `pipeline_source.overrides_allowed` config knob (default on) and per
      pipeline via the `periodic_refresh_overrides_allowed` flag on the
      `Pipeline` row (default on, editable through the pipeline API by whoever
      may edit the pipeline). Overrides are honored only when BOTH allow them;
      when denied, the pipeline falls back to the system default cadence —
      denial restores the safe default, it does not halt polling.
- [x] The effective-cadence resolution (applied at sync time, briefly cached):
      overrides allowed ∧ `schedule` set → cron drives; overrides allowed ∧
      `interval` set → due at `now >= last_attempt + interval` (`0` = opt
      out); otherwise → the system default
      `pipeline_source.refresh_interval` /
      `CDROM_PIPELINE_SOURCE_REFRESH_INTERVAL` (default `120s`).
- [x] A `PipelineSourceState` records the last sync's bookkeeping:
      `last_synced_at`, `last_version` (the source's version identifier — the
      git commit hash, an HTTP `ETag`/`Last-Modified`, or the file's mtime — so
      a no-change can be detected cheaply), `file_hash` (the content hash of the
      file at that version), and `last_error` (set when a sync fails, cleared on
      the next success).
- [x] The raw YAML (`source_file`, verbatim — so it is retrievable through the
      API and is the exact input the compiler ran) and its content hash
      (`source_hash`, the SHA-256 of `source_file`, hex) are stored on the
      `Pipeline` row and retrievable via the API.
- [x] The pipeline's source LOCATION (git / http / file) is **not** in the
      file — it is a `PipelineSource` stored in the database and configured
      through the API (source CRUD), so the same file is portable across
      source kinds; a pipeline becomes externally-sourced when a
      `PipelineSource` is attached to it. (Its CADENCE, however, MAY be in the
      file — `spec.periodicRefresh` — subject to the admin gate.)
- [x] `GET /api/pipelines/{id}/source` returns the `PipelineSource` (kind,
      reference, credential name) plus the `PipelineSourceState` (last sync
      time, last version, file hash, last error), the stored `source_file`
      (the raw YAML), and the CADENCE VIEW: the file's declared
      `periodicRefresh`, whether overrides are allowed (global ∧ pipeline),
      and the effective cadence — how a user sees "what definition is
      currently loaded, where it came from, and why it polls at the rate it
      does" without checking out the source.
- [x] `GET /api/pipelines/{id}` returns the pipeline's **compiled** definition
      (the same shape the UI editor shows), so the UI and the file are two views
      of the same model.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Location is not in the file; cadence may be.** WHERE a pipeline is
  pulled from (a `git` / `http` / `file` source and its credential) is a
  **database** concept — a `PipelineSource` row associated with the pipeline —
  not part of the YAML, so the same file is portable across source kinds (the
  source that fetches it is a deployment concern, not a definition concern).
  HOW OFTEN it is pulled, however, is a BEHAVIORAL preference of the
  definition and MAY live in the file as `spec.periodicRefresh` (an
  `interval` duration and/or a `schedule` cron), compiled onto the
  `Pipeline` row and captured in the version snapshot (F-11) — subject to the
  ADMIN GATE: the global `pipeline_source.overrides_allowed` config knob and
  the per-pipeline `periodic_refresh_overrides_allowed` DB flag (both default
  on); when either denies, the file's override is ignored and the system
  default cadence (2 minutes) applies. Denying restores the safe default — it
  never silences polling wholesale. The early-slice `schedule` column on
  `PipelineSource` is retired (unread) in favor of the file field.
- **The raw YAML + hash are stored in the database.** An externally-sourced
  pipeline stores `source_file` (the verbatim YAML) and `source_hash` (its
  SHA-256) on the `Pipeline` row, plus a `PipelineSource` (where it came from:
  a `kind` of `git` / `http` / `file` and its `reference`) and a
  `PipelineSourceState` (last sync / version / error). The stored file is
  retrievable through the API (`GET /api/pipelines/{id}/source`), and
  `GET /api/pipelines/{id}` returns the compiled definition, so the UI and the
  file are two views of the same model.
- **New fields / RPCs / endpoints (this sub-feature).** `PipelineSource` and
  `PipelineSourceState` models (registered in `models.All()`); `source_file` /
  `source_hash` / `source` on `Pipeline` (db); `periodic_refresh_interval` /
  `periodic_refresh_schedule` (from the file) and
  `periodic_refresh_overrides_allowed` (DB flag) on `Pipeline` (db);
  `source_kind` / `source_reference` / `source_version` /
  `source_file_hash` on `PipelineRun` (db); `spec.periodicRefresh` support in
  `internal/pipelinefile` (parse/validate/export); the config knobs
  `pipeline_source.refresh_interval` (system default cadence) and
  `pipeline_source.overrides_allowed` (global gate) (api); source CRUD in the
  database service; the source CRUD endpoints and
  `GET /api/pipelines/{id}/source` (api).
