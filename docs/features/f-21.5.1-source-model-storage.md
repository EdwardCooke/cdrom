# F-21.5.1 · Source model & storage

> Part of [F-21.5 · Externally-sourced pipelines](f-21.5-externally-sourced-pipelines.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The database model for externally-sourced pipelines: a
`PipelineSource` (where a pipeline is pulled from: a `kind` of `git` / `http` /
`filesystem` plus the kind's locator, a refresh `schedule`, and a credential
reference), a `PipelineSourceState` (the last sync's bookkeeping), and the raw
YAML + content hash stored on the `Pipeline` row (`source_file` /
`source_hash`). The source is a **database concept** configured through the API
— it is not in the file — so the same file is portable across source kinds.

**Why.** Keeping the source out of the file means the definition is purely the
definition: the same file can be checked into git, served over HTTP, or mounted
on the filesystem, and where it is pulled from is a deployment concern managed
through the API. Storing the raw YAML + hash makes the loaded definition
retrievable through the API and gives the sync routine (F-21.5.2) a cheap,
authoritative change detector.

**Scope.**
- `internal/models` — a `PipelineSource` (a `kind` of `git` / `http` /
  `filesystem` plus the kind's locator — `url` / `branch` / `path` for git,
  `url` + optional `headers` for http, `path` for filesystem — a `schedule`
  (a cron expression for the scheduled refresh; empty means no scheduled
  refresh), and a `credential` (the name of the `SourceCredential` used to
  authenticate; empty means the source is public / needs no credential)), a
  `PipelineSourceState` (`last_synced_at`, `last_version`, `file_hash`,
  `last_error`), and `source_file` / `source_hash` on the `Pipeline` row;
  registered in `models.All()`.
- `internal/services/database` — source CRUD (attach / update / detach a
  source to / from a pipeline) and the stored YAML + hash.
- `internal/api/server.go` — the **source** CRUD endpoints and
  `GET /api/pipelines/{id}/source` (the `PipelineSource` plus the
  `PipelineSourceState` and the stored `source_file`).

**Acceptance criteria.**
- [ ] A `PipelineSource` has a `kind` (`git` / `http` / `filesystem`) plus the
      kind's locator — `git`: `url` (the git remote), `branch` (the ref to
      track; default `main`), and `path` (the path of the definition file within
      the repo); `http`: `url` (the endpoint that serves the definition file,
      e.g. an object-store URL or a raw-file endpoint) and an optional `headers`
      map (e.g. an `Authorization` header) for endpoints that need it in-band;
      `filesystem`: `path` (an absolute path to the definition file on the
      source-fetcher's host) — a `schedule` (a cron expression for the scheduled
      refresh; empty means no scheduled refresh), and a `credential` (the name
      of the `SourceCredential` used to authenticate; empty means the source is
      public / needs no credential).
- [ ] A `PipelineSourceState` records the last sync's bookkeeping:
      `last_synced_at`, `last_version` (the source's version identifier — the
      git commit hash, an HTTP `ETag`/`Last-Modified`, or the file's mtime — so
      a no-change can be detected cheaply), `file_hash` (the content hash of the
      file at that version), and `last_error` (set when a sync fails, cleared on
      the next success).
- [ ] The raw YAML (`source_file`, verbatim — so it is retrievable through the
      API and is the exact input the compiler ran) and its content hash
      (`source_hash`, the SHA-256 of `source_file`, hex) are stored on the
      `Pipeline` row and retrievable via the API.
- [ ] The pipeline's source (git / http / filesystem) is **not** in the file —
      it is a `PipelineSource` stored in the database and configured through the
      API (source CRUD), so the same file is portable across source kinds; a
      pipeline becomes externally-sourced when a `PipelineSource` is attached to
      it.
- [ ] `GET /api/pipelines/{id}/source` returns the `PipelineSource` (kind,
      url/branch/path, schedule, credential name) plus the
      `PipelineSourceState` (last sync time, last version, file hash, last
      error) and the stored `source_file` (the raw YAML) — how a user sees
      "what definition is currently loaded and where it came from" without
      checking out the source.
- [ ] `GET /api/pipelines/{id}` returns the pipeline's **compiled** definition
      (the same shape the UI editor shows), so the UI and the file are two views
      of the same model.

---

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The source is not in the file.** Where a pipeline is pulled from (a
  `git` / `http` / `filesystem` source, its schedule, and its credential) is a
  **database** concept — a `PipelineSource` row associated with the pipeline —
  not part of the YAML. The file is purely the definition; the source is
  configured through the API and stored in the database. This keeps the file
  portable: the same file can be checked into git, served over HTTP, or mounted
  on the filesystem, and the source that fetches it is a deployment concern,
  not a definition concern.
- **The raw YAML + hash are stored in the database.** An externally-sourced
  pipeline stores `source_file` (the verbatim YAML) and `source_hash` (its
  SHA-256) on the `Pipeline` row, plus a `PipelineSource` (where it came from:
  a `kind` of `git` / `http` / `filesystem` and its locator) and a
  `PipelineSourceState` (last sync / version / error). The stored file is
  retrievable through the API (`GET /api/pipelines/{id}/source`), and
  `GET /api/pipelines/{id}` returns the compiled definition, so the UI and the
  file are two views of the same model.
- **New fields / RPCs / endpoints (this sub-feature).** `PipelineSource` and
  `PipelineSourceState` models (registered in `models.All()`); `source_file` /
  `source_hash` / `source` on `Pipeline` (db); source CRUD in the database
  service; the source CRUD endpoints and `GET /api/pipelines/{id}/source`
  (api).
