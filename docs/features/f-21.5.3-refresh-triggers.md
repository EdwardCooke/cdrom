# F-21.5.3 · Refresh triggers

> Part of [F-21.5 · Externally-sourced pipelines](f-21.5-externally-sourced-pipelines.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The three triggers that drive the sync routine (F-21.5.2): **on a
schedule** (the API's leader-gated source-refresh loop wakes on each source's
`schedule` cron), **when a run is kicked off** (a refresh-on-run hook just
before a run of an externally-sourced pipeline is created), and **manually**
(`POST /api/pipelines/{id}/source/refresh`). All three go through the same sync
routine, so they are behaviorally identical; only the trigger differs.

**Depends on.** [F-21.5.2](f-21.5.2-sync-routine.md) (the sync routine).

**Why.** A schedule keeps the definition current on its own; a refresh-on-run
guarantees "what I just kicked off is what is in the source right now" without
waiting for the next scheduled tick; and a manual refresh is the "I just
pushed, pull it now" path. One routine behind three triggers means they can
never drift apart in behavior.

**Scope.**
- `internal/api` — the **source-refresh loop**: a leader-gated background loop
  (a named lease on the Database service, like the scheduler's loops, F-23)
  that wakes on each source's `schedule` cron and syncs it; a source with no
  schedule is not polled.
- `internal/api` — the **refresh-on-run** hook: just before a run of an
  externally-sourced pipeline is created (manual, cron, webhook, or event
  trigger), the API syncs the source so the run executes the latest reviewed
  definition; a refresh-on-run that fails (e.g. the source is unreachable) does
  **not** block the run — the run proceeds on the last successfully-synced
  definition, and the failure is recorded on the source state and surfaced to
  the UI.
- `internal/api/server.go` — `POST /api/pipelines/{id}/source/refresh`: forces
  an immediate sync (regardless of schedule) and applies the result.

**Acceptance criteria.**
- [ ] An externally-sourced pipeline is refreshed on its schedule (cron): the
      API's **source-refresh loop** (leader-gated via a named lease on the
      Database service, like the scheduler's loops, F-23) wakes on each
      source's `schedule` cron and syncs it; a source with no schedule is not
      polled.
- [ ] An externally-sourced pipeline is refreshed again when a run of it is
      kicked off (manual, cron, webhook, or event trigger): just before the run
      is created, the API performs a **refresh-on-run** so the run executes the
      latest reviewed definition — "what I just kicked off is what is in the
      source right now" — without waiting for the next scheduled tick.
- [ ] A refresh-on-run that fails (e.g. the source is unreachable) does **not**
      block the run: the run proceeds on the last successfully-synced
      definition, and the failure is recorded on the source state and surfaced
      to the UI.
- [ ] A pipeline can be refreshed manually via the API:
      `POST /api/pipelines/{id}/source/refresh` forces an immediate sync
      (regardless of schedule) and applies the result — the "I just pushed,
      pull it now" path.
- [ ] All three triggers go through the same sync routine (F-21.5.2), so they
      are behaviorally identical; only the trigger differs.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Refresh is one routine, three triggers.** A single sync routine (F-21.5.2)
  is driven by (1) the API's leader-gated source-refresh loop (a named lease on
  the Database service, like the scheduler's loops, F-23) on each source's cron
  schedule, (2) a refresh-on-run hook just before a run of an
  externally-sourced pipeline is created, and (3) a manual
  `POST /api/pipelines/{id}/source/refresh`. A sync is serialized per pipeline
  so the triggers cannot race. A refresh-on-run that fails does not block the
  run (it proceeds on the last good definition and records the error); a
  scheduled or manual failure is recorded on the source state.
- **New fields / RPCs / endpoints (this sub-feature).** The `source-refresh`
  background loop (a named lease on the Database service) and the refresh-on-run
  hook (api); `POST /api/pipelines/{id}/source/refresh` (api).
