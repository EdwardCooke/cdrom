# F-21.5.3 · Refresh triggers

> Part of [F-21.5 · Externally-sourced pipelines](f-21.5-externally-sourced-pipelines.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The three triggers that drive the sync routine (F-21.5.2):
**periodically** (the API's leader-gated source-refresh loop syncs each source
at its next-due instant — resolving the EFFECTIVE cadence: the pipeline file's
`spec.periodicRefresh` (its `schedule` cron when set, else its `interval`) when
the admin gate allows it, otherwise the system default of 2 minutes), **when a
run is kicked off** (a refresh-on-run hook just before a run of an
externally-sourced pipeline is created, which also snapshots the source's
location and revision onto the run row), and **manually**
(`POST /api/pipelines/{id}/source/refresh`). All three go through the same sync
routine, so they are behaviorally identical; only the trigger differs.

**Depends on.** [F-21.5.2](f-21.5.2-sync-routine.md) (the sync routine).

**Why.** Periodic refresh keeps the definition current on its own (a
steady-state interval for everyday freshness, a cron for precise timing — e.g.
syncing only during after-hours when load is minimal); putting the cadence in
the file lets owners tune it per pipeline, while the ADMIN GATE (a global
config knob + a per-pipeline DB flag) keeps that power accountable — authors
propose, administrators dispose. A refresh-on-run
guarantees "what I just kicked off is what is in the source right now" without
waiting for the next scheduled tick; and a manual refresh is the "I just
pushed, pull it now" path. One routine behind three triggers means they can
never drift apart in behavior.

**Scope.**
- `internal/api` — the **source-refresh loop**: a leader-gated background loop
  (a named lease on the Database service, like the scheduler's loops, F-23)
  that resolves each source's EFFECTIVE cadence (the file's
  `spec.periodicRefresh` when the admin gate — global
  `pipeline_source.overrides_allowed` ∧ per-pipeline
  `periodic_refresh_overrides_allowed` — allows it; otherwise the system
  default `pipeline_source.refresh_interval` /
  `CDROM_PIPELINE_SOURCE_REFRESH_INTERVAL`, default `120s`), maintains a
  next-due instant per source (the next cron fire when a `schedule` drives,
  otherwise `last_attempt + interval`), and syncs whatever is due; a source
  opted out (a HONORED `interval` of `0` and no cron) is not polled.
- `internal/api` — the **refresh-on-run** hook: just before a run of an
  externally-sourced pipeline is created (manual, cron, webhook, or event
  trigger), the API syncs the source so the run executes the latest reviewed
  definition; a refresh-on-run that fails (e.g. the source is unreachable) does
  **not** block the run — the run proceeds on the last successfully-synced
  definition, and the failure is recorded on the source state and surfaced to
  the UI.
- `internal/api` — the **kickoff provenance stamp**: at run creation, after the
  refresh-on-run hook has settled, the run row records `source_kind`,
  `source_reference`, `source_version`, and `source_file_hash` (the definition
  the run actually executed — the last successful sync's values when the
  kickoff fetch failed); surfaced on `GET /api/runs/{id}`.
- `internal/api/server.go` — `POST /api/pipelines/{id}/source/refresh`: forces
  an immediate sync (regardless of schedule) and applies the result.

**Acceptance criteria.**
- [x] An externally-sourced pipeline is refreshed periodically at its
      EFFECTIVE cadence: the API's **source-refresh loop** (leader-gated via a
      named lease on the Database service, like the scheduler's loops, F-23)
      resolves the file's `spec.periodicRefresh` (its `schedule` cron when set
      — precise timing, e.g. after-hours syncs when load is minimal — else its
      `interval`) when the admin gate allows it, and the system default of 2
      minutes otherwise; it syncs each source at its next-due instant, and a
      source opted out (a HONORED `interval` of `0` and no cron) is not polled.
- [x] The ADMIN GATE is enforced: the global `pipeline_source.overrides_allowed`
      config knob (default on) and the per-pipeline
      `periodic_refresh_overrides_allowed` DB flag (default on, editable
      through the pipeline API) together decide whether the file's
      `periodicRefresh` is honored; when either denies, the pipeline falls
      back to the system default cadence (denial restores the safe default —
      it does not halt polling), and the source view explains the resolution.
- [x] An externally-sourced pipeline is refreshed again when a run of it is
      kicked off: just before a run STARTED THROUGH THE API (manual, webhook)
      is created, the API performs a **refresh-on-run** so the run executes the
      latest reviewed definition — "what I just kicked off is what is in the
      source right now" — without waiting for the next periodic tick. AUTONOMOUS
      FIRES (the scheduler's cron and event loops) originate INSIDE the
      scheduler, which talks only to the Database service (topology rule) and
      cannot reach the fetcher: those runs execute the definition the PERIODIC
      LOOP keeps current (≤ one effective-cadence stale), which is the
      topology-consistent approximation of the guarantee.
- [x] A refresh-on-run that fails (e.g. the source is unreachable) does **not**
      block the run: the run proceeds on the last successfully-synced
      definition, and the failure is recorded on the source state and surfaced
      to the UI.
- [x] When a run is kicked off, the source's location and revision are
      snapshotted onto the run row (`source_kind`, `source_reference`,
      `source_version`, `source_file_hash`), so a run answers “which file, at
      which revision, produced it?” even after the source is repointed or
      detached; when the kickoff fetch fails, the provenance reflects the last
      successful sync.
- [x] A pipeline can be refreshed manually via the API:
      `POST /api/pipelines/{id}/source/refresh` forces an immediate sync
      (regardless of schedule) and applies the result — the "I just pushed,
      pull it now" path.
- [x] All three triggers go through the same sync routine (F-21.5.2), so they
      are behaviorally identical; only the trigger differs.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Refresh is one routine, three triggers.** A single sync routine (F-21.5.2)
  is driven by (1) the API's leader-gated source-refresh loop (a named lease on
  the Database service, like the scheduler's loops, F-23) at each source's
  next-due instant (resolving the effective cadence — the file's
  `spec.periodicRefresh` when the admin gate allows it, else the system
  default of 2 minutes), (2) a refresh-on-run hook just before a run of an
  externally-sourced pipeline is created — which also snapshots the source's
  location and revision onto the run row (kickoff provenance) — and (3) a
  manual `POST /api/pipelines/{id}/source/refresh`. A
  sync is serialized per pipeline so the triggers cannot race. A refresh-on-run
  that fails does not block the run (it proceeds on the last good definition
  and records the error); a periodic or manual failure is recorded on the
  source state.
- **Scale rules (hundreds/thousands of sources).** The loop is built for a
  LARGE fleet of sources:
  - **SKIP-IF-IN-FLIGHT** — a due source whose previous sync is still presumed
    running is SKIPPED (counted `skipped_busy`); the next due instant is tried
    again. An overshooting sync (longer than its interval) therefore yields a
    STEADY rhythm (skip, run, skip…) — never a queued second sync, never
    piled-up debt, never parked goroutines. Pacing is reserved at ISSUANCE
    (conservative: a full interval of quiet after every sync begins).
  - **PER-SYNC TIMEOUT** — every sync runs under a bounded context
    (`pipeline_source.sync_timeout` / `CDROM_PIPELINE_SOURCE_SYNC_TIMEOUT`,
    default `5m`), so a blackholed origin cannot hold a source in flight
    forever — zombies are impossible by construction.
  - **THROTTLABLE CONCURRENCY** — `pipeline_source.max_parallel` /
    `CDROM_PIPELINE_SOURCE_MAX_PARALLEL` (default `0` = UNLIMITED — goroutines
    are cheap; the fetcher self-regulates via its per-repo locks) caps
    simultaneous in-flight syncs; a due source that cannot get a slot is
    DEFERRED to the next tick (counted `skipped_throttled`) — delayed, never
    blocked or starved.
  - **ANTI-PHASE JITTER** — interval-mode due instants carry a stable
    per-source phase offset (±⅛ of the interval, hash-indexed) so fleets of
    identical intervals do not march in lockstep; cron mode stays exact.
  - **METRICS (F-20)** — `cdrom_api_source_syncs_total{outcome}`
    (success / unchanged / error / deferred_peer / skipped_busy /
    skipped_throttled), `cdrom_api_source_sync_duration_seconds{outcome}`,
    `cdrom_api_source_sync_in_flight`, and `cdrom_api_leader_state` (holding
    the source-refresh lease); plus a rate-limited WARN when a sync outpaces
    its own interval.
- **Due-testing beats cron-firing.** The loop paces from the last attempt (not
  the last success), so a failing source is retried on its own cadence — not
  hammered every tick — and `last_error` keeps it diagnosable. Fires missed
  during a leadership gap or outage collapse into a single catch-up sync on
  recovery; there is no backlog replay (definitions converge, and
  refresh-on-run already guards kickoff freshness).
- **New fields / RPCs / endpoints (this sub-feature).** The `source-refresh`
  background loop (a named lease on the Database service; resolves the
  effective cadence honoring the admin gate), the refresh-on-run hook +
  kickoff provenance stamp on the run row (api),
  `POST /api/pipelines/{id}/source/refresh` (api), and the config knobs
  `pipeline_source.refresh_interval` (system default cadence) and
  `pipeline_source.overrides_allowed` (global gate) (api).
- **Coverage.** Unit-tested (cadence resolution, the sync routine's
  change/no-op/failure legs, cross-replica deferral, the loop's poll, the
  endpoint) and END-TO-END by
  `scripts/e2e/15-externally-sourced-pipelines.sh` (attached to a live stack +
  fetcher: bootstrap import, change re-applies + a run executes the new
  definition, no-op, provenance surviving a repoint, the cadence view, the
  gate denial fallback, and the broken-source last-error-with-survivors).
