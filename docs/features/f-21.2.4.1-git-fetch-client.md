# F-21.2.4.1 · Git fetch client

> Part of [F-21.2.4 · Fetch clients](f-21.2.4-fetch-clients.md) · Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **`git` fetch client** — the client that serves a `git` reference
(F-21.2.2) by reading a single file at a branch ref from a repository served by
the on-disk cache (F-21.2.3). It drives the cache's fetch lifecycle
(F-21.2.3.2) — acquire the lock, shallow-clone on a miss or fetch on a hit,
resync on failure — then reads the file at the reference's `path` from the
object store at the branch's tip and produces the `FetchSource` response
(content, version identifier, content hash). A private repository is
authenticated by a `git-ssh` or `git-https` credential (F-21.3) passed in for
the call; a public repository needs no credential.

**Why.** Isolating the git fetch in its own client keeps the rest of the
service (the gRPC contract, F-21.2.1) thin and makes the git-specific behavior
— cache interaction, credential application, and the commit-hash version
identifier — a single, testable unit.

**Scope.**
- The **`git`** client in `internal/services/pipelinesource` — read a single
  file at a branch ref from a repository served by the cache (F-21.2.3).
- Credential application — authenticate a private repository with a `git-ssh`
  or `git-https` credential (F-21.3) passed in for the call.- SSH host-key verification — a per-credential expected host key (strict), a
  built-in set of common provider keys (GitHub, GitLab, Bitbucket, Azure
  DevOps) embedded in the binary, and the runtime-managed host keys the API
  passes in (`FetchSourceRequest.known_hosts`); unknown hosts are rejected,
  key mismatches are rejected.
- Runtime-managed host keys — the `SSHKnownHost` table (Database service), the
  `ListSSHKnownHosts` / `CreateSSHKnownHost` / `DeleteSSHKnownHost` RPCs, the
  API endpoints `GET/POST/DELETE /api/ssh-known-hosts` (gated on
  `ssh-known-hosts.can-view` / `ssh-known-hosts.can-manage`), and the
  `known_hosts` field on `FetchSourceRequest`.
- The version identifier — the branch's commit hash after the fetch/clone.
- The content hash — the SHA-256 of the file's content.

**Acceptance criteria.**
- [x] A file can be fetched from a **git** repository (a single file at a
      branch/ref; a private repository is authenticated by a `git-ssh` or
      `git-https` credential).
- [x] SSH host keys are verifiable without per-credential configuration: the
      built-in common provider keys (GitHub, GitLab, Bitbucket, Azure DevOps)
      are embedded in the binary, and a host not in the set is rejected while a
      key mismatch is rejected.
- [x] An admin can **add and remove** SSH host keys at runtime via the API
      (`GET/POST/DELETE /api/ssh-known-hosts`, gated on
      `ssh-known-hosts.can-view` / `ssh-known-hosts.can-manage`), so a
      self-hosted or corporate-firewalled git host is not blocked; the keys are
      stored in the database and passed to the fetcher on each git-ssh fetch
      (`FetchSourceRequest.known_hosts`).
- [x] The **`git`** client reads the file from the repository served by the
      cache (F-21.2.3) and returns the branch's commit hash as the version
      identifier; a private repository is authenticated by a `git-ssh` or
      `git-https` credential (F-21.3) passed in for the call, and a public
      repository needs no credential.
- [x] The client drives the cache's fetch lifecycle (F-21.2.3.2): it acquires
      the repository's lock (F-21.2.3.3), shallow-clones the repository on a
      cache miss or fetches the requested branch on a cache hit, and resyncs
      (re-clones) if a fetch fails.
- [x] The client returns the file's **content** and its **content hash**
      (SHA-256 of the content) alongside the branch's commit hash as the
      version identifier.
- [x] A fetch failure (unreachable repository, missing file at the path, auth
      failure) returns a clear gRPC error the API can surface on the source's
      state (F-21.5).

## The git fetch client

The `git` client serves a `git` reference (F-21.2.2) — `<repo>@<branch>[<path>]`
— by reading the file at `path` from a repository served by the on-disk cache
(F-21.2.3):

- **Cache interaction.** The client drives the cache's fetch lifecycle
  (F-21.2.3.2): it acquires the repository's lock (F-21.2.3.3), then — on a
  cache miss — shallow-clones (depth 1) the repository as a **bare object
  store** for the requested branch, or — on a cache hit — fetches the requested
  branch into the shared object store. If a fetch fails, the client resyncs by
  discarding the store and re-cloning from upstream. The clone/fetch are
  performed by **go-git** (a pure-Go git implementation), so the fetcher has no
  external dependency on the `git` binary. The clone is **shallow (depth 1)**
  and the fetch is a **plain incremental fetch** into the already-shallow
  store: the client only ever reads the file at the branch ref, so the store
  holds the branch tip plus only the commits added since the last fetch (the
  shallow boundary stays at the original clone point) — never the full history
  — keeping the on-disk cache small for large repositories. Because the store
  is bare and shared across branches, a request for a different branch is a
  cheap incremental fetch and the file is read from the objects at that
  branch's tip (no worktree, no reset, no stale-branch content).
- **Credential application.** A private repository is authenticated by a
  `git-ssh` or `git-https` credential (F-21.3) passed in for the call: a
  `git-https` credential authenticates the clone/fetch with HTTP basic auth
  (username + token, the token never logged), and a `git-ssh` credential uses
  the private key for the SSH handshake. A public repository needs no
  credential.
- **SSH host-key verification.** A `git-ssh` fetch verifies the server's host
  key in this order: (1) if the credential carries an expected host key, it is
  verified strictly (it takes precedence); (2) otherwise the **combined
  known_hosts set** is used — the built-in common provider keys (GitHub,
  GitLab, Bitbucket, and Azure DevOps, embedded in the binary), plus the
  **runtime-managed host keys** the API passes in for the fetch (see below) —
  so a known host is verified strictly without per-credential configuration;
  (3) a host NOT in the set is rejected (no lenient accept-new), and a key
  **mismatch** for a known host is rejected (the MITM case). The built-in
  common provider keys are refreshed by `scripts/update-known-hosts.sh`
  (ssh-keyscan), which rewrites
  `internal/services/pipelinesource/common_known_hosts`.
- **Runtime-managed host keys.** The combined set includes the host keys an
  admin adds at runtime via the API (`GET/POST/DELETE /api/ssh-known-hosts`,
  gated on `ssh-known-hosts.can-view` / `ssh-known-hosts.can-manage`). They are
  stored in the database (the `SSHKnownHost` table, owned by the Database
  service) and passed to the fetcher on each git-ssh fetch
  (`FetchSourceRequest.known_hosts`, OpenSSH known_hosts lines). This is how a
  self-hosted or corporate-firewalled git host gets strict host-key
  verification without a redeployment and without editing the fetcher's
  built-in keys — the upcoming UI manages them through these endpoints.
- **Reading the file.** After the fetch/clone, the client reads the file at
  `path` from the object store at the requested branch's tip commit (no
  worktree).
- **Version identifier.** The response's version identifier is the requested
  branch's commit hash (the tip of the branch after the fetch/clone).
- **Content hash.** The response's content hash is the SHA-256 of the file's
  content.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The git client reads from the cache.** The `git` fetch client serves a
  `git` reference by reading the file at `path` from a repository served by the
  on-disk cache (F-21.2.3), driving the cache's fetch lifecycle (F-21.2.3.2) —
  lock, shallow-clone-or-fetch, resync-on-failure — and returns the requested
  branch's commit hash as the version identifier. A private repository is
  authenticated by a `git-ssh` or `git-https` credential (F-21.3) passed in for
  the call. The git operations are performed by **go-git** (a pure-Go git
  implementation), so the fetcher has no external dependency on the `git`
  binary. The cache holds a **bare object store** per repository URL (shared
  across branches); the file is read from the objects at the requested
  branch's tip — no worktree, no reset.
- **New fields / RPCs / endpoints (this sub-feature).** The `git` fetch client
  in `internal/services/pipelinesource` (cache interaction, credential
  application, SSH host-key verification, file read, commit-hash version
  identifier); the built-in common provider host keys (embedded in the binary);
  the `SSHKnownHost` model and the `ListSSHKnownHosts` / `CreateSSHKnownHost` /
  `DeleteSSHKnownHost` RPCs in the Database service; the `known_hosts` field on
  `FetchSourceRequest`; and the API endpoints `GET/POST/DELETE
  /api/ssh-known-hosts` (gated on `ssh-known-hosts.can-view` /
  `ssh-known-hosts.can-manage`).
