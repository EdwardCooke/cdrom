# F-21.2.4.1 · Git fetch client

> Part of [F-21.2.4 · Fetch clients](f-21.2.4-fetch-clients.md) · Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **`git` fetch client** — the client that serves a `git` reference
(F-21.2.2) by reading a single file at a branch ref from a repository served by
the on-disk cache (F-21.2.3). It drives the cache's fetch lifecycle
(F-21.2.3.2) — acquire the lock, clone or refetch (subject to the debounce),
resync on failure — then reads the file at the reference's `path` from the
checkout and produces the `FetchSource` response (content, version identifier,
content hash). A private repository is authenticated by a `git-ssh` or
`git-https` credential (F-21.3) passed in for the call; a public repository
needs no credential.

**Why.** Isolating the git fetch in its own client keeps the rest of the
service (the gRPC contract, F-21.2.1) thin and makes the git-specific behavior
— cache interaction, credential application, and the commit-hash version
identifier — a single, testable unit.

**Scope.**
- The **`git`** client in `internal/services/pipelinesource` — read a single
  file at a branch ref from a repository served by the cache (F-21.2.3).
- Credential application — authenticate a private repository with a `git-ssh`
  or `git-https` credential (F-21.3) passed in for the call.
- The version identifier — the branch's commit hash after the fetch/clone.
- The content hash — the SHA-256 of the file's content.

**Acceptance criteria.**
- [ ] A file can be fetched from a **git** repository (a single file at a
      branch/ref; a private repository is authenticated by a `git-ssh` or
      `git-https` credential).
- [ ] The **`git`** client reads the file from the repository served by the
      cache (F-21.2.3) and returns the branch's commit hash as the version
      identifier; a private repository is authenticated by a `git-ssh` or
      `git-https` credential (F-21.3) passed in for the call, and a public
      repository needs no credential.
- [ ] The client drives the cache's fetch lifecycle (F-21.2.3.2): it acquires
      the repository's lock (F-21.2.3.3), clones the repository on a cache miss
      or refetches it on a cache hit (subject to the debounce), and resyncs
      (re-clones) if a fetch fails.
- [ ] The client returns the file's **content** and its **content hash**
      (SHA-256 of the content) alongside the branch's commit hash as the
      version identifier.
- [ ] A fetch failure (unreachable repository, missing file at the path, auth
      failure) returns a clear gRPC error the API can surface on the source's
      state (F-21.5).

## The git fetch client

The `git` client serves a `git` reference (F-21.2.2) — `<repo>@<branch>[<path>]`
— by reading the file at `path` from a repository served by the on-disk cache
(F-21.2.3):

- **Cache interaction.** The client drives the cache's fetch lifecycle
  (F-21.2.3.2): it acquires the repository's lock (F-21.2.3.3), then — on a
  cache miss — clones the repository into a new cache directory, or — on a
  cache hit — refetches it from upstream (a `git fetch` of the branch + a hard
  reset, subject to the debounce). If a fetch fails, the client resyncs by
  discarding the checkout and re-cloning from upstream.
- **Credential application.** A private repository is authenticated by a
  `git-ssh` or `git-https` credential (F-21.3) passed in for the call: a
  `git-https` credential authenticates the clone/fetch as
  `https://<username>:<token>@host/…` (the token is never logged), and a
  `git-ssh` credential uses the private key for the SSH handshake and verifies
  the server's host key against the expected host key. A public repository
  needs no credential.
- **Reading the file.** After the fetch/clone, the client reads the file at
  `path` from the checkout at the branch ref.
- **Version identifier.** The response's version identifier is the branch's
  commit hash after the fetch/clone.
- **Content hash.** The response's content hash is the SHA-256 of the file's
  content.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The git client reads from the cache.** The `git` fetch client serves a
  `git` reference by reading the file at `path` from a repository served by the
  on-disk cache (F-21.2.3), driving the cache's fetch lifecycle (F-21.2.3.2) —
  lock, clone-or-refetch, resync-on-failure — and returns the branch's commit
  hash as the version identifier. A private repository is authenticated by a
  `git-ssh` or `git-https` credential (F-21.3) passed in for the call.
- **New fields / RPCs / endpoints (this sub-feature).** The `git` fetch client
  in `internal/services/pipelinesource` (cache interaction, credential
  application, file read, commit-hash version identifier).
