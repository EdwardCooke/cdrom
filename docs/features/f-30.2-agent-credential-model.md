# F-30.2 · Agent credential model & lifecycle

> Part of [F-30 · Agent credentials & the agent/worker topology](f-30-agent-credentials-and-topology.md) · Phase 8 — Target credentials & execution topology · [Feature index](../Features.md)

**What.** The ISSUING/TRACKED side of target identity: a durable, revocable
**agent credential** — an IdP-**signed JWT** wrapping a **tracked row** in the
database (the JWT's `jti` is the row id). An administrator (via the upcoming
UI, or the API directly) issues one for a named agent; the plaintext JWT is
returned **exactly once**. The row is the authority for liveness (active,
unexpired, unrevoked), so **revocation is a row mutation** — no key ceremony.
Operations: **issue**, **renew** (extend the row's deadline; the SAME JWT
keeps working — self-service by the agent presenting its own valid
credential, or by an admin), **rotate** (successor JWT; predecessor retired),
**revoke** (immediate), **list/get** (metadata only — never JWT material).
The JWT is DISTRIBUTED to the agent as a **credential file** (persisted by the
administrator/operator from the one-shot response; the agent SOURCES its
token from that file, never from the environment) — see Distribution below.
Consumption-side enforcement (who may present what, stream teardown,
transport) is F-30.3.

**Entity.** `AgentCredential` (registered in `models.All()`), owned by the
Database service, mutated only through the IdP's gRPC surface (the F-25
shape: *logic in the IdP, API is a thin proxy*). Fields: `id` (== JWT `jti`),
`agent_name` (several rows may share a name during rotation overlap; at most
one ACTIVE row per name is the operating assumption), `issued_by` (acting
principal), `description`, `created_at`, `expires_at`, `replaced_by_id`
(set on rotation), `revoked_at` + `revoked_reason` (set on revocation),
`last_seen_at` (bumped on verified presentation, throttled — F-30.3). The
JWT itself is **never stored**: its signature is the custody proof.

**Claims.** `iss` = IdP issuer; `sub` = `agent:<name>`; `aud` = the API's
configured audience(s); `jti` = credential id; `iat`; `exp` = a **generous
placeholder** (weeks). The API never enforces `exp` — mirroring the
job-token rule in `internal/api/jobsauth.go`; the ROW'S `expires_at` is the
real deadline. No secret material, no group/environment claims (those remain
registration assertions, F-30.3).

**Endpoints** (thin API proxies to the IdP; the agent acts on ITS OWN
credential by presenting it — humans act by RBAC permission):

| Method & path | Effect | Guard |
|---|---|---|
| `POST /api/agents/{name}/credentials` | Issue: IdP signs + stores; plaintext JWT returned once | `agents.can-manage` |
| `GET /api/agents/{name}/credentials` | List rows (metadata, no JWT material) | `agents.can-view` |
| `POST /api/agents/{name}/credentials/{id}/renew` | Extend `expires_at` to now + TTL (same JWT keeps working) | presenter holds a valid credential for `{name}` (self-service) **OR** `agents.can-manage` |
| `POST /api/agents/{name}/credentials/{id}/rotate` | Retire row, issue successor; new JWT returned once | `agents.can-manage` |
| `DELETE /api/agents/{name}/credentials/{id}` | Revoke (immediate) | `agents.can-manage` |

Issuance/renew/rotate/revoke are **audited** (F-15) with the acting
principal. Secret-value hygiene: the JWT travels only in the one-shot
response body and in the agent's own config/memory.

**Configuration.** IdP: `auth.agent_credentials.ttl` (expiry horizon for
issued/renewed credentials; suggested default 30 days). Agent:
`credential.file` (path to the credential file; REQUIRED — the agent REFUSES
TO BOOT without one, with a diagnostic naming the expected path) and
`auto_renew.ahead_of_expiry` (renew this long before the row's `expires_at`;
suggested default 24 h) with jittered retry on failure.

**Distribution (credential file).** Because the plaintext JWT is returned
exactly ONCE, reaching the agent is a DISTRIBUTION problem, and the answer is
a file, not an environment variable:

- The administrator/operator persists the one-shot JWT to the agent's
  credential file (the UI's "give it to the admin" flow ends here). Writes
  are ATOMIC (DOT-PREFIXED temp file + rename, so the agent's watcher never
  sees in-flight writes) and the file is chmod `0600` (owner rw only) and
  never logged. The mechanics are factored into the shared
  `internal/credfile` primitive (`WriteAtomically` / `Read`): restrictive
  perms, torn-read immunity, whitespace-tolerant reads, and a DISTINCT
  diagnosable error for a missing file (the agent's boot refusal, F-30.3).
  Landings: race-tested rotation cycle, contended-reader invariant, watcher
  quiescence, and failure leaves the original intact.
- The agent SOURCES its token from the file at BOOT (parse: trim whitespace;
a PEM-like `-----BEGIN CDROM AGENT CREDENTIAL-----` envelope is OPTIONAL —
bare JWT is the canonical form) and presents it on every target RPC (F-30.3).
- **Rotated tokens OVERWRITE the file.** The agent WATCHES the file (debounced
  mtime/hash comparison, ~1 s granularity) and ADOPTS a changed token LIVE —
  so a rotation needs NEITHER an agent restart NOR a window of failed
  heartbeats: the old `jti` is still valid during the overlap (the retired
  row's successors are independent), and the agent's next RPC presents the
  successor. Restart-after-rotation is equally safe: the file already holds
  the successor, so a cold boot re-registers cleanly.
- **Why a file and not the environment.** Env vars leak into process
  listings (`/proc/*/environ`), are inherited by EVERY child process —
  critically, the per-job WORKER subprocesses violate F-30.4's "the agent
  credential never appears in the worker's env" — and cannot be UPDATED
  without a restart. A file is updatable in place, permission-controlled,
  and distributable by any operator tooling (ansible, secret manager, scp).

**Rotation without disturbance (requirement).** Renew is a row extension —
the presented JWT is untouched, so renewal CAN NEVER break a live session.
Rotate/retire: the API tears down affected `WatchJobs` streams and rejects
heartbeats bearing the dead `jti` (F-30.3); the operator OVERWRITES the
credential file with the successor JWT (returned once by the rotate call),
the agent's file-watch adopts it live (or the next cold boot sources it), and
the agent reconnects within its watch-backoff (≤ 2 s) — the poll path (F-23)
covers any assignments missed meanwhile. **Running workers are UNAFFECTED in all
cases** — they authenticate with their own job tokens, which neither
operation touches.

**Lapse.** If a credential expires unrenewed, the agent loses its identity:
it stops watching/new spawns, ceases heartbeats (the watchdog marks it dead;
fan-out derivation proceeds per the F-16/derivation rules), and **lets
in-flight workers finish** (their job tokens are independent). It exits
non-zero with a diagnostic; under a process supervisor (systemd unit,
Windows service, k8s workload) the non-zero exit drives automatic restart,
which settles once a valid credential exists.

**Why.** Bootstrap and eviction. Today a target's identity is its transport
credential (a mesh client cert, or nothing on plaintext): provisioning a new
machine copies somebody's cert, and there is no way to evict one. A tracked
JWT gives the UI/admin a first-class "issue a token for this machine" flow
and instant, auditable revocation.

**Design decisions.**
- **Signed JWT wrapper + tracked row = separable concerns.** The signature
  proves the IdP issued it; the row (looked up by `jti`) decides life.
  Revocation is a row mutation — propagates through F-30.3's short liveness
  cache, and is uniformly observable (`last_seen_at`, audit).
- **Renew ≠ rotate (contrast with F-25).** F-25's "update" edits metadata
  without touching the secret; here RENEW extends the DEADLINE without
  touching the JWT (structural no-break), and ROTATE mints a NEW JWT
  retiring the old. Both exist because the agent needs autonomous survival
  (renew) and administrators need compromise-response (rotate/revoke).
- **Logic in the IdP, API thin, row in the Database service** — the F-25
  division of labor, replicated so multi-replica agreement is free.
- **The credential file is the distribution medium; the environment is
  banned.** Exactly-once JWTs need a DURABLE, UPDATABLE resting place that
  survives agent restarts and outlives the one-shot HTTP response. A file
  provides that (atomic overwrite on rotation, `0600`, no process-listing
  exposure, no leakage into worker subprocess env — the latter is a HARD
  F-30.4 requirement). This is deliberately asymmetric with the WORKER's
  job token, which IS env-carried: job tokens are short-lived per-job
  mandates handed parent→child at spawn, whereas the agent credential is a
  long-lived identity the agent must recover autonomously after any reboot.

**Remaining criteria — MOVED to F-30.3.** The four below govern how the
AGENT obtains and maintains the credential (file sourcing, auto-renew timing,
rotation adoption, distribution mechanics); they travel with F-30.3's
mandatory presentation, where they are restated and expanded. Every
IdP/API-side prerequisite landed in this feature:
- TTL (IdP-side) and renew-ahead (agent-side) are configurable; the agent's
  auto-renew timer fires within its configured window. _(IdP-side half
  LANDED here: `auth.agent_credentials.ttl` /
  `CDROM_IDP_AGENT_CREDENTIAL_TTL` feed issue/renew. Timer + window: F-30.3._)
- The agent BOOTS from its credential file (sources the token there, not from
  the environment) and REFUSES TO START with a diagnostic when the file is
  missing or unparsable.
- Overwriting the credential file with a rotated JWT is ADOPTED by the
  running agent (file-watch, debounced) without a restart; a cold boot after
  rotation likewise registers cleanly. During the rotation overlap no running
  job is disturbed.
- The credential file is written atomically (temp + rename) and carries
  restrictive permissions (`0600`); the JWT never appears in logs, argv, or
  any child process's environment. _(The shared write/read primitive landed
  EARLY in `internal/credfile` so F-30.3's agent merely consumes it._)
