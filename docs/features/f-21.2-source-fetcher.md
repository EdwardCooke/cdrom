# F-21.2 · Source-fetcher service

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature builds the **source-fetcher** — a dedicated, standalone gRPC
service that performs the actual fetch of a pipeline definition file named by a
**reference** (`git:…`, `http:…`, or `file:…`): a **git** clone/fetch served
from a rolling 24-hour on-disk repository cache, an **HTTP/HTTPS** GET, or a
read of a file on the **local filesystem** (rooted in a configured directory).
It is a separate process so the API and scheduler never need git, network
egress, or the source's filesystem.

**What.** A new service — `cmd/pipelinesource` (entrypoint) with logic in
`internal/services/pipelinesource` — in the same shape as the other services
(`db`, `scheduler`, `artifacts`, `idp`). It exposes one RPC, `FetchSource`,
which takes a **reference** (a `<type>:<spec>` string naming the kind and the
file to retrieve) and an optional credential (the plaintext secret material,
when one is needed) and returns the file's content, its version identifier, and
its content hash. The fetcher holds no pipeline definitions, no credentials,
and no encryption key at rest; its only on-disk state is a transient,
self-pruning **git repository cache** (a rolling 24 hours, below). It only ever
performs a single fetch per call.

**Why.** Keeping the fetch out of the API and scheduler means neither needs git
installed, outbound network egress, or the source's filesystem. The fetcher can
be run with a network policy that allows only the repos/endpoints it must reach,
and it can be scaled or replaced independently of the control plane. It also
keeps the API's process free of long-running git operations — and repeated
fetches of the same repository are served from the fetcher's local cache
(refetched from upstream on a debounce) instead of re-cloning.

**Scope.**
- `cmd/pipelinesource` + `internal/services/pipelinesource` — the **source
  fetcher**: a standalone gRPC server (a new process, like `db` / `scheduler` /
  `artifacts` / `idp`) that performs the actual fetch — a git clone/fetch from
  its on-disk repository cache, an HTTP GET, or a rooted local file read — and
  returns the file's content, version, and hash. It holds no definitions, no
  credentials, and no key at rest (its only on-disk state is the transient git
  repository cache) and is dialed **only by the API** over gRPC (mutual TLS
  when a CA is configured).
- `proto/cdrom/pipelinesource/v1/` — the fetcher's gRPC API (`FetchSource`,
  plus the `SourceCredential` message); generated code in `internal/gen/`
  (`make proto`).
- The fetcher's git / HTTP / filesystem clients (a single file at a ref / URL /
  rooted path, authenticated by a `SourceCredential` passed in for that one
  call when one is needed).
- The fetcher's **git repository cache** — a (shared) on-disk cache of
  checked-out repositories (a rolling 24 hours), a text index file (updated
  atomically), a per-repository lock (so multiple fetcher replicas sharing the
  cache never race), a configurable fetch debounce, and a background cleanup
  thread that prunes inactive repositories.
- `internal/config` — the fetcher's listen address
  (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), its git
  repository-cache root (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, default the
  `repositories` directory under the OS temp directory), its repository
  **fetch debounce** (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`, a duration;
  a recently fetched repository is not refetched within the window), its
  local-filesystem root for `file:` references (`CDROM_PIPELINE_SOURCE_FILE_ROOT`;
  the `file` kind is disabled when it is unset), and its dedicated metrics port
  (F-20).

**Acceptance criteria.**
- [ ] A file can be fetched from a **git** repository (a single file at a
      branch/ref; a private repository is authenticated by a `git-ssh` or
      `git-https` credential), an **HTTP/HTTPS** endpoint (a GET whose request
      headers come from the source's `http` credential — a credential is
      optional), or a file on the **local filesystem** (a path resolved against
      the fetcher's configured filesystem root).
- [ ] The fetch is named by a **reference** — a `<type>:<spec>` string with
      `<type>` of `git` / `http` / `file` (The reference format) — and
      `FetchSource` parses it to select the kind and the locator; an unknown
      type is a clear error.
- [ ] A **`git`** reference is `<repo>@<branch>[<path>]`: the branch ref may
      contain `/` (and any other character git allows in a ref), and the file
      path is wrapped in `[]`. The first **unescaped** `@` is the branch
      separator, so a `@` that is part of the repository (the `git@host` in an
      SSH remote, or a literal `@` in an HTTPS path) or part of the branch is
      escaped as `\@`; a literal `[` / `]` / `\` is escaped as `\[` / `\]` /
      `\\`. The reference must end immediately after the closing `]`.
- [ ] `FetchSource` returns the file's content, its **version identifier**
      (the git commit hash, an HTTP `ETag`/`Last-Modified`, or the file's mtime),
      and its **content hash** (SHA-256 of the content).
- [ ] **Git repositories are cached on disk for a rolling 24 hours**: a
      checked-out repository is pruned only after 24 hours without use, and
      every fetch of the repository updates its last-accessed timestamp, so an
      actively used repository is never pruned.
- [ ] The **cache root** is configurable at the process level
      (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`) and defaults to a `repositories`
      directory under the OS temp directory (e.g. `/tmp/repositories` on Linux,
      `%TEMP%\repositories` on Windows).
- [ ] A **text index file** at the cache root records, per cached repository,
      the repository directory, the repository URL, the last-accessed Unix
      epoch timestamp, and the last-fetched Unix epoch timestamp; it is updated
      **atomically** (the new content is written to a temp file and renamed over
      the index) on every change.
- [ ] A cached repository's **directory name** is a Unix epoch timestamp and an
      incrementing counter (e.g. `1761024000-3`) — characters that are safe on
      both Windows and Linux filesystems.
- [ ] A **cleanup thread** (a background goroutine) periodically walks the
      cache and deletes repositories that have been inactive for more than 24
      hours; before a directory is pruned, its entry is removed from the index
      file.
- [ ] On a fetch, the repository's last-accessed timestamp in the index file
      is updated; if the repository has no entry, a new cache directory is
      created, the repository is cloned into it, and a new index entry is added.
- [ ] Every time a file is requested from a repository, the repository is
      **refetched from upstream** (a `git fetch` of the branch + a hard reset to
      the fetched ref), so upstream changes — including a **force push** — are
      brought down fresh.
- [ ] A fetch that fails (a diverged / non-fast-forward state, local corruption,
      a transient error) **resyncs** the repository: the checkout is discarded
      and the repository is re-cloned from upstream; if the re-clone also fails,
      the fetch fails with a clear error.
- [ ] A repository is **locked** while it is being cloned, fetched, or resynced
      (a per-repository OS file lock — `flock` on Linux, `LockFileEx` on
      Windows — with a stale-lock timeout), so multiple fetcher replicas sharing
      the cache (e.g. two pods on a PVC) never read a half-written checkout or
      double-fetch.
- [ ] A recently fetched repository is not refetched again within the
      **debounce window** (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`, a
      configurable duration); the last-fetched timestamp is shared in the index
      file so the debounce is effective across replicas.
- [ ] A **`file:`** reference is resolved against the fetcher's configured
      local-filesystem root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`): a reference of
      `file:/shared-variables.yaml` with a root of `/shared` reads
      `/shared/shared-variables.yaml`, and the resolved path must stay within
      the root. When no root is configured, the `file` kind is **disabled** and
      a `file:` fetch fails with a clear error.
- [ ] The fetcher is a **standalone gRPC server** dialed **only by the API**;
      with a TLS CA configured the connection uses mutual TLS, and without one
      it falls back to plaintext (local dev) — the same convention as the other
      services (`internal/grpcutil`).
- [ ] The fetcher holds **no pipeline definitions, no credentials, and no
      encryption key at rest**; a credential is passed in for one fetch and is
      never persisted or logged. Its only on-disk state is the transient git
      repository cache, which is safe to lose (a re-clone rebuilds it).
- [ ] The fetcher's address comes from config / env
      (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), and it serves
      its own `/metrics` + `/healthz` on a dedicated metrics port (F-20).
- [ ] A fetch failure (unreachable repo/endpoint, missing file, auth failure,
      an unknown reference type, or a `file:` reference with no root
      configured) returns a clear gRPC error the API can surface on the
      source's state (F-21.5).

## The source-fetcher service

The actual fetch is done by a dedicated **source-fetcher** service — a separate
process (`cmd/pipelinesource`, logic in `internal/services/pipelinesource`), in
the same shape as the other services (`db`, `scheduler`, `artifacts`, `idp`):

- **A standalone gRPC server.** It exposes one RPC, `FetchSource`, which takes a
  **reference** (a `<type>:<spec>` string — `git` / `http` / `file`) and an
  optional credential (the plaintext secret material, when one is needed) and
  returns the file's content, its version identifier, and its content hash. The
  fetcher holds no pipeline definitions, no credentials, and no encryption key
  at rest; its only on-disk state is the transient git repository cache (below).
  It performs a single fetch per call.
- **Dialed only by the API, over gRPC.** The API is the only caller (the same
  topology rule as the other services: the API talks to everything else). The
  connection uses **mutual TLS** when a TLS CA is configured (`TLSConfig` in
  `internal/config`; creds built in `internal/grpcutil`) and falls back to
  plaintext without one (local dev) — exactly the convention the other services
  follow. The fetcher's address comes from config / env
  (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), and it serves its
  own `/metrics` + `/healthz` on a dedicated metrics port (F-20).
- **Why a separate process.** Keeping the fetch out of the API and scheduler
  means neither needs git installed, outbound network egress, or the source's
  filesystem. The fetcher can be run with a network policy that allows only the
  repos/endpoints it must reach, and it can be scaled or replaced independently
  of the control plane. It also keeps the API's process free of long-running
  git operations — repeated fetches of the same repository are served from the
  fetcher's local cache (refetched from upstream on a debounce) instead of
  re-cloning.
- **Protos.** `proto/cdrom/pipelinesource/v1/` defines `FetchSource` (and the
  `SourceCredential` message); generated code is committed under
  `internal/gen/` (`make proto`). The service impl lives in
  `internal/services/pipelinesource/server.go` and implements the generated
  `*Server` interface (embedding `Unimplemented*Server`), per the gRPC
  conventions.

### The reference format

A fetch is named by a single **reference** string — `<type>:<spec>`, where
`<type>` is the kind of source and `<spec>` is the kind-specific locator. The
reference is the shared syntax for naming a definition file: the source-fetcher
parses it to perform the fetch, and the same syntax is what a file's imports
(F-21.4) and a `PipelineSource` (F-21.5.1) use to point at a file.

| Type   | Spec | Example |
|--------|------|---------|
| `git`  | `<repo>@<branch>[<path>]` — the git remote, the branch ref, and the file path wrapped in `[]` (a `@` in the repo or branch is escaped as `\@`) | `git:https://github.com/edwardcooke/cdrom.git@main[/some/path/file.yaml]` |
| `http` | the URL of the endpoint that serves the file | `http:https://www.example.com/some/file.yaml` |
| `file` | the path of the file, resolved against the fetcher's configured local-filesystem root | `file:/shared-variables.yaml` |

**`git`** — `<repo>@<branch>[<path>]`:

- `<repo>` — the git remote, in the SSH form
  (`ssh://github.com:EdwardCooke/cdrom.git`) or the HTTPS form
  (`https://github.com/EdwardCooke/cdrom.git`).
- `<branch>` — the branch ref to track (e.g. `main`); it may contain `/` and
  any other character git allows in a ref. The `@<branch>` segment is written
  explicitly even for the default branch.
- `[<path>]` — the path of the file within the repository, wrapped in square
  brackets (e.g. `[/some/path/file.yaml]`).

**Escaping.** A backslash `\` escapes the next character. The structurally
significant characters — `@` (the branch separator), `[` and `]` (the path
brackets), and `\` itself — must be escaped to appear literally:

| Literal | Written as |
|---------|-----------|
| `@`     | `\@`      |
| `[`     | `\[`      |
| `]`     | `\]`      |
| `\`     | `\\`      |

The only **unescaped** `@` in the reference is the branch separator. Any `@`
that is part of the repository — the `git@host` in an SSH remote, or a literal
`@` in an HTTPS path — or part of the branch must be written as `\@`.

**Parsing.** The reference is parsed left to right, honoring escapes:

1. The first **unescaped** `@` is the branch separator; the text before it
   (escapes resolved) is the repository.
2. The first **unescaped** `[` after the separator opens the path; the text
   between the separator and the `[` (escapes resolved) is the branch.
3. The first **unescaped** `]` after the opener closes the path; the text
   between the brackets (escapes resolved) is the path.
4. The reference must end immediately after the closing `]`.

**Examples.**

- `git:https://github.com/edwardcooke/cdrom.git@main[/some/path/file.yaml]`
  → repo `https://github.com/edwardcooke/cdrom.git`, branch `main`, path
  `/some/path/file.yaml`.
- `git:ssh://github.com:EdwardCooke/cdrom.git@main[/path/to/file.yaml]`
  → an SSH remote, branch `main`,
  path `/path/to/file.yaml`.
- `git:https://somegit.com/edward\@test/cdrom.git@branch\@name[/test/aweird\]path/file.yaml]`
  → repo `https://somegit.com/edward@test/cdrom.git` (a literal `@` in the
  path, escaped), branch `branch@name` (a literal `@`, escaped), path
  `/test/aweird]path/file.yaml` (a literal `]`, escaped).

**`http`** — the full URL of the endpoint that serves the file (e.g. an
object-store URL or a raw-file endpoint). Request headers (e.g. an
`Authorization` header) are not part of the reference — they come from the
source's `http` credential (F-21.3), which makes a credential **optional**: an
endpoint that needs no authentication is fetched with a plain GET.

**`file`** — a path resolved against the fetcher's configured local-filesystem
root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`): the file is read from `<root><path>`.
For example, a reference of `file:/shared-variables.yaml` with a root of
`/shared` reads `/shared/shared-variables.yaml`. The root keeps the fetcher from
reading arbitrary files on its host; when no root is configured the `file` kind
is disabled.

### The three source kinds

`FetchSource` parses the reference and performs one of three fetches:

- **`git`** — the reference names the repository, the branch ref, and the path
  of the definition file within the repo. The fetcher serves the repository
  from its **on-disk cache** (below): a cached checkout is refetched from
  upstream (subject to the debounce), or a repository with no cache entry is
  cloned into a new cache directory. It reads the file at `path` and returns
  the branch's commit hash as the version identifier. A private repository is
  authenticated by a `git-ssh` or `git-https` credential (F-21.3) passed in
  for the call; a public repository needs no credential.
- **`http`** — the reference is the endpoint that serves the definition file
  (e.g. an object-store URL or a raw-file endpoint). The fetcher does a GET and
  uses the response body as the file. Request headers are supplied by the
  source's `http` credential (F-21.3 — a `token` sent in a configurable
  `header`, default `Authorization: Bearer <token>`); there are no in-band
  headers on the reference, and a credential is **optional** — an endpoint that
  needs no authentication is fetched with a plain GET. It returns the
  `ETag`/`Last-Modified` as the version identifier.
- **`file`** — the reference is a path resolved against the fetcher's
  configured local-filesystem root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`): the
  file is read directly from `<root><path>`; no network is involved and the
  file is not cached. This is the kind for a definition that is mounted into
  the fetcher's pod (e.g. a ConfigMap or a volume) and is "pulled" by
  re-reading the file. It returns the file's mtime as the version identifier.
  When no root is configured the kind is disabled and a `file:` fetch fails
  with a clear error.

### The git repository cache

Cloning a repository on every fetch is slow, so the fetcher keeps checked-out
git repositories on disk for a **rolling 24 hours**: a repository used again
within 24 hours of its last use is reused instead of re-cloned, and one that
goes 24 hours unused is pruned. Every time a file is requested from a
repository the repository is **refetched from upstream** (subject to a
configurable **debounce**, below) so upstream changes — including a force
push — are brought down fresh; a fetch that fails is **resynced** by
discarding the checkout and re-cloning from upstream. The cache is transient
working state — the fetcher's only on-disk state — and is safe to lose: losing
it only costs a re-clone.

The cache root is a **shared** directory: in a multi-replica (HA) deployment
several fetcher replicas (e.g. two pods in Kubernetes) can run against the same
cache on a shared volume (a PVC). Because the replicas share the cache, a
repository is **locked** while it is being fetched or resynced, and the index
file (below) is the shared coordination point that keeps the replicas from
double-fetching or reading a half-written checkout.

- **Cache root.** The root of the cache is configurable at the process level
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`) and defaults to a `repositories`
  directory under the OS temp directory — `/tmp/repositories` on Linux,
  `%TEMP%\repositories` on Windows (`os.TempDir()`). Each cached repository
  lives in its own subdirectory of the root.
- **Repository directory names.** A repository's directory is named
  `<unix-epoch-seconds>-<counter>` (e.g. `1761024000-0`, `1761024000-1`) —
  the Unix epoch timestamp of when it was created, plus a process-local
  incrementing counter that disambiguates repositories created within the same
  second. Digits and a hyphen are safe on both Windows and Linux filesystems,
  and the name sorts by creation time.
- **The index file.** A simple text file at the cache root records the cache's
  contents: one line per cached repository — the repository directory, the
  repository URL, the last-accessed Unix epoch timestamp, and the last-fetched
  Unix epoch timestamp (tab-separated:
  `<dir>\t<url>\t<last-accessed-epoch>\t<last-fetched-epoch>`). The index is the
  authoritative map of which directory holds which repository, and it is updated
  **atomically**: every change rewrites the whole file to a temp file in the
  same directory and renames it over the index (a rename within one volume is
  atomic on both Windows and Linux). A process-wide lock serializes index
  mutations within a process; across replicas the atomic rewrite plus the
  per-repository lock (below) keep the shared index consistent.
- **A fetch (get) of a `git` reference.**
  1. The reference is parsed into the repository URL, the branch, and the path.
  2. The index is consulted for the repository URL.
  3. The repository's **lock** is acquired (below); a concurrent fetch of the
     same repository — on this replica or another — waits for it.
  4. **Cache miss** (no index entry) — a new directory `<epoch>-<counter>` is
     created under the cache root, the repository is cloned into it (checking
     out the branch), and a new index entry (the repository directory, the URL,
     and the current timestamp for both last-accessed and last-fetched) is added
     by an atomic index rewrite.
  5. **Cache hit** (an index entry exists) — the entry's last-accessed
     timestamp is updated to now (updating it on every use is what makes the
     24-hour window *rolling*: an actively used repository is never pruned). The
     repository is then **refetched from upstream** unless it was fetched within
     the debounce window (below): a `git fetch` of the branch ref followed by a
     hard reset of the checkout to the fetched ref, which absorbs upstream
     changes including a force push. When a fetch does run, the entry's
     last-fetched timestamp is updated to now (an atomic index rewrite).
  6. **Resync on fetch failure** — if the fetch (or the reset) fails for any
     reason (a diverged / non-fast-forward state, local corruption, a transient
     error), the checkout is discarded and the repository is **re-cloned from
     upstream** (a full resync, checking out the branch). If the re-clone also
     fails, the lock is released and the fetch fails with a clear error.
  7. The file is read from the checkout at the branch ref. The response's
     version identifier is the branch's commit hash after the fetch/clone; the
     content hash is the SHA-256 of the file's content.
  8. The lock is released.
- **Locking.** A repository is **locked** while it is being cloned, fetched, or
  resynced, so a concurrent fetch — on this replica or on another replica
  sharing the cache — never reads a half-written checkout or starts a duplicate
  fetch. The lock is a per-repository lock file in the cache root (e.g.
  `<dir>.lock`), acquired with an OS file lock (`flock` on Linux, `LockFileEx`
  on Windows) and held for the duration of the fetch/resync. A **stale-lock
  timeout** (a heartbeat in the lock file) lets a replica take over a lock held
  by a crashed or gone-away replica, so a dead fetcher cannot wedge the shared
  cache.
- **Debounce.** A repository that was fetched very recently is not refetched
  again on the next request: if the entry's last-fetched timestamp is within the
  **debounce window** (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`, a
  configurable duration, default e.g. 30s), the fetch is skipped and the file is
  read from the current checkout. The debounce keeps a burst of requests for the
  same repository (many pipelines from one repo syncing at once, or several
  replicas fetching concurrently) from hammering the upstream. The last-fetched
  timestamp lives in the shared index file, so the debounce is effective across
  replicas, not just within one process.
- **The cleanup thread.** A background goroutine started with the service
  periodically walks the cache (on a fixed interval, e.g. hourly) and prunes
  repositories that have gone inactive: for every index entry whose
  last-accessed timestamp is more than 24 hours old, it first deletes the
  entry from the index file (an atomic rewrite) and only then deletes the
  repository's directory. Removing the index entry before the directory means a
  concurrent fetch can never be pointed at a directory that is being deleted —
  it sees no entry and clones a fresh one. The sweep skips a repository that is
  currently locked (a fetch in progress) and retries it on the next pass, and it
  also removes orphaned directories that exist under the cache root but have no
  index entry (e.g. a clone interrupted by a crash).

### The `FetchSource` contract

```
rpc FetchSource(FetchSourceRequest) returns (FetchSourceResponse)

message FetchSourceRequest {
  string reference;             // "<type>:<spec>" — "git" | "http" | "file"
  SourceCredential credential;  // optional; the plaintext secret material for this fetch
}

message SourceCredential {
  string kind;                  // "git-ssh" | "git-https" | "http"
  string username;              // git-https (may be empty for token-only auth)
  string token;                 // git-https / http
  string private_key;           // git-ssh (PEM)
  string host_key;              // git-ssh (expected host public key)
  string header;                // http (header the token is sent in; default Authorization: Bearer)
}

message FetchSourceResponse {
  bytes content;                // the file's content
  string version;               // git commit hash / ETag|Last-Modified / mtime
  string hash;                  // SHA-256 of content (hex)
}
```

The reference selects the kind and carries the locator (The reference format);
the credential is **optional** and is needed only for a private git repository
or an authenticated HTTP endpoint. The `SourceCredential` message carries the
**plaintext** secret material for the duration of one call. The API decrypts it
(F-12) and passes it in; the fetcher uses it to authenticate the fetch and
discards it — it is never persisted or logged. The credential model itself
(kinds, regex matching, encryption at rest, API CRUD) is
[F-21.3](f-21.3-source-credentials.md).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The fetch is a separate process.** The actual fetch (a git clone/fetch from
  the fetcher's on-disk cache, an HTTP GET, or a rooted local file read) is
  performed by a dedicated **source-fetcher** service
  (`cmd/pipelinesource` / `internal/services/pipelinesource`) — a standalone
  gRPC server in the same shape as the other services. It holds no definitions,
  credentials, or key at rest (its only on-disk state is the transient git
  repository cache) and is dialed **only by the API** over gRPC: mutual TLS
  when a CA is configured, plaintext otherwise (the convention in
  `internal/grpcutil`). This keeps git, network egress, and the source's
  filesystem out of the API and scheduler, and lets the fetcher be
  network-policy'd to only the sources it must reach.
- **One RPC, a reference string.** `FetchSource` takes a single **reference**
  (`<type>:<spec>` — `git` / `http` / `file`) and an optional
  `SourceCredential` (plaintext for the one call) and returns the content,
  version identifier, and SHA-256 hash. The reference is the shared syntax for
  naming a definition file (imports in F-21.4, sources in F-21.5.1). The
  version identifier (git commit hash / `ETag` / mtime) lets a caller detect a
  no-change cheaply; the hash is the authoritative change detector used by the
  sync routine (F-21.5).
- **Git repositories are cached on disk for a rolling 24 hours, refetched on a
  debounce, and locked across replicas.** The fetcher keeps checked-out
  repositories under a process-level cache root
  (`CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR`, default the `repositories` directory
  under the OS temp directory). Each repository's directory is named
  `<unix-epoch>-<counter>` (portable across Windows and Linux); a text index
  file at the root maps each repository URL to its directory and its
  last-accessed and last-fetched Unix epoch timestamps and is rewritten
  atomically (temp file + rename) on every change. Every file request
  **refetches** the repository from upstream (a `git fetch` + hard reset, which
  absorbs a force push) unless it was fetched within the configurable
  **debounce** window (`CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE`); a fetch
  that fails **resyncs** by discarding the checkout and re-cloning from
  upstream. The cache root is **shared** across fetcher replicas (e.g. two pods
  on a PVC), so a repository is **locked** (a per-repository OS file lock with a
  stale-lock timeout) while it is cloned/fetched/resynced, and a background
  cleanup thread prunes repositories inactive for more than 24 hours, removing
  the index entry before the directory. The cache is transient and is the
  fetcher's only on-disk state.
- **`file:` references are rooted.** A `file:` reference is resolved against a
  configured local-filesystem root (`CDROM_PIPELINE_SOURCE_FILE_ROOT`), so the
  fetcher can read only files under that root — never an arbitrary path on its
  host. With no root configured the `file` kind is disabled.
- **HTTP headers come from the credential store.** An `http` fetch's request
  headers are supplied by the source's `http` credential (F-21.3), not in-band
  on the reference — so a credential is optional (a public endpoint is fetched
  with a plain GET).
- **New fields / RPCs / endpoints (this sub-feature).** A new
  `proto/cdrom/pipelinesource/v1/` gRPC API (`FetchSource` + the
  `SourceCredential` message) with generated code in `internal/gen/` (`make
  proto`); a `cmd/pipelinesource` + `internal/services/pipelinesource` service
  (the fetcher, dialed by the API over gRPC/mTLS); the fetcher's git / HTTP /
  filesystem clients; the git repository cache (cache root + text index +
  per-repository lock + fetch debounce + cleanup thread); and
  `CDROM_PIPELINE_SOURCE_ADDR` (default `127.0.0.1:7107`),
  `CDROM_PIPELINE_SOURCE_REPO_CACHE_DIR` (default `<os.TempDir()>/repositories`),
  `CDROM_PIPELINE_SOURCE_REPO_FETCH_DEBOUNCE` (the fetch debounce window),
  `CDROM_PIPELINE_SOURCE_FILE_ROOT` (unset = the `file` kind disabled), plus a
  dedicated metrics port in `internal/config`.
