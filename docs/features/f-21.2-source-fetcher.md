# F-21.2 · Source-fetcher service

> Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

This sub-feature builds the **source-fetcher** — a dedicated, standalone gRPC
service that performs the actual fetch of a pipeline definition file: a **git**
clone/fetch, an **HTTP/HTTPS** GET, or a read of a file on the **local
filesystem**. It is a separate process so the API and scheduler never need git,
network egress, or the source's filesystem.

**What.** A new service — `cmd/pipelinesource` (entrypoint) with logic in
`internal/services/pipelinesource` — in the same shape as the other services
(`db`, `scheduler`, `artifacts`, `idp`). It exposes one RPC, `FetchSource`,
which takes a source locator (kind + url/branch/path + optional headers) and a
credential (the plaintext secret material, when one is needed) and returns the
file's content, its version identifier, and its content hash. The fetcher is
**stateless**: it holds no pipeline definitions, no credentials, and no
encryption key at rest. It only ever performs a single fetch per call.

**Why.** Keeping the fetch out of the API and scheduler means neither needs git
installed, outbound network egress, or the source's filesystem. The fetcher can
be run with a network policy that allows only the repos/endpoints it must reach,
and it can be scaled or replaced independently of the control plane. It also
keeps the API's process free of long-running git operations.

**Scope.**
- `cmd/pipelinesource` + `internal/services/pipelinesource` — the **source
  fetcher**: a standalone gRPC server (a new process, like `db` / `scheduler` /
  `artifacts` / `idp`) that performs the actual fetch — git clone/fetch, HTTP
  GET, or a local file read — and returns the file's content, version, and
  hash. It is stateless (no definitions, no credentials, no key at rest) and is
  dialed **only by the API** over gRPC (mutual TLS when a CA is configured).
- `proto/cdrom/pipelinesource/v1/` — the fetcher's gRPC API (`FetchSource`,
  plus the `SourceLocator` / `SourceCredential` / `FetchedFile` messages);
  generated code in `internal/gen/` (`make proto`).
- The fetcher's git / HTTP / filesystem clients (a single file at a ref / URL /
  path, authenticated by a `SourceCredential` passed in for that one call).
- `internal/config` — the fetcher's listen address
  (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`) and its dedicated
  metrics port (F-20).

**Acceptance criteria.**
- [ ] A file can be fetched from a **git** repository (a single file at a
      branch/ref, authenticated by a `git-ssh` or `git-https` credential), an
      **HTTP/HTTPS** endpoint (a GET, with optional in-band headers or a named
      credential), or a file on the **local filesystem** (an absolute path on
      the fetcher's host).
- [ ] `FetchSource` returns the file's content, its **version identifier**
      (the git commit hash, an HTTP `ETag`/`Last-Modified`, or the file's mtime),
      and its **content hash** (SHA-256 of the content).
- [ ] The fetcher is a **standalone gRPC server** dialed **only by the API**;
      with a TLS CA configured the connection uses mutual TLS, and without one
      it falls back to plaintext (local dev) — the same convention as the other
      services (`internal/grpcutil`).
- [ ] The fetcher is **stateless**: it holds no pipeline definitions, no
      credentials, and no encryption key at rest; it performs a single fetch per
      call. A credential is passed in for one fetch and is never persisted or
      logged.
- [ ] The fetcher's address comes from config / env
      (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), and it serves
      its own `/metrics` + `/healthz` on a dedicated metrics port (F-20).
- [ ] A fetch failure (unreachable repo/endpoint, missing file, auth failure)
      returns a clear gRPC error the API can surface on the source's state
      (F-21.5).

## The source-fetcher service

The actual fetch is done by a dedicated **source-fetcher** service — a separate
process (`cmd/pipelinesource`, logic in `internal/services/pipelinesource`), in
the same shape as the other services (`db`, `scheduler`, `artifacts`, `idp`):

- **A standalone gRPC server.** It exposes one RPC, `FetchSource`, which takes a
  source locator (kind + url/branch/path + optional headers) and a credential
  (the plaintext secret material, when one is needed) and returns the file's
  content, its version identifier, and its content hash. The fetcher is
  **stateless**: it holds no pipeline definitions, no credentials, and no
  encryption key at rest. It only ever performs a single fetch per call.
- **Dialed only by the API, over gRPC.** The API is the only caller (the same
  topology rule as the other services: the API talks to everything else). The
  connection uses **mutual TLS** when a TLS CA is configured (`TLSConfig` in
  `internal/config`; creds built in `internal/grpcutil`) and falls back to
  plaintext without one (local dev) — exactly the convention the other services
  follow. The fetcher's address comes from config / env
  (`CDROM_PIPELINE_SOURCE_ADDR`, default `127.0.0.1:7107`), and it serves its
  own `/metrics` + `/healthz` on a dedicated metrics port (F-20).
- **Why a separate process.** Keeping the fetch out of the API and scheduler
  means neither needs git installed, outbound network egress, or the source's
  filesystem. The fetcher can be run with a network policy that allows only the
  repos/endpoints it must reach, and it can be scaled or replaced independently
  of the control plane. It also keeps the API's process free of long-running
  git operations.
- **Protos.** `proto/cdrom/pipelinesource/v1/` defines `FetchSource` (and the
  `SourceLocator` / `SourceCredential` / `FetchedFile` messages); generated code
  is committed under `internal/gen/` (`make proto`). The service impl lives in
  `internal/services/pipelinesource/server.go` and implements the generated
  `*Server` interface (embedding `Unimplemented*Server`), per the gRPC
  conventions.

### The three source kinds

`FetchSource` takes a `SourceLocator` naming one of three kinds:

- **`git`** — `url` (the git remote), `branch` (the ref to track; default
  `main`), and `path` (the path of the definition file within the repo). The
  fetcher clones/fetches the repo at the ref and reads the file at `path`. It
  returns the commit hash as the version identifier. Authentication is by a
  `git-ssh` or `git-https` credential (F-21.3) passed in for the call.
- **`http`** — `url` (the endpoint that serves the definition file, e.g. an
  object-store URL or a raw-file endpoint). The fetcher does a GET and uses the
  response body as the file. An optional `headers` map (e.g. an `Authorization`
  header) can be set on the locator for endpoints that need it in-band; a named
  `http` credential (F-21.3) is the preferred way to supply a token. It returns
  the `ETag`/`Last-Modified` as the version identifier.
- **`filesystem`** — `path` (an absolute path to the definition file on the
  source-fetcher's host). The file is read directly; no network is involved.
  This is the kind for a definition that is mounted into the fetcher's pod
  (e.g. a ConfigMap or a volume) and is "pulled" by re-reading the file. It
  returns the file's mtime as the version identifier.

### The `FetchSource` contract

```
rpc FetchSource(FetchSourceRequest) returns (FetchSourceResponse)

message FetchSourceRequest {
  SourceLocator locator;      // kind + url/branch/path + optional headers
  SourceCredential credential; // optional; the plaintext secret material for this fetch
}

message SourceLocator {
  string kind;                // "git" | "http" | "filesystem"
  string url;                 // git remote or http endpoint (empty for filesystem)
  string branch;              // git ref (default "main")
  string path;                // file path in repo (git) / absolute path (filesystem)
  map<string,string> headers; // optional in-band headers (http)
}

message SourceCredential {
  string kind;                // "git-ssh" | "git-https" | "http"
  string username;            // git-https (may be empty for token-only auth)
  string token;               // git-https / http
  string private_key;         // git-ssh (PEM)
  string host_key;            // git-ssh (expected host public key)
  string header;              // http (header the token is sent in; default Authorization: Bearer)
}

message FetchSourceResponse {
  bytes content;              // the file's content
  string version;             // git commit hash / ETag|Last-Modified / mtime
  string hash;                // SHA-256 of content (hex)
}
```

The `SourceCredential` message carries the **plaintext** secret material for the
duration of one call. The API decrypts it (F-12) and passes it in; the fetcher
uses it to authenticate the fetch and discards it — it is never persisted or
logged. The credential model itself (kinds, regex matching, encryption at rest,
API CRUD) is [F-21.3](f-21.3-source-credentials.md).

## Design decisions (folded into AGENTS.md / Architecture.md)

- **The fetch is a separate process.** The actual fetch (git clone/fetch, HTTP
  GET, or a local file read) is performed by a dedicated **source-fetcher**
  service (`cmd/pipelinesource` / `internal/services/pipelinesource`) — a
  standalone gRPC server in the same shape as the other services. It is
  **stateless** (no definitions, credentials, or key at rest) and is dialed
  **only by the API** over gRPC: mutual TLS when a CA is configured, plaintext
  otherwise (the convention in `internal/grpcutil`). This keeps git, network
  egress, and the source's filesystem out of the API and scheduler, and lets the
  fetcher be network-policy'd to only the sources it must reach.
- **One RPC, three kinds.** `FetchSource` takes a `SourceLocator` (kind +
  url/branch/path + optional headers) and an optional `SourceCredential`
  (plaintext for the one call) and returns the content, version identifier, and
  SHA-256 hash. The version identifier (git commit hash / `ETag` / mtime) lets a
  caller detect a no-change cheaply; the hash is the authoritative change
  detector used by the sync routine (F-21.5).
- **New fields / RPCs / endpoints (this sub-feature).** A new
  `proto/cdrom/pipelinesource/v1/` gRPC API (`FetchSource` + `SourceLocator` /
  `SourceCredential` / `FetchedFile` messages) with generated code in
  `internal/gen/` (`make proto`); a `cmd/pipelinesource` +
  `internal/services/pipelinesource` service (the fetcher, dialed by the API
  over gRPC/mTLS); the fetcher's git / HTTP / filesystem clients; and
  `CDROM_PIPELINE_SOURCE_ADDR` (default `127.0.0.1:7107`) + a dedicated metrics
  port in `internal/config`.
