# F-21.1.2 · Step spec shape & name-based step referencing

> Part of [F-21.1 · File format & compiler](f-21.1-file-format-compiler.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** How a step is written in the file and how the compiler maps it onto
the `JobStep`: the **step spec shape** (the common fields plus a key that names
a registered step handler type, whose value is that handler's `params`), the
`shell` **plain-string shorthand**, **shared steps** under `spec.steps`
referenced by `ref` (an empty entry is shorthand for `ref: <same name>`), and
the **name-based step referencing** so a step's outputs are referenced by a
user-definable step name in the file and stored as that same name on the
`JobStep` (the executor's condition context is keyed by step name, so no
rewrite is needed).

**Depends on.** [F-21.1.1](f-21.1.1-manifest-envelope.md) (the manifest
envelope + compiler skeleton).

**Why.** Steps are the unit of work, and naming them (rather than numbering
them) is what keeps the file stable under reordering and reviewable in a PR: a
step that wants another step's output references it by that step's name, and
the name flows through unchanged from the file to the stored `JobSpec` to the
executor's condition context.

**Scope.**
- `internal/pipelinefile` — the **step spec shape**: a step's value is a map;
  the common fields (`workdir`, `env`, `timeout`, `condition`, `ignoreFailed`,
  `once`) are recognized by name and lifted onto the `JobStep`; a key that names
  a registered step handler type (e.g. `shell`, `token_exchange`, `approval`,
  `email`, `webhook`) selects that handler and its value is the handler's
  `params`; when no handler-type key is present the step uses the default
  handler (`shell`) and the remaining keys are its `params`.
- The `shell` handler's value may be a **plain string**: `shell: <string>` is
  shorthand for `shell: {command: <string>}` — only the `command` param is set,
  nothing else (no `args`, no `shell`). A shell step that sets no `shell` param
  runs its command through the target OS's **default shell** (e.g. `bash` on
  Linux, `pwsh` on Windows).
- **Shared steps** under `spec.steps` (a name → step-spec map): a job's step
  entry may be inline, a `ref` to a shared step (the referenced step's full spec
  is used), or an **empty** entry — shorthand for `ref: <same name>`; a name
  with no matching shared step is a validation error.
- **Name-based step referencing**: a job's steps run in the order their names
  appear in the file; the compiler stores each step's name on the `JobStep`
  (`name` field) and a step's outputs are referenced by that name in the
  executor's condition context (`{{ .steps.build.Outputs.version }}`); a
  reference to a step name that is not a *prior* step in the order is a
  validation error (a step cannot read a later step's output).

**Acceptance criteria.**
- [x] A step's value is a map: the common fields (`workdir`, `env`, `timeout`,
      `condition`, `ignoreFailed`, `once`) are recognized by name and lifted
      onto the `JobStep`; a key that names a registered step handler type

      that handler and its value is the handler's `params`; when no handler-type
      key is present the step uses the default handler (`shell`) and the
      remaining keys are its `params` — so `shell: {command: …}` (an explicit
      type) and a bare `{command: …}` (the default handler) both describe a
      shell step.
- [x] A `shell` step's handler value may be a plain string: `shell: <string>`
      is shorthand for `shell: {command: <string>}` (only the `command` param
      is set, nothing else); a shell step that sets no `shell` param runs its
      command through the target OS's default shell.
- [x] Shared steps live under `spec.steps` (a name → step-spec map); a job's
      step entry may be inline, a `ref` to a shared step (the referenced step's
      full spec is used), or an empty entry — shorthand for `ref: <same name>`
      (it implicitly references the shared step of the same name); a name with

- [x] A step's outputs are referenced in the file by a **user-definable step

- [x] A reference to a step name that is not a *prior* step in the order is a

## Design decisions (folded into AGENTS.md / Architecture.md)

- **Step spec shape.** A step's value is a map. The common fields (`workdir`,
  `env`, `timeout`, `condition`, `ignoreFailed`, `once`) are recognized by name
  and lifted onto the `JobStep`. A key that names a registered step handler type
  selects that handler, and its value is the handler's `params`. When no
  handler-type key is present the step uses the default handler (`shell`) and
  the remaining keys are its `params`. The `shell` handler's value may also be a
  plain string (`shell: <string>` is shorthand for `shell: {command: <string>}`
  — only the `command` param is set), and a shell step that sets no `shell`
  param runs its command through the target OS's default shell, so the string
  form is the portable way to write a one-line shell command.
- **Steps are referenced by name, never by ordinal.** A job's `steps` is a name
  → step-spec map, and a step's name (the map key) is its id. A step that wants
  another step's output references it by that step's name; a job's steps run in
  the order their names appear in the file (the compiler parses the YAML
  preserving key order, so a map still yields a deterministic ordered step
  list). The compiler stores each step's name on the `JobStep` (`name` field)
  and the executor's condition context is keyed by step name, so the name flows
  through unchanged from the file to the stored `JobSpec` to the executor —
  there is no name → ordinal rewrite. The mapping is one-directional and total:
  every name in the file must resolve to exactly one target, and the compiler
  fails the import with an actionable error naming the unresolvable reference.
  Once compiled, the stored `JobSpec` is canonical (name-based) and is what the
  executor runs.
- **New fields / RPCs / endpoints (this sub-feature).** Step-spec parsing in
  `internal/pipelinefile` (common-field lifting, handler-type selection, the
  `shell` plain-string shorthand, shared steps + `ref` + empty-entry shorthand,
  and storing each step's name on the `JobStep`, with the prior-step-only
  validation rule).
