# F-28.4 · SCIM user management

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** Three interlocking deliveries. **(1)** The `/Users` resource
endpoints that deliver the user lifecycle over SCIM: `POST /scim/v2/Users`
(provision or re-provision), `GET /scim/v2/Users` (paginated, filterable
list), and `GET/PUT/PATCH/DELETE /scim/v2/Users/{id}` — the SCIM↔directory
mapping, the conflict matrix, and audit of every mutation. **(2)** The
underlying **identity-anchor restructure**: `IDPUser` keys on a unique
`Username` (carrying the OIDC subject claim and SCIM `userName`) plus the
`ExternalID` (the corporate link), and `Email` is demoted to a separate,
OPTIONAL field — a UPN/subject need not be an email (App-registrations with
UUID subjects are first-class). All lookups run through identifiers, never
email. **(3)** The **admission gate** (the JIT-vs-SCIM provisioning-mode
switch), consolidated in the IdP service and enforced by the API for every
human user principal, plus the operator switches it interplays with
(local-login enablement, the hand-edit restriction, and a public
system-information feed for the UI). Builds on F-28.1 (mount/metadata),
F-28.2 (caller gate), and F-28.3 (states/transitions).

**Identity anchors.** Authority ranking, highest first:
- **Numeric ID** — the stable primary key; the SCIM resource id (decimal
  string) and the token subject. Immovable.
- **`ExternalID`** — the corporate directory's identifier (e.g. the Azure
  object id); logically unique; the re-provisioning match key. Sticky once
  set (a SCIM write that alters or removes it ⇒ 400).
- **`Username`** — UNIQUE, mutable metadata: the OIDC subject claim (claim
  name configurable, default `sub`) lands here, and SCIM `userName` writes
  here. It is the login identifier (F-24 password channel) and the gate's
  correlation key, but carries no deeper semantic weight — a `POST` matching
  an active row's `externalId` with a NEW `userName` RENAMES that row (the
  got-married case), preserving ID and history.
- **`Email`** — optional, NON-unique, informational: filled from
  `emails[type=primary]` (SCIM) or the email claim (JIT); never a lookup key.

Lookups: by ID, `Username`, or `ExternalID` — never by email. No migration,
no back-compatibility: the identifier rename (email→username) crosses the
F-24 surfaces (login, register, admin API, fixtures) in one deliberate cut.

**Mapping (RFC 7643 User schema ↔ `IDPUser`).**
- `userName` → `Username` (the anchor; unique).
- `name.givenName` / `name.familyName` → `FirstName` / `LastName`; the compact
  single-string `name` form is ALSO accepted (tolerant split: first token ⇒
  given name, remainder ⇒ family name). Responses emit the object form.
- Filtering is PUSHED DOWN: the SCIM filter subset translates into GENERIC
  EQUALITY CONSTRAINTS (canonical vocabulary: `username`, `external_id`,
  `email`, `first_name`, `last_name`, `active`, `provisioned`) that the
  LISTING SERVICE evaluates ITSELF — in the Database service for the
  production store (predicate → WHERE clause; case sensitivity pinned per
  predicate; booleans demand the literal constants `"true"`/`"false"`;
  unknown attributes are InvalidArgument), in memory for the test store
  (identical rules). Callers therefore transfer only matching rows, never
  the population. The same algebra rides the IdP gRPC's `ListUsers.generic_filter`
  (camelCase attributes, translated to the canonical vocabulary) — the
  intended vehicle for exposing admin-side user-search to the UI later.
- `active` → `Active` (F-28.3).
- `externalId` → `ExternalID` (re-provisioning match key; sticky).
- `emails[type=primary].value` → `Email` (fills the optional email; absent ⇒
  empty; non-primary entries are acknowledged and ignored).
- `groups` (membership refs) → parsed and DISCARDED (debug-logged) until
  F-28.5 lands the group→role application.
- `meta.created` / `meta.lastModified` → `CreatedAt` / `UpdatedAt` — echoed
  from the row's ACTUAL timestamps, not emission time.
- The SCIM `Location` id ⇄ the user's stable numeric ID (rendered as a
  decimal string).

**Conflict matrix.** `POST` resolution ORDER: `externalId` match first
(identifiers outrank names), then `userName` match.

| Request | Target state | Outcome |
|---------|--------------|---------|
| `POST` | no match | 201 — provision (stock `user` role placeholder until F-28.5 group derivation lands, `provisioned=true`, `active` per payload or true) |
| `POST` | tombstoned row matches `externalId` or `userName` | 200 — **re-provision**: reactivate the row (F-28.3), repopulate, same stable ID |
| `POST` | active row matches `externalId` | 200 — **rename/repopulate**: set `Username` to the posted `userName` (got-married case); if the new `userName` collides with ANOTHER active row ⇒ 409 |
| `POST` | active row matches `userName` (no `externalId` match) | 409 `duplicate` (strict; never a duplicate row) |
| `GET`/`PUT`/`PATCH`/`DELETE` | none | 404 `notFound` |
| `GET`/`PUT`/`PATCH`/`DELETE` | tombstoned | 404 (revival is exclusively via `POST`) |
| `PUT` | active | DEFINITE replace of the tracked fields (omitted ⇒ defaults: names "", email "", active true); `userName` REQUIRED; `externalId` immutable (altering it ⇒ 400) |
| `PATCH` | active | apply ops (`replace`/`add`/`remove`) on the supported attributes — the usual carrier for `active` toggles; read-modify-write, last-writer-wins (ETags deferred) |

**Provisioning modes (JIT vs. SCIM) — the admission gate.** Mutually
exclusive; there is always exactly one source of user records. The gate is
consolidated in the **IdP service** (new gRPC `AdmitPrincipal`); the API's
auth middleware invokes it for EVERY human user principal — OIDC tokens AND
user API keys (service accounts and job tokens are exempt) — **WITHOUT
CACHING: every request re-verifies the user's state**, so a SCIM-driven
deactivation bites the very next hop (the ~1-second memo that DOES exist
belongs to the SCIM GUARD's key-bundle refresh, F-28.2 — a different
mechanism, not the gate). The correlation key is the token's SUBJECT claim
(claim name configurable, default `sub`), looked up as `Username`.
- **Judgment is ORIGIN-INDEPENDENT.** The gate weighs the CLAIMS the token
carries, not who signed it. The built-in IdP issues user tokens ONLY for
valid username/password (or coins break-glass temporaries) and job tokens
ONLY for dispatched jobs — it never signs for an unknown human — so in
practice the gate chiefly adjudicates FOREIGN-ISSUED tokens (the corporate
IdP), where token acquisition happens upstream and is invisible to us;
JIT creation fires on the FIRST sight of such a token's subject.
- **Known + active** ⇒ admitted. **Deactivated / tombstoned** ⇒ denied with
  the distinct F-28.3 reasons. These verdicts hold in BOTH modes.
- **Unknown + `idp.scim.enabled: true`** ⇒ denied (no JIT). The corporate IdP
  is the sole source of truth; un-provisioned “shadow” users never reach
  Cdrom.
- **Unknown + `idp.scim.enabled: false`** (the default) ⇒ **JIT**: create
  `provisioned=true`, `external_id=""`, name/email from the args, roles = the
  claim-derived set — REQUIRED NON-EMPTY (no stock role injection). Empty
  roles ⇒ denied AND no row is created (fail-closed; the operator grants a
  role mapping first). Returning JIT users REFRESH name/email from the args
  on every admission and GROW roles monotonically (`stored ∪ incoming`);
  a claim dropping off never strips an operator-granted role.
- **Known locally-registered users** (F-24) match by username and are
  admitted as-is — no overwrite (they are hand-managed).
- **Degradation:** IdP unreachable ⇒ fail CLOSED (503) for gated principals.
  The OIDC-disabled passthrough mode (synthetic admin) is ungated, as today.
- The built-in IdP's dev-shim `/auth` (`?user=…`) stays blind/trusting: the
  gate lives in the API, the single choke point that sees REAL issuer tokens
  — including foreign issuers, where token acquisition happens at the
  corporate IdP and is invisible to us.

**Hand-edit restriction.** The LOCKED population is `provisioned=true` AND
`external_id ≠ ""` — sticky: flipping SCIM off later does NOT unlock such
rows. For those users:
- The admin API and UI refuse manual edits to the identity fields (username,
names, email, active state) — EVEN value-preserving no-ops — pointing at the
  upstream IdP (409).
- Role assignment STAYS OPEN, including scoped bindings (pipeline-read
  regexes etc.): operator grants coexist with F-28.5's group derivation (merge
  policy is F-28.5's).
- `DELETE /api/users/{id}` REMAINS available on locked users — the sanctioned
  emergency valve when SCIM sync lags behind the need to revoke access
  (audited override; the tombstone is reversible).
- JIT users (`provisioned && external_id=""`) and locally-registered users
  (F-24) are fully editable.
- The password channel stays closed for ALL provisioned users (F-28.3):
  no write path may attach a password; logins are SSO-only.

**Operator switches & system info.**
- **`idp.local_login_enabled`** (default true): when false, `/api/login` and
  `/api/register` are refused — EXCEPT break-glass holders: the IdP reports
  which channel satisfied a login (standing vs. temporal), and the API lets
  only the temporal through. A CALM MODE SWITCH (ruled 2026-11-06): false =
  SSO-only; true = local logins (manually configured users, break-glass
  holders) alongside a configured SSO. NO boot warning — even with OIDC off,
  the break-glass hatch (default on) guarantees recoverability, so the
  combination is a legitimate steady state, not a footgun.
- **`GET /api/system/info`** — unauthenticated, strictly non-secret whitelist
  driving the UI's show/hide decisions (login-form visibility, management
  badges): which mechanics are on (OIDC, userpass, API keys, service
  accounts, RBAC), IdP flags (SCIM, local login, break-glass), artifact store
  kind. Fed by API-local config + small `Describe` gRPCs (IdP, Artifacts);
  unreachable components report `null` segments rather than failing the
  endpoint. Addresses, keys, and DSNs never appear here.
