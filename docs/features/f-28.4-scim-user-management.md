# F-28.4 · SCIM user management

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** The `/Users` resource endpoints that deliver the user lifecycle over
SCIM: `POST /scim/v2/Users` (provision or re-provision), `GET /scim/v2/Users`
(paginated, filterable list), and `GET/PUT/PATCH/DELETE /scim/v2/Users/{id}`.
Implements the SCIM↔directory mapping, the conflict matrix, the
provisioning-mode switch (JIT vs. SCIM) on the OIDC login path, the refusal of
manual edits to SCIM-managed users, and audit of every mutation. Builds on
F-28.1 (mount/metadata), F-28.2 (gate), and F-28.3 (states/transitions).

**Mapping (RFC 7643 User schema ↔ `IDPUser`).**
- `userName` → `Email` (the unique login identifier).
- `name.givenName` / `name.familyName` → `FirstName` / `LastName`.
- `active` → `Active` (F-28.3).
- `externalId` → `ExternalID` (the re-provisioning match key).
- `emails[type=primary].value` → corroborates `Email` (mismatch ⇒ 400
  `invalidValue`).
- `groups` (membership refs) → handed to F-28.5 (group→role mapping
  application).
- `meta.created` / `meta.lastModified` → `CreatedAt` / `UpdatedAt` (echoed in
  responses).
- The SCIM `Location` id ⇄ the user's stable numeric ID (rendered as a
  decimal string).

**Conflict matrix.**

| Request | Target state | Outcome |
|---------|--------------|---------|
| `POST` | none | 201 — provision (default role, `provisioned=true`) |
| `POST` | active, same `userName` | 409 `duplicate` (tolerantly: 200 with the existing record is acceptable; never a duplicate row) |
| `POST` | tombstoned, same `userName` or `externalId` | 200 — **re-provision**: reactivate the row (F-28.3), repopulate, same stable ID |
| `GET`/`PUT`/`PATCH`/`DELETE` | none | 404 `notFound` |
| `GET`/`PUT`/`PATCH`/`DELETE` | tombstoned | 404 (revival is exclusively via `POST`) |
| `PUT` | active | full replace of the tracked fields (omitted tracked fields revert to defaults) |
| `PATCH` | active | apply ops (`replace`/`add`/`remove`) — the usual carrier for `active` toggles |

**Provisioning modes (JIT vs. SCIM).** Mutually exclusive; there is always
exactly one source of user records:
- **`idp.scim.enabled: true`** — the corporate IdP is the sole source of
  truth. The OIDC login path requires an existing, non-tombstoned user; an
  unknown user is rejected (no JIT). Stops un-provisioned “shadow” users from
  reaching Cdrom.
- **`idp.scim.enabled: false`** (the default) — **JIT**: the first OIDC login
  creates a record from the token's claims (subject/email, name) with the
  default role, marked provisioned; subsequent logins reuse it. This is the
  simple local-dev / plain-OIDC mode where users are not pre-created.

**Hand-edit restriction.** A user with `provisioned=true` under SCIM-enabled
operation has its identity (email, name, active state, group/role
memberships) driven by the corporate directory: the admin API and UI refuse
manual edits to those fields (pointing at the upstream IdP instead).
Locally-registered users (F-24) remain fully manageable and are untouched by
SCIM.

**Scope.**
- `internal/idp` (`scim_users.go`) — the `/Users` routes, SCIM User-schema
  (de)serialisation, `ListResponse` construction (`startIndex` / `count` /
  `totalResults`), the filter parser for the supported subset (`userName eq
  X`, `active eq true|false`, `externalId eq X`; unsupported compounds ⇒ 400
  `invalidFilter`), and the mapping/conflict logic above, delegating to
  `UserStore` (F-28.3 primitives).
- `internal/idp` (OIDC login path) — the provisioning-mode branching above.
- `internal/api` — the hand-edit refusal for SCIM-managed users (update
  endpoints + the UI payload, including state and provenance markings).
- F-15 audit — every SCIM mutation (provision, re-provision, update,
  activate/deactivate, deprovision) writes an event: actor = the SCIM service
  identity, target user, operation, outcome.
- `ui/` — the user view renders the four lifecycle states and marks
  SCIM-managed users (identity fields shown as locked).
- **Deferred** (advertised unsupported by the F-28.1 metadata): `Bulk`
  operations, ETag/`If-Match` concurrency.

**Acceptance criteria.**
- [ ] `POST /Users` provisions a new user mapped per the table, with the
      default role; the user can then authenticate (via OIDC when SCIM is
      enabled).
- [ ] A duplicate `POST` for an existing active `userName` never creates a
      second row (409, or 200 with the existing record).
- [ ] A `POST` matching a tombstoned user's `userName` or `externalId`
      reactivates the same row (stable ID preserved, history intact) — the
      re-hire case.
- [ ] `PATCH {id}` with `active:false` deactivates: login and new token
      minting reject the user; the record is retained; `active:true` restores
      access.
- [ ] `DELETE {id}` deprovisions via the F-28.3 tombstone semantics.
- [ ] `GET`/`PUT`/`PATCH`/`DELETE` on an unknown or tombstoned id return a
      404 SCIM-error.
- [ ] Lists paginate (`startIndex`/`count`/`totalResults`) and respect the
      filter subset; unsupported filter forms return 400 `invalidFilter`.
- [ ] Successful responses carry the correct `schemas`/`meta`/`location`;
      errors are RFC 7644-shaped SCIM-errors.
- [ ] With SCIM disabled, a first-ever OIDC login auto-provisions from claims
      (default role); with SCIM enabled, an unknown user's login is rejected.
- [ ] Manual edits to a SCIM-managed user's identity fields are refused via
      the admin API and locked in the UI.
- [ ] Every mutation writes an audit event attributing the SCIM service.
