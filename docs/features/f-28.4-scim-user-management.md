# F-28.4 · SCIM user management

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** Three interlocking deliveries. **(1)** The `/Users` resource
endpoints that deliver the user lifecycle over SCIM: `POST /scim/v2/Users`
(provision or re-provision), `GET /scim/v2/Users` (paginated, filterable
list), and `GET/PUT/PATCH/DELETE /scim/v2/Users/{id}` — the SCIM↔directory
mapping, the conflict matrix, and audit of every mutation. **(2)** The
underlying **identity-anchor restructure**: `IDPUser` keys on a unique
`Username` (carrying the OIDC subject claim and SCIM `userName`) plus the
`ExternalID` (the corporate link), and `Email` is demoted to a separate,
OPTIONAL field — a UPN/subject need not be an email (App-registrations with
UUID subjects are first-class). All lookups run through identifiers, never
email. **(3)** The **admission gate** (the JIT-vs-SCIM provisioning-mode
switch), consolidated in the IdP service and enforced by the API for every
human user principal, plus the operator switches it interplays with
(local-login enablement, the hand-edit restriction, and a public
system-information feed for the UI). Builds on F-28.1 (mount/metadata),
F-28.2 (caller gate), and F-28.3 (states/transitions).

**Identity anchors.** Authority ranking, highest first:
- **Numeric ID** — the stable primary key; the SCIM resource id (decimal
  string) and the token subject. Immovable.
- **`ExternalID`** — the corporate directory's identifier (e.g. the Azure
  object id); logically unique; the re-provisioning match key. Sticky once
  set (a SCIM write that alters or removes it ⇒ 400).
- **`Username`** — UNIQUE, mutable metadata: the OIDC subject claim (claim
  name configurable, default `sub`) lands here, and SCIM `userName` writes
  here. It is the login identifier (F-24 password channel) and the gate's
  correlation key, but carries no deeper semantic weight — a `POST` matching
  an active row's `externalId` with a NEW `userName` RENAMES that row (the
  got-married case), preserving ID and history.
- **`Email`** — optional, NON-unique, informational: filled from
  `emails[type=primary]` (SCIM) or the email claim (JIT); never a lookup key.

Lookups: by ID, `Username`, or `ExternalID` — never by email. No migration,
no back-compatibility: the identifier rename (email→username) crosses the
F-24 surfaces (login, register, admin API, fixtures) in one deliberate cut.

**Mapping (RFC 7643 User schema ↔ `IDPUser`).**
- `userName` → `Username` (the anchor; unique).
- `name.givenName` / `name.familyName` → `FirstName` / `LastName`.
- `active` → `Active` (F-28.3).
- `externalId` → `ExternalID` (re-provisioning match key; sticky).
- `emails[type=primary].value` → `Email` (fills the optional email; absent ⇒
  empty; non-primary entries are acknowledged and ignored).
- `groups` (membership refs) → parsed and DISCARDED (debug-logged) until
  F-28.5 lands the group→role application.
- `meta.created` / `meta.lastModified` → `CreatedAt` / `UpdatedAt` — echoed
  from the row's ACTUAL timestamps, not emission time.
- The SCIM `Location` id ⇄ the user's stable numeric ID (rendered as a
  decimal string).

**Conflict matrix.** `POST` resolution ORDER: `externalId` match first
(identifiers outrank names), then `userName` match.

| Request | Target state | Outcome |
|---------|--------------|---------|
| `POST` | no match | 201 — provision (stock `user` role placeholder until F-28.5 group derivation lands, `provisioned=true`, `active` per payload or true) |
| `POST` | tombstoned row matches `externalId` or `userName` | 200 — **re-provision**: reactivate the row (F-28.3), repopulate, same stable ID |
| `POST` | active row matches `externalId` | 200 — **rename/repopulate**: set `Username` to the posted `userName` (got-married case); if the new `userName` collides with ANOTHER active row ⇒ 409 |
| `POST` | active row matches `userName` (no `externalId` match) | 409 `duplicate` (strict; never a duplicate row) |
| `GET`/`PUT`/`PATCH`/`DELETE` | none | 404 `notFound` |
| `GET`/`PUT`/`PATCH`/`DELETE` | tombstoned | 404 (revival is exclusively via `POST`) |
| `PUT` | active | DEFINITE replace of the tracked fields (omitted ⇒ defaults: names "", email "", active true); `userName` REQUIRED; `externalId` immutable (altering it ⇒ 400) |
| `PATCH` | active | apply ops (`replace`/`add`/`remove`) on the supported attributes — the usual carrier for `active` toggles; read-modify-write, last-writer-wins (ETags deferred) |

**Provisioning modes (JIT vs. SCIM) — the admission gate.** Mutually
exclusive; there is always exactly one source of user records. The gate is
consolidated in the **IdP service** (new gRPC `AdmitPrincipal`); the API's
auth middleware invokes it for EVERY human user principal — OIDC tokens AND
user API keys (service accounts and job tokens are exempt) — with a short
TTL cache per username. The correlation key is the token's SUBJECT claim
(claim name configurable, default `sub`), looked up as `Username`.
- **Known + active** ⇒ admitted. **Deactivated / tombstoned** ⇒ denied with
  the distinct F-28.3 reasons. These verdicts hold in BOTH modes.
- **Unknown + `idp.scim.enabled: true`** ⇒ denied (no JIT). The corporate IdP
  is the sole source of truth; un-provisioned “shadow” users never reach
  Cdrom.
- **Unknown + `idp.scim.enabled: false`** (the default) ⇒ **JIT**: create
  `provisioned=true`, `external_id=""`, name/email from the args, roles = the
  claim-derived set — REQUIRED NON-EMPTY (no stock role injection). Empty
  roles ⇒ denied AND no row is created (fail-closed; the operator grants a
  role mapping first). Returning JIT users REFRESH name/email from the args
  on every admission and GROW roles monotonically (`stored ∪ incoming`);
  a claim dropping off never strips an operator-granted role.
- **Known locally-registered users** (F-24) match by username and are
  admitted as-is — no overwrite (they are hand-managed).
- **Degradation:** IdP unreachable ⇒ fail CLOSED (503) for gated principals.
  The OIDC-disabled passthrough mode (synthetic admin) is ungated, as today.
- The built-in IdP's dev-shim `/auth` (`?user=…`) stays blind/trusting: the
  gate lives in the API, the single choke point that sees REAL issuer tokens
  — including foreign issuers, where token acquisition happens at the
  corporate IdP and is invisible to us.

**Hand-edit restriction.** The LOCKED population is `provisioned=true` AND
`external_id ≠ ""` — sticky: flipping SCIM off later does NOT unlock such
rows. For those users:
- The admin API and UI refuse manual edits to the identity fields (username,
names, email, active state) — EVEN value-preserving no-ops — pointing at the
  upstream IdP (409).
- Role assignment STAYS OPEN, including scoped bindings (pipeline-read
  regexes etc.): operator grants coexist with F-28.5's group derivation (merge
  policy is F-28.5's).
- `DELETE /api/users/{id}` REMAINS available on locked users — the sanctioned
  emergency valve when SCIM sync lags behind the need to revoke access
  (audited override; the tombstone is reversible).
- JIT users (`provisioned && external_id=""`) and locally-registered users
  (F-24) are fully editable.
- The password channel stays closed for ALL provisioned users (F-28.3):
  no write path may attach a password; logins are SSO-only.

**Operator switches & system info.**
- **`idp.local_login_enabled`** (default true): when false, `/api/login` and
  `/api/register` are refused — EXCEPT break-glass holders: the IdP reports
  which channel satisfied a login (standing vs. temporal), and the API lets
  only the temporal through. Boots with a loud warning when false while OIDC
  is also off (then only the hatch remains).
- **`GET /api/system/info`** — unauthenticated, strictly non-secret whitelist
  driving the UI's show/hide decisions (login-form visibility, management
  badges): which mechanics are on (OIDC, userpass, API keys, service
  accounts, RBAC), IdP flags (SCIM, local login, break-glass), artifact store
  kind. Fed by API-local config + small `Describe` gRPCs (IdP, Artifacts);
  unreachable components report `null` segments rather than failing the
  endpoint. Addresses, keys, and DSNs never appear here.

**Slices & acceptance criteria.** Five sequential increments (S1 → S5
strictly), each ending compiled, tested, and demonstrable (checkpoint commit
per slice); each slice's acceptance criteria are tagged directly beneath it
(per-slice tagging, mirroring F-28.3). Boxes fill in as slices land.

- **Slice 1 — Identity anchors (model + store + identifier cutover).** The
  structural rebuild; nothing SCIM yet, but everything now keys on username.
  - `internal/models`: `IDPUser` gains `Username` (string, `uniqueIndex`,
    `notNull`); `Email` demotes to a plain indexed column (non-unique).
    AutoMigrate picks it up; fresh-install assumption — old local databases
    hold empty/duplicated usernames: wipe is documented, migration is
    deliberately absent.
  - `proto/cdrom/db/v1` (+ `make proto`): `IDPUser.username`;
    `GetIDPUserRequest` locators reworked to mutually-exclusive
    `id | username | external_id` (more than one set ⇒ InvalidArgument);
    `UpdateIDPUser` gains `username`.
  - `proto/cdrom/idp/v1` (+ `make proto`): `Login`/`Register`/
    `CreateUser`/`UpdateUser` payloads shift email→username (breaking,
    ratified).
  - `internal/idp`: `UserStore` rework — `GetByEmail ⇒ GetByUsername`, new
    `FindByExternalID` (both `includeDeleted`-aware); `Create` requires a
    username, email optional; memstore + dbstore conformances. `grpc.go`:
    Login/Register/CRUD follow suit (first-admin heuristic retained for local
    register); audit attribution strings switch to username.
  - `internal/api`: `loginRequest{username,password}`,
    `registerRequest{username,first,last,email?,password}`, `/api/users`
    DTOs render username primary / email ancillary; userpass client conforms.
  - `server.go` dev-shim `/auth`: synthesize `username=subject`, `email="`
    (stop fabricating `@example.com` domains).
  - Fixtures + existing e2e scripts: mechanical email→username renames.
  - Tests: store-semantics units; SQLite integration roundtrip incl.
    email-less users.
  - Demonstrable: curl register (no email) → login by username → list.
  - Acceptance:
    - [x] Register accepts a user WITHOUT an email; login identifies by
          username; `GET /api/users` renders username primary, email
          ancillary. *(LANDED: live-stack proof — two email-less registrations
          (201), login by username, token-verified admin list rendering
          username-first; e2e 05/06/07/08/18/19/20/21 all passing.)*
    - [x] `GetIDPUser` locators are mutually exclusive (two set ⇒
          InvalidArgument); `FindByExternalID` finds a tombstoned row only
          with include_deleted. *(Covered by `TestIDPUsers` — the double-locator
          InvalidArgument case and the external_id round trip.)*
    - [x] Fresh installs migrate cleanly (AutoMigrate); `GOOS=windows
          GOARCH=amd64 go build ./cmd/...` stays green.
- **Slice 2 — The SCIM `/Users` resource (transport-complete).**
  - `internal/idp` `scim_users.go`: mount the concrete patterns
    (`GET/POST /Users`, `GET/PUT/PATCH/DELETE /Users/{id}`) under the
    existing guard (Accept + key pool + connector attribution); the subtree
    fallback comment updates.
  - Serialisation: the user doc (`schemas`; `meta` from the row's own
    `created_at`/`updated_at`; `location` via `scimLocation`); RFC 7644-
    shaped errors (`status`/`detail`, scalar type where cheap).
  - The conflict matrix per the resolution order above: provision,
    re-provision (`Reactivate` + definite repopulate), got-married rename,
    strict 409.
  - A new Database RPC for **definite profile replace** (explicit per-field
    presence flags — proto3 omitted-means-zero makes today's supplied-value
    `UpdateIDPUser` unfit for PUT); PATCH rides read-modify-write over the
    F-28.3 primitives (last-writer-wins; ETags deferred).
  - Filter parser, the supported subset: `userName eq`, `active eq
    true|false`, `externalId eq`, AND-chaining, quoted values; anything else
    ⇒ 400 `invalidFilter`. Evaluated in memory over
    `List(includeDeleted=false)` sorted by ID (portable; directories are
    people-sized).
  - Pagination: honor `count` (clamped to `EffectiveMaxPageSize` — today's
    `scimListDoc` ignores it; fix), `startIndex` 1-based, `totalResults`
    post-filter.
  - `groups`: parsed, discarded (debug-logged) until F-28.5.
  - Audit: `scim.provision` / `scim.reprovision` / `scim.update` /
    `scim.activate` / `scim.deactivate` / `scim.deprovision` (reads unaudited),
    actor = the presenting connector; metric
    `cdrom_scim_operations_total{op,result}`.
  - Tests: httptest harness (permissive authorizer, cf. the framing suite)
    covering every matrix cell + filter/pagination negatives; SQLite
    integration.
  - Demonstrable: key bootstrap (cf. 19-scim-keys.sh) → POST → list with
    filter → PATCH `active:false` → observe login denial → DELETE → POST
    re-hire (same numeric id).
  - Acceptance:
    - [ ] `POST /Users` provisions a new user mapped per the table (stock
          `user` role placeholder, `provisioned=true`, `active` per payload
          or true).
    - [ ] A duplicate `POST` for an existing active `userName` never creates
          a second row (strict 409).
    - [ ] A `POST` matching a tombstoned user's `userName` or `externalId`
          reactivates the same row (stable ID preserved, history intact) —
          the re-hire case.
    - [ ] A `POST` matching an ACTIVE user's `externalId` with a different
          `userName` renames that row (got-married case); a collision with a
          third party's active `userName` ⇒ 409.
    - [ ] `PATCH {id}` with `active:false` deactivates (record retained,
          credentials suspended); `active:true` restores.
    - [ ] `DELETE {id}` deprovisions via the F-28.3 tombstone semantics;
          subsequent item ops 404.
    - [ ] `GET`/`PUT`/`PATCH`/`DELETE` on an unknown or tombstoned id return
          a 404 SCIM-error.
    - [ ] Lists paginate (`startIndex`/`count`/`totalResults`, `count`
          clamped to the page bound) and respect the filter subset;
          unsupported filter forms return 400 `invalidFilter`.
    - [ ] Responses carry the correct `schemas`/`meta` (row timestamps)/
          `location`; errors are RFC 7644-shaped SCIM-errors.
    - [ ] Every SCIM mutation writes an audit event attributing the
          presenting connector key.
- **Slice 3 — Admission gate (consolidated in the IdP, enforced in the API).**
  - `proto/cdrom/idp/v1`: `AdmitPrincipal(username, email, name, roles[]) ⇒
    verdict (admitted | deactivated | deprovisioned | unknown_rejected |
    no_roles_rejected) + user profile`.
  - `grpc.go`: the mode branching; JIT creation (non-empty claim-derived
    roles required at birth — no stock-role injection); returning JIT users
    refresh name/email from the args and grow roles monotonically
    (`stored ∪ incoming`); local and SCIM-managed users admitted untouched.
    Light sanity bounds (length/charset) on the subject-derived username;
    violations ⇒ denied, no row.
  - `internal/auth` middleware: after token verification, for human user
    principals (OIDC and user-API-key paths; synthetic admin, service
    accounts, job tokens exempt). Subject-claim name configurable (new
    `auth` option, default `sub`); missing ⇒ denied. TTL cache per username
    (positive ≈60s, negative ≈15s constants). IdP unreachable ⇒ fail closed
    (503). Distinct 403 texts per verdict. Metric
    `cdrom_admissions_total{verdict}`.
  - Tests: branch-graph units (memstore); middleware integration (fake IdP
    gRPC); the empty-roles JIT case asserts NO residual row.
  - Demonstrable: stacked run — first login with mapped roles auto-creates;
    flip `scim.enabled` on the same stack ⇒ unknown denied; a SCIM-driven
    deactivation bites the next login within the negative window.
  - Acceptance:
    - [ ] A known + active user is admitted — including the SCIM-provisioned
          user from S2 (completing S2's first box's "can authenticate" leg).
    - [ ] With SCIM disabled, a first login with mapped roles auto-provisions
          (name/email refreshed and roles grown monotonically on return
          visits); zero roles ⇒ denied with NO row created.
    - [ ] With SCIM enabled, an unknown user's login is rejected (no JIT).
    - [ ] Deactivated / tombstoned users are denied with the distinct
          reasons; a SCIM-driven deactivation bites the NEXT login within the
          negative window.
    - [ ] The gate applies to API-key-authenticated user principals too;
          service accounts and job tokens are exempt; IdP down ⇒ fail
          closed.

  - Tests: switch×channel matrix units; system-info shape + non-secret-review

  - Demonstrable: flag off ⇒ standing login 403 while break-glass still signs

  - Acceptance:
    - [ ] Manual edits to a SCIM-managed user's identity fields are refused

    - [ ] `local_login_enabled: false` blocks standing login/register while a

    - [ ] `GET /api/system/info` (unauthenticated) exposes the enablement
