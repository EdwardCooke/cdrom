# F-28.2 · SCIM caller authentication

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** Authenticate the caller of the SCIM surface: every request under
the configured base path (metadata and resources alike) must present
`Authorization: Bearer <key>`, where `<key>` is one of the **SCIM API keys**
maintained in the database. Keys are created, listed, edited, revoked, and
reinstated through administrative endpoints on the API server
(`/api/scim/keys`), which lets operators **rotate the credential with zero
downtime** — mint a successor, repoint the corporate connector, retire the
predecessor — without reloading or redeploying anything. Missing,
malformed, revoked, or expired presentations get a `401` with a
SCIM-error body. This sub-feature delivers the guard that wraps the entire
`/scim/v2` subtree and the recording of failed attempts.

**Why.** The SCIM surface can create, alter, deactivate, and deprovision the
whole user directory — it is an identity-administration power. It is
deliberately a privileged machine-to-machine channel, separate from the
human-facing OIDC sign-in surface. Matching a single static bearer token
baked into IdP config would have made rotation a coordinated config change +
reload across every IdP replica — an outage risk on a channel the corporate
connector exercises continuously. Holding the credential in a small, rotated
pool of database-held keys avoids that coupling: validation is a lookup
against shared state, so all replicas agree, and overlapping key lifetimes
absorb the switchover.

**Slices.** Built as three sequential increments, each ending compiled,
tested, and demonstrable (checkpoint commit per slice):

- **Slice 1 — Foundation (store + semantics + permissions).** The `ScimKey`
  model (automigrated via `models.All()`), the Database service gRPC surface
  (save / bundle-pull / list / get / update / revoke / reinstate / prune /
  mark-last-used) with CANDIDACY governed centrally by the Database service
  (it builds the encoding bundle — the non-revoked candidate set — and enforces
  cap/CAS/prune semantics), the IdP's DERIVATION rpc (draws the key and computes the Argon2ID encoding with the configured pepper), and the five `scim-keys.*`
  permissions registered in the F-14 catalog. Demonstrable: unit/integration
  tests exercise CRUD, the validity transitions (expired / revoked /
  reinstated), and Argon2ID determinism (pepper-sensitive, salt-distinct)
  against SQLite. No behavioural change yet — nothing consumes the pool.
- **Slice 2 — Administrative API + maintenance.** The six endpoints
  (table below) on the API server with RBAC wiring, THIN-PROXY creation
  (asks the IdP to derive the key + Argon2ID encoding, persists through the
  Database service, displays the plaintext exactly once), audit hooks, and
  the hourly prune sweep started alongside the audit pruner. Demonstrable: a curl walkthrough —
  create → list (prefix only) → edit → revoke → reinstate → prune —
  confirming the plaintext appeared exactly once, in the `201`.
- **Slice 3 — Guard + separation.** The IdP `scimGuard` swaps its TODO for
  pool validation (bundle pull + local evaluation + memo), failure
  recording (warning log + audit event), `lastUsedAt` bumps, and the e2e
  scenario proving the
  bootstrap ritual (first key created via the admin API unlocks the
  surface) and the F-25/F-26 separation. Demonstrable: the full acceptance
  matrix below, end to end.

Dependency: S1 → S2 → S3 strictly; S2's endpoints are inert until S3 flips
the guard on, and S3's guard is harmless until S2 can mint keys.

**Scope.**
- `internal/idp` — the auth guard wired into the SCIM router (F-28.1): parse
  the `Authorization` header, resolve the presented key against the pool
  (validation below), and on failure return `401` with a SCIM-error body
  (`status: "401"`, `detail: "Unauthorized"`). Applies uniformly to every
  route under the base path. ALSO the derivation rpc: draws the key + salt
  and computes the Argon2ID encoding with the configured pepper (the ONLY
  pepper-touching sites, with evaluation).
- `internal/models` — the `ScimKey` entity (data model below), registered in
  `models.All()`.
- `internal/services/database` — gRPC surface for the pool: save,
  salt-bundle pull (validation material), list/read/update, revoke/
  reinstate, mark-last-used, and prune. Receives (encoding, prefix) pairs only —
  never the pepper, never the plaintext.
- `internal/api` — the administrative HTTP endpoints (administrative API
  below), acting as THIN PROXIES for derivation (ask the IdP, persist via
  the Database service, display the plaintext exactly once), their RBAC
  enforcement, and the periodic prune sweep (started alongside the audit
  pruner in `cmd/api`).
- `internal/authz` — five new permissions
  (`scim-keys.can-view` / `can-create` / `can-edit` / `can-revoke` /
  `can-reinstate`) registered in the F-14 catalog.
- **Recording** — a failed SCIM auth attempt produces a warning log entry
  (timestamp, remote address, requested path — never the presented key) and
  an audit event (F-15) attributed to an unauthenticated SCIM caller, so
  probing is observable. Successful validations bump the matched key's
  `last_used_at` (writes throttled).

**Design decisions.**
- **Exactly one mechanism: `Bearer <key>` matched against the pool.** No
  key material lives in config: the F-28.1-era `idp.scim.credential` /
  `CDROM_SCIM_CREDENTIAL` setting has been REMOVED, and a stray
  `credential:` key in an existing config file is ignored (unknown scalar).
  Bootstrapping: the first operator creates a key via the administrative
  API and hands its plaintext to whoever manages the corporate connector.
- **The plaintext is never persisted.** The database stores only the
  Argon2ID ENCODING (PHC string — `$argon2id$` with the random salt and
  parameters embedded) plus its first eight characters (`prefix`) as a
  display aid. The full key is shown to the operator exactly once — in the
  `201` response of the create call — and at VALIDATE the plaintext never
  leaves the IdP process (it pulls the encoding bundle and verifies
  candidates locally; decision below). Encoding verification lets the guard
  validate without ever reconstructing the plaintext.
- **Shape: 32 characters, alphanumeric + curated specials, no spaces.**
  Drawn uniformly with `crypto/rand` from a 73-character alphabet (uppercase,
  lowercase, digits, plus `! @$ ^ & * _ - += .`) — roughly 198 bits of
  entropy. Quotes, backslash, forward slash, percent, brackets, and
  parentheses are deliberately absent: they invite escape bugs in shells,
  URLs, and config files.
- **Encoded + peppered KDF (follows the F-25/F-26 house pattern, now
  unified on Argon2ID).** The stored encoding is `argon2id(pepper ‖ key)`
  with the pepper PREPENDED to the KDF input — the same role the pepper
  played in the retired `SHA-512(pepper + salt + key)` formulas. Argon2ID
  draws and EMBEDS its own random salt (16 bytes) in the encoding, so no
  separate salt column is stored; two keys with the same plaintext get
  DISTINCT encodings (defeating precomputed/rainbow tables), and uniqueness
  is intrinsic (collisions are computationally impossible). `pepper` is an
  OPTIONAL secret configured ONLY on the IdP
  (`CDROM_IDP_SCIM_KEYS_PEPPER`); when empty the IdP logs a startup security
  warning (house pattern) and encodings reduce to `argon2id(key)`. ALL
  pepper-touching computation is CONCENTRATED in the IdP: at CREATION the
  IdP draws the key and computes the encoding (the API is a thin proxy —
  coordinate + display, mirroring F-26, where the IdP generates the
  service-account key); at EVALUATION the IdP PULLS the encoding bundle
  (encodings + statuses + timestamps of the non-revoked rows, ≤5) from the
  Database service and verifies the presented key against each encoding
  LOCALLY. As a result the Database service NEVER sees the pepper (it
  persists only the encoding — a stolen database yields material
  unforgeable offline without the pepper) and never sees the presented key
  either. Leaking the encoding bundle is harmless: encodings are openly
  storable and disclose nothing about any key. PERF NOTE: the key profile is
  tuned for per-request verification (≈7 ms/op on commodity hardware; ≈35 ms
  for a full 5-entry bundle walk), comfortably absorbed by the guard's ~1 s
  memo.
- **Overlap, not timers, gives zero-downtime rotation.** A key is valid
  from the instant it is created until it is revoked (or its optional
  `expires_at` lapses) — there is NO automatic ageing-out, so EVERY
  non-revoked key is accepted, however old. Rotation works because several
  keys can be valid at the same time: issue the successor, repoint the
  connector mid-overlap, revoke the predecessor — no restart, no config
  reload, no trapped sequencing, and up to the pool cap of concurrent keys
  all validate simultaneously.
- **Expiration is optional.** `expires_at` (nullable) bounds a key's life —
  e.g. a short-lived key for a third-party tenant, or a belt-and-braces
  sunset on a key the operator may forget to revoke. Effectiveness = not
  revoked, AND (`expires_at` null or in the future).
- **Revocation is undoable for 24 h, then physical.** `revoke` stamps
  `revoked_at` (validation stops immediately). `reinstate` clears it —
  recovering an accidental revocation — provided the stamp is younger than
  24 h. A periodic sweep (~hourly, on the API) **physically deletes** rows
  whose `revoked_at` is older than 24 h,
  keeping the table lean; the audit trail (F-15) retains who/where/when of
  the revocation, so deletion costs no accountability.
- **Completely separate from F-26 service accounts.** Distinct subsystem,
  distinct store, distinct auth path: SCIM keys authenticate the corporate
  IdP's connector against the IdP's `/scim/v2` surface; service accounts
  authenticate principals against the API's HTTP/gRPC surfaces. No shared
  tables, peppers, or fallback between the two — a service-account token
  presented to SCIM gets a 401, and a SCIM key presented to the API does
  too.
- **Timing-safe by construction.** The IdP verifies ALL non-revoked rows
  (≤5 by the pool cap) — decoding each stored encoding and running the KDF
  with the presented key, comparing tags in constant time
  (`crypto/subtle.ConstantTimeCompare`) — REGARDLESS of which row (if any)
  matches, so the CPU profile is independent of the outcome; unknown,
  revoked, and expired all collapse to the identical 401 body — no
  enumeration oracle.
- **Bounded pool.** At most five non-revoked keys at any time; creating
  beyond the cap gets `409`. The lookup stays tiny and operational sprawl
  stays sane.
- **Deny-by-default RBAC.** Managing the pool requires the granular
  `scim-keys.*` permissions (style mirrors F-26); the admin role gains them
  wholesale via `AllPermissions`.
- **Central candidacy, local judgement (Slice 1).** The Database service
  governs WHO qualifies as a candidate (the encoding bundle omits revoked
  rows)
  and HOW the pool mutates (cap, CAS, prune thresholds) — the semantics
  that historically drifted between replicas. The IdP applies the final
  judgement (digest match ∧ expiry) locally over the bundle: the predicate
  is a single boolean conjunction, so replication-drift risk is
  negligible, and the upside is that the presented key never travels to
  the Database service.
- **Derivation is delegated to the IdP (Slice 2).** Mirroring F-26 (whose
  IdP generates the service-account key), the IdP draws the key (32 chars
  from the documented alphabet, `crypto/rand`), and computes
  the Argon2ID encoding with the configured pepper. The API is a thin proxy:
  request derivation → persist (encoding, prefix, description,
  expiresAt, createdBy) via the Database service → display the plaintext
  exactly once (the `201`). The plaintext crosses only the IdP→API response
  leg (mTLS-carried when certs are configured) and the API→operator
  response; it never touches a log and is never persisted.
- **Hot-path memo (Slice 3).** The guard memoizes verdicts ~1 s keyed by
  the presented key (positives AND negatives — negative caching blunts
  brute-force probing), and caches the encoding bundle on the same cadence.
  A WARM request is a local map lookup; a MISS pays one bundle pull + the
  per-row verification walk (≤5 rows × one Argon2ID, ≈7 ms each). Worst-case
  staleness after a revoke is ~1 s, acceptable for a machine channel and
  consistent with the tail-cadence eventualities elsewhere in the control
  plane.
- **CAS mutations (Slice 1).** Revoke/reinstate are compare-and-set on
  `revoked_at` (`SET revoked_at=:now WHERE id=:id AND revoked_at IS NULL` /
  `SET revoked_at=NULL WHERE id=:id AND revoked_at IS NOT NULL AND
  revoked_at > :cutoff`); zero affected rows means a concurrent loser or a
  pruned row → `404`/`409`, never a silent no-op with a misleading `200`.
- **Identifiers are numeric (Slice 1).** The autoincrement `id` is surfaced
  as `identifier`, matching every other resource (`jobs`, `runs`, service
  accounts); the 8-char `prefix` is the human recognition device.
- **Editable attributes, immutable identity (Slice 2).** `PATCH` mutates
  exactly two fields: `description` and `expiresAt`. The identity columns
  (`hash`, `prefix`, `created_at`, creator) are frozen — an edit cannot
  launder a key's provenance. Partial semantics: an omitted field is
  unchanged, an explicit `null` `expiresAt` CLEARS the expiration, and a
  value must be strictly in the future (same rule as create). Edits act
  only on NON-REVOKED keys — a revoked key gets `409` (reinstate first), so
  a PATCH can never dress up a zombie row.
- **Bootstrap ritual, no flags (Slice 3).** Flipping the guard on with an
  empty pool 401s the connector — self-inflicted but recoverable IN BAND:
  the admin API lives on the API server, outside `/scim/v2`, so unlocking is
  always one `POST /api/scim/keys` away. Ops ritual: create the first key
  before relying on the surface; the e2e asserts exactly that ordering.

**Data model** (`ScimKey`, automigrated via `models.All()`):

| Column | Type | Notes |
|--------|------|-------|
| `id` | bigint PK | numeric identifier surfaced as `identifier` |
| `hash` | text | Argon2ID encoding (PHC string; salt + parameters embedded) of `pepper ‖ key` |
| `prefix` | varchar(8) | first 8 characters of the plaintext (display aid) |
| `description` | varchar(200) | operator-supplied label (which connector / environment) |
| `created_by` | string | creating principal (audit link) |
| `created_at` | timestamp | issuance |
| `updated_at` | timestamp | last mutation |
| `expires_at` | timestamp, NULL | NULL = no expiration |
| `last_used_at` | timestamp, NULL | bumped on successful validation (write-throttled) |
| `revoked_at` | timestamp, NULL | NULL = active; non-null = revoked (prune candidate after 24 h) |

**Validation (the guard).** Given a presented `Bearer` value `K` (evaluated
BY THE IdP; the pepper is taken from IdP config and never transmitted):
1. Pull the encoding bundle from the Database service — the non-revoked rows'
   (id, encoding, `expires_at`, `last_used_at`), ≤5 elements — memoized
   ~1 s.
2. Verify ALL bundled encodings, no early exit: for each row `i`, decode
   the encoding (extracting its embedded salt and parameters), derive the
   tag for `argon2id(pepper ‖ K)` with those parameters, and compare tags in
   constant time (`crypto/subtle.ConstantTimeCompare`). The CPU profile is
   thus independent of which row (if any) matches.
3. ACCEPT iff some encoding verifies AND
   (`expires_at IS NULL` OR `expires_at > now`); otherwise REJECT.
4. On accept: attribute downstream SCIM activity to
   “SCIM connector (key #id)” and fire a throttled `MarkLastUsed(id)` at
   the Database service. On reject: emit the identical 401 SCIM-error +
   recording for unknown, revoked, and expired alike — the response
   discloses nothing about which category fired.

**Administrative API.** Mounted on the API server's HTTP mux (`:8080`);
guarded by regular UI authentication + RBAC. These endpoints sit OUTSIDE the
`/scim/v2` tree and consume neither SCIM keys nor service accounts —
operators drive them with an OIDC session or a user API key (F-25) holding
the appropriate `scim-keys.*` permission. Timestamps are RFC 3339 UTC.

| Method & path | Permission | Contract |
|---------------|------------|----------|
| `GET /api/scim/keys` | `scim-keys.can-view` | List all **non-revoked** keys, newest first: `identifier`, `description`, `prefix`, `createdAt`, `expiresAt`, `lastUsedAt` |
| `POST /api/scim/keys` | `scim-keys.can-create` | Create a key. Body: `description` (required, ≤200 chars) and optional `expiresAt` (RFC 3339; omitted/null = no expiration; must be strictly in the future). Responds `201` with the key object plus `key` — the full 32-character plaintext, shown exactly once |
| `GET /api/scim/keys/{id}` | `scim-keys.can-view` | Read one key: the object shape plus `revoked` (`true` for a key within its 24 h post-revocation window — the row still exists, so it is distinguishable from a pruned one). `404` if unknown or already pruned |
| `PATCH /api/scim/keys/{id}` | `scim-keys.can-edit` | Edit mutable attributes: `description` (1–200 chars) and `expiresAt` (omitted = unchanged; explicit `null` = clear the expiration; value = strictly in the future). Non-revoked keys only — `409` if revoked. `200` with the updated object |
| `POST /api/scim/keys/{id}/revoke` | `scim-keys.can-revoke` | Stamp `revokedAt` (validation stops immediately). Idempotent while the row survives the 24 h window. `200` echoes the object flagged `revoked: true` |
| `POST /api/scim/keys/{id}/reinstate` | `scim-keys.can-reinstate` | Clear `revokedAt` (accidental-revocation recovery); responds `200` with the object flagged `revoked: false`. `404` if unknown or already pruned (outside the 24 h window) |

Notes:
- The list element never contains the plaintext or the full digest — only
  the 8-character `prefix` identifies a key visually.
- Errors: `400` malformed body / past `expiresAt`; `404` unknown
  identifier (deliberately indistinguishable from a pruned row — no
  existence leak); `409` outstanding-cap reached; `403` missing
  permission.

**Rotation playbook** (operational runbook; mirrored in the Architecture.md
configuration reference):
1. `POST /api/scim/keys` with a description naming the purpose (e.g.
   “Okta connector — Q4 rotation”); deliver the returned `key` to the team
   managing the connector through a secure channel.
2. Repoint the connector at the new key. Because both keys validate during
   the overlap, the switch and its verification can happen in either order.
3. Confirm the new key is flowing: `lastUsedAt` advances on
   `GET /api/scim/keys`, and the IdP log shows no 401 spike.
4. `POST /api/scim/keys/{old-id}/revoke` the predecessor. Its 24 h reinstate
   window absorbs misclicks; the sweep retires it afterwards.
If step 4 is forgotten, the predecessor lingers as a dormant duplicate key
until somebody revokes it — no outage, just tidying debt; giving rotation
keys an `expiresAt` sunsets them automatically.

**Maintenance (pruning).** An approximately hourly sweep on the API
(started alongside the audit pruner) executes:
`DELETE FROM scim_key WHERE revoked_at IS NOT NULL AND revoked_at < NOW() -
INTERVAL '24 hour'`. Rows disappear; the audit log retains the revocation
event.

**Acceptance criteria.** Tagged by delivering slice (S1 = foundation,
S2 = administrative API + maintenance, S3 = guard + separation).

*S1 — foundation*
- [ ] The database holds only the salt, the salted hex digest, and the
      8-char prefix: no scan of the store recovers the plaintext.
- [ ] Stored keys satisfy the shape contract (32 characters from the
      documented alphabet, no space/quote/`%`/`/`/`\`); digests are salted
      per the formula (two keys with the SAME plaintext get DIFFERENT
      digests), are pepper-sensitive when a pepper is configured, and the
      digest index still guards uniqueness.
- [ ] The Database service never persists the pepper and never RECEIVES the
      plaintext (derivation is delegated to the IdP; validation pulls the
      encoding bundle; the IdP verifies locally); the verification walk covers
      all non-revoked rows with uniform workload (CPU profile independent
      of which row matches).
- [ ] The central validity predicate accepts every non-revoked,
      non-expired key (however old — no automatic ageing-out) and
      distinguishes expired / revoked / reinstated correctly; revoke and
      reinstate are CAS-guarded (concurrent losers get `404`/`409`, never a
      spurious `200`).
- [ ] The five-key outstanding cap is enforced at create (`409` beyond it).
- [ ] The five `scim-keys.*` permissions exist in the F-14 catalog and the
      admin role carries them via `AllPermissions`.

*S2 — administrative API + maintenance*
- [ ] `GET /api/scim/keys` lists non-revoked keys with identifier,
      description, prefix, and timestamps — never the plaintext or the full
      digest.
- [ ] Create enforces the required description and future-only `expiresAt`;
      the full 32-character plaintext is shown to the operator exactly once
      (the `201` response) and persisted nowhere.
- [ ] `PATCH` updates `description`/`expiresAt` (explicit `null` clears the
      expiration; past dates refused), leaves identity columns frozen, and
      refuses revoked keys with `409`.
- [ ] Revoke stops validation immediately (the next request 401s);
      reinstate restores it within the 24 h window; post-prune reinstate →
      `404`.
- [ ] The prune sweep physically deletes rows revoked more than 24 h ago
      and leaves every other row untouched.
- [ ] Pool-management endpoints are denied by default and unlocked by the
      five `scim-keys.*` permissions.

*S3 — guard + separation*
- [ ] Every route under the configured base path (including
      `ServiceProviderConfig`/`Schemas`/`ResourceTypes`) rejects requests
      without a valid pooled key with HTTP 401 and an RFC 7644-shaped
      SCIM-error body.
- [ ] A request bearing a just-created key succeeds (against the F-28.1
      metadata endpoints).
- [ ] Predecessor and successor keys both succeed during the rotation
      overlap; after the predecessor is revoked it gets 401 — and a
      never-revoked key keeps succeeding indefinitely (nothing ages out).
- [ ] Unknown, revoked, and expired keys all get the identical 401 body —
      the response discloses nothing about which category caused the
      rejection.
- [ ] Validation is timing-safe: per-row Argon2ID verification + constant-
      time tag compare across all non-revoked rows; no oracle on key
      existence or shape.
- [ ] Failed attempts are recorded (warning log + audit event) without
      echoing the presented key; successful validations bump `lastUsedAt`.
- [ ] Two IdP replicas serving the same pool (shared database) exhibit
      identical validation behaviour — no config-parity requirement.
- [ ] A service-account token or user API key presented to `/scim/v2` gets
      401 — the SCIM channel is completely separate from F-25/F-26.
