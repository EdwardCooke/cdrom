# F-28.2 · SCIM caller authentication

> Part of [F-28 · SCIM user provisioning](f-28-scim-provisioning.md) · Phase 6 — Authentication · [Feature index](../Features.md)

**What.** Authenticate the caller of the SCIM surface: every request under
the configured base path (metadata and resources alike) must present
`Authorization: Bearer <credential>`, where `<credential>` is the SCIM service
token carried by `idp.scim.credential` (F-28.1). Missing, malformed, or
mismatched presentations get a `401` with a SCIM-error body. This sub-feature
delivers the guard that wraps the entire `/scim/v2` subtree and the
recording of failed attempts.

**Why.** The SCIM surface can create, alter, deactivate, and deprovision the
whole user directory — it is an identity-administration power. It is
deliberately a privileged machine-to-machine channel, separate from the
human-facing OIDC sign-in surface. A single dedicated credential makes the
trust relationship explicit (only the corporate IdP holding it can provision),
easy to rotate, and auditable.

**Scope.**
- `internal/idp` — the auth guard wired into the SCIM router (F-28.1): parse
  the `Authorization` header, compare the bearer token against the configured
  credential in **constant time** (`crypto/subtle.ConstantTimeCompare`), and
  on failure return `401` with a SCIM-error body (`status: "401"`,
  `detail: "Unauthorized"`). Applies uniformly to every route under the base
  path.
- **Recording** — a failed SCIM auth attempt produces a warning log entry
  (timestamp, remote address, requested path — never the presented
  credential) and an audit event (F-15) attributed to an unauthenticated SCIM
  caller, so probing is observable.
- **Deployment note** — the credential is shared by operators with the
  corporate IdP's SCIM connector (most connectors accept a static
  token/header). Rotating it means redeploying/reloading the IdP config; the
  rotation procedure is documented in the Architecture.md configuration
  reference.
- **Future direction (stretch, not MVP)** — replace or supplement the static
  token with an OAuth2 **client-credentials** flow: register a dedicated
  client at our IdP, have the corporate IdP obtain a short-lived JWT from
  `/token` with `grant_type=client_credentials`, and validate it
  cryptographically (signature, audience, expiry) instead of comparing a
  static string. Same guard seam, swapped validator.

**Design decisions.**
- **Static bearer token is the MVP mechanism**: broadly supported by
  corporate connectors (they all offer a “static token” option), zero extra
  infrastructure, and trivially consistent across IdP replicas (same shared
  config). The client-credentials upgrade path is kept open by isolating the
  validation behind the guard.
- **Constant-time comparison** defeats timing oracles on the token.
- **The credential is a secret everywhere**: not persisted to the database,
  not logged, not exposed via API/UI, and never included in audit payloads
  (at-most presence/absence).
- **401, not 403**: the SCIM surface has no notion of “authenticated but
  wrong principal” — there is exactly one authorised caller identity.

**Acceptance criteria.**
- [ ] Every route under the configured base path (including
      `ServiceProviderConfig`/`Schemas`/`ResourceTypes`) rejects requests
      without a valid Bearer credential with HTTP 401 and an RFC 7644-shaped
      SCIM-error body.
- [ ] A request bearing the configured credential succeeds (against the
      F-28.1 metadata endpoints).
- [ ] Token comparison is constant-time; a failed attempt leaks nothing about
      where the first differing byte occurs.
- [ ] Failed attempts are recorded (warning log + audit event) without
      echoing the presented credential.
- [ ] The credential value never reaches the database, logs, metrics, or any
      API/UI response.
- [ ] Two IdP replicas with the same config behave identically towards the
      SCIM caller.
