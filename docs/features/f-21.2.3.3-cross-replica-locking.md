# F-21.2.3.3 · Cross-replica locking

> Part of [F-21.2.3 · Git repository cache](f-21.2.3-git-repository-cache.md) · Part of [F-21.2 · Source-fetcher service](f-21.2-source-fetcher.md) · Part of [F-21 · Config as code](f-21-config-as-code.md) · Phase 4 — Delivery & observability · [Feature index](../Features.md)

**What.** The **per-repository lock** that serializes access to a cached
repository while it is being cloned, fetched, or resynced (F-21.2.3.2). The
lock is a per-repository lock file in the cache root (F-21.2.3.1) created
**atomically** (`O_EXCL`) and carrying a **heartbeat**, with a **stale-lock
timeout** so a crashed replica cannot wedge the shared cache. It exists because
the cache root is a **shared** directory: in a multi-replica (HA) deployment
several fetcher replicas (e.g. two pods in Kubernetes) run against the same
cache on a shared volume (a PVC).

**Why.** Without a lock, two replicas fetching the same repository at once
could read a half-written checkout, double-fetch, or corrupt the index. An
atomic lock file plus a heartbeat is the portable, database-free way to
serialize access to a shared directory across processes and hosts (it uses only
file creation and reads/writes, so it works on both Windows and Linux without
platform-specific advisory locks); the stale-lock timeout makes the lock
self-releasing so a dead fetcher cannot wedge the cache.

**Scope.**
- The **per-repository lock** (a lock file in the cache root, e.g.
  `<dir>.lock`), created atomically (`O_EXCL`) and held for the duration of a
  clone/fetch/resync.
- The **stale-lock timeout** (a heartbeat in the lock file) that lets a replica
  take over a lock held by a crashed or gone-away replica.

**Acceptance criteria.**
- [x] A repository is **locked** while it is being cloned, fetched, or resynced
      (F-21.2.3.2), so a concurrent fetch — on this replica or on another replica
      sharing the cache — never reads a half-written checkout or starts a
      duplicate fetch.
- [x] The lock is a per-repository lock file in the cache root (e.g.
      `<dir>.lock`), created atomically (`O_EXCL`) and held for the duration of
      the fetch/resync.
- [x] A **stale-lock timeout** (a heartbeat in the lock file) lets a replica
      take over a lock held by a crashed or gone-away replica, so a dead fetcher
      cannot wedge the shared cache.
- [x] Multiple fetcher replicas sharing the cache (e.g. two pods on a PVC) never
      read a half-written checkout or double-fetch the same repository.

## Locking

A repository is **locked** while it is being cloned, fetched, or resynced
(F-21.2.3.2), so a concurrent fetch — on this replica or on another replica
sharing the cache — never reads a half-written checkout or starts a duplicate
fetch.

- **The lock file.** The lock is a per-repository lock file in the cache root
  (F-21.2.3.1; e.g. `<dir>.lock`), created **atomically** (`O_EXCL`) and held
  for the duration of the fetch/resync. A replica that cannot create the file
  (another holds it) waits and retries; the mechanism uses only file creation
  and reads/writes, so it is portable across Windows and Linux without
  platform-specific advisory locks.
- **The stale-lock timeout.** The lock file carries a heartbeat (the holder's
  pid + a timestamp, refreshed periodically while held). If a replica holding
  the lock crashes or goes away, its heartbeat stops; after the **stale-lock
  timeout** elapses, another replica takes over the lock. This means a dead
  fetcher cannot wedge the shared cache — the lock is self-releasing.
- **Shared cache.** The cache root is a **shared** directory: in a multi-replica
  (HA) deployment several fetcher replicas (e.g. two pods in Kubernetes) can run
  against the same cache on a shared volume (a PVC). Because the replicas share
  the cache, the per-repository lock plus the atomic index rewrite
  (F-21.2.3.1) keep the replicas from double-fetching or reading a half-written
  checkout.

## Design decisions (folded into AGENTS.md / Architecture.md)

- **A repository is locked across replicas while it is cloned/fetched/resynced.**
  The cache root is **shared** across fetcher replicas (e.g. two pods on a
  PVC), so a repository is **locked** (a per-repository lock file created
  atomically with a heartbeat + stale-lock timeout) while it is
  cloned/fetched/resynced. The lock file lives in the cache root (F-21.2.3.1);
  the heartbeat + stale-lock timeout make the lock self-releasing so a dead
  fetcher cannot wedge the shared cache. The mechanism is portable (file
  creation + reads/writes only) so it works on both Windows and Linux.
- **New fields / RPCs / endpoints (this sub-feature).** The per-repository lock
  (atomic lock file + heartbeat + stale-lock timeout) in
  `internal/services/pipelinesource`.
